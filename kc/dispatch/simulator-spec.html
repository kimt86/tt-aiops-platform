해측 배차 시뮬레이터 — 시나리오 구조 & 필요 요소 (기획)

레이아웃·라우터가 준비된 시뮬레이터에 해측(QC↔야드, TT) 배차를 모델링하는 기획 — 에뮬레이터(장비 물리) ↔ 정책(배차) 구조, 장비 모듈, 시나리오 스키마, 동적 QC 작업지점·베이이동·해치커버, 정책 훅·보정. 지금은 해측만(게이트는 나중).

배차 · 시뮬레이터 기획구현자용
전제·범위

독자: 시뮬레이터 구현자. 전제: 레이아웃 + 라우터는 이미 준비됨 — 빠진 건 에뮬레이터 장비 모듈 + 시뮬레이션 시나리오. 범위(지금): 해측(quayside)만 — QC ↔ 야드 블록을 TT가 나르는 양하(DS)·적하(LD). 게이트(외부트럭·반출입)는 나중. 모든 수치/공식은 라이브 코드·DB로 검증(2026-07-01, MYT=UTC+8).

1. "해측 작업"의 정확한 정의

해측 = QC가 선박을 작업하고 그 컨테이너를 내부 트럭(TT)이 QC ↔ 야드 블록으로 나르는 사이클.

양하 DS:  [TT 빈차]→QC 도착→QC가 배에서 내려 적재→[TT 적재]→야드 블록→YC(RTG) 적치→[TT 자유]
적하 LD:  [TT 빈차]→야드 블록 도착→YC(RTG) 적재→[TT 적재]→QC 도착→QC가 배에 적재→[TT 자유]
  • 배차 결정 = 빈차 구간(TT→픽업)만. 적재 구간은 작업이 정한 고정 경로(QC↔블록).
  • STALL(크레인 굶음): QC가 다음 컨테이너를 처리하려는데 트럭이 없으면 대기 — 해측 성능의 핵심.

포함(지금): QC DS/LD·TT 내부운반·YC 야드 핸드오버·베이이동·해치커버·STALL·선박 마감. 제외(나중·게이트): 외부 도로트럭·게이트 반입/반출·야드 재정리·철도. (배차 로직은 이미 JOBTYPE IN('DS','LD') 전용이라 범위 일치.)

2. 아키텍처 — 에뮬레이터(장비) ↔ 정책(배차)

정책(Policy)매 결정틱(60s) snapshot→배차 주문 · 우리 2단계 매처 | TOS baseline
⇅ 주문(ytno→work) / 상태 snapshot
에뮬레이터(장비 물리)Vessel─QC─YC(RTG)─TT 모듈이 시각 전진 · 라우터로 이동시간 · 이벤트 생성
▼ 종단 KPI
MetricsCollector + CalibrationHarness (§7)
  • 에뮬레이터 = 장비가 주문을 실행하며 물리(이동·크레인 작업·핸드오버·타이밍)를 전개하고 이벤트를 냄(TOS 없이 장비 거동 재현).
  • 정책 = 에뮬레이터 상태를 보고 배차 결정. 우리 정책/TOS baseline 교체 가능.
  • 둘의 경계가 검증의 핵심: 같은 에뮬레이터(물리)에 정책만 갈아끼워 성능 비교.
이전 초안의 잘못

QC를 "cadence+큐", YC를 "flat handover"로 뭉개 베이이동·해치커버·동적 작업지점·YC 큐를 빠뜨림. §3가 이를 장비 모듈로 1급화.

3. 장비 에뮬레이터 상세 — 상태기계 + 이벤트

3.0 공통 — 이벤트 구동 + 모듈 간 핸드셰이크

에뮬레이터는 이산사건(DES). 각 모듈은 다음 이벤트를 시각순 큐에 예약, 클럭은 다음 이벤트로 점프. 정책은 결정틱(60s)에서만 호출되고 그 사이 장비는 이벤트로 자율 전개. 모듈 결합은 이벤트로만:

이벤트생산→소비효과
Dispatch(ytno, work)정책→TT트럭 빈차이동 시작
TruckArriveQC(ytno, qc)TT→QCDS=빈트럭 / LD=적재트럭 도착 → 핸드셰이크
TruckArriveBlock(ytno, blk, cont)TT→YCYC 대기큐 진입
QcMoveDone(qc, cont)QC→TTDS=트럭 적재완료 / LD=트럭 비움
YcServiceDone(blk, ytno)YC→TTDS=트럭 비움(자유) / LD=트럭 적재완료
CraneStallStart/End(qc)QC→Metrics굶음(STALL) 누적
WorkPointMoved(qc, loc)QC→좌표맵동적 작업지점 갱신(§3.2)
TruckFree(ytno)TT/YC/QC→가용 풀다음 틱 후보 복귀

수요 노출: QC는 자기 큐의 앞쪽 horizon 미배차 컨테이너를 "dispatchable work(=Q)"로 노출(live_candidate Q-status 대응). 정책이 배정하면 'A', QC가 소비하면 제거.

3.1 선박(Vessel) 에뮬레이터

  • 역할: QC가 walk할 베이 플랜 + 출항 마감.
  • 적부구조는 데이터에 인코딩 — live_workqueue.queuename = <베이><D|H>-<D|L>: 02H-D=베이02·홀드·양하, 08D-D=베이08·덱·양하, 06H-L=베이06·홀드·적하. total_qty=그 (베이,덱/홀드) 수, seq=QC 처리 순서.
  • 상태: 베이별 잔여(QcMoveDone마다 감소). 전 베이 소진 → VesselComplete.
  • 출항: estdep에 떠남. 그 시각 미완 work는 마감 미스로 집계(1차: 정시 출항 가정).

3.2 QC 에뮬레이터 — 상태기계 ★핵심

상태: IDLE → GANTRY → HATCH → AWAIT_TRUCK(STALL) → WORKING → … → DONE. 보유: 현재 베이/덱홀드, 진행 work, 동적 작업지점.

[다음 큐항목 (bay,dh,job,qty) 진입]
  bay ≠ 현재베이  → GANTRY : clock += BAY_CHANGE_S(180); 현재베이=bay; emit WorkPointMoved
  해치 전환       → HATCH  : 양하 덱→홀드 += HATCH_DS(340) | 적하 홀드→덱 += HATCH_LD(390)
  remaining = qty
[컨테이너 스텝] (remaining > 0)
  이 컨테이너를 dispatchable work로 노출
  필요 트럭이 작업지점에 있나? (DS=빈트럭 도착 / LD=이 컨테이너 실은 트럭 도착)
    예   → WORKING : clock += move_s(learn_qc_move_time, 폴백 DS90/LD110); schedule QcMoveDone
    아니오 → AWAIT_TRUCK : emit CraneStallStart; TruckArriveQC 대기
on TruckArriveQC: AWAIT_TRUCK였으면 CraneStallEnd → WORKING
on QcMoveDone(cont):
  DS: cont 트럭 위 → 트럭 적재상태로 야드 블록 출발(TT)
  LD: cont 배 위  → 트럭 비움 출발(TT)
  remaining -= 1  (트윈쌍이면 -= 2)
  remaining == 0 → 다음 큐항목 / else 컨테이너 스텝
  • ★ 동적 작업지점: GANTRY마다 갱신 = 현재 베이 안벽 위치(선석위치 + 베이오프셋). TT의 DS 픽업/LD 드롭 끝점이 이걸 따라감(리플레이는 QC GPS로 검증).
  • STALL = AWAIT_TRUCK 누적 — 우리 정책 가치의 주 측정량. QC 진행 = max(cadence, 트럭 공급). (라이브 workpool.rs의 베이전환/해치 가산·move_factor와 동일.)
  • 노브: ① 에이프런 버퍼(1차 0=1:1 보수, 옵션 k대 → STALL 완화). ② LD 적재 순서(1차 큐 엄격, 옵션 도착순).

3.3 YC(RTG) 에뮬레이터 — 대기큐 있는 서비스

상태: IDLE → SERVING → … + 대기 트럭 FIFO 큐.

on TruckArriveBlock: 큐에 추가; IDLE이면 서비스 시작
[서비스 시작] state=SERVING; clock += yc_service_s(블록내 갠트리 + 리프트, rtg_move_log 분포)
on YcServiceDone:
  DS: cont 적치 → 트럭 비움(자유)     LD: cont 트럭 적재 → QC로 출발(TT)
  큐 dequeue; 남았으면 다음 서비스 / else IDLE

큐 대기가 K_RTG_Q(~544s)의 큰 부분 — 블록 혼잡이 핸드오버 지연을 만듦(YC move 자체는 LD 84·DS 60s). 매핑 yt_topos(예 04U-0809)→블록→YC. 1차 블록당 YC 1대·서비스 분포; 옵션 2 RTG/블록.

3.4 TT(트럭) 에뮬레이터 — 사이클 상태기계

상태: IDLE → EMPTY_TRAVEL → AT_PICKUP → LADEN_TRAVEL → AT_DROP → (IDLE). 이동시간=라우터. 끝점: 현위치 / QC 동적 작업지점 / 블록(YC).

차량 주행속도 = GPS 실측 22.8 km/h (움직이는 30초 구간 중앙, p90 41)

⚠ 점대점 "유효속도"(직선 ~6.9 km/h)는 정지 ~47%가 섞이고 짧은 leg에 가중돼 너무 느림 — 그대로 쓰면 안 됨. 라우터에 주행속도 ~23 km/h만 쓰고, 정지(큐·대기·신호)는 에뮬레이터(QC/YC 핸드오버·큐·STALL)에서 별도 모델(차량 속도에 넣으면 이중계상). 검증: 라우터(주행)+에뮬레이터(정지) 합 = 실측 leg시간·C1(TT 사이클 740s). 확률 모드: 로그정규 샘플링(mu=ln(p50), sigma=(ln(p90)−ln(p50))/1.2816, 실측 p90/p50≈2.4).

leg 분해 — ARRIVED가 물리 도착과 일치(중앙 −4s)

빈차 leg을 30초 GPS 모션분할로 구간시간(total_s, 비용 라벨) + 주행(drive_s ~53%)/정지(stop_s ~47%)로 쪼갬. 핵심: 크레인 큐는 도착 이후이지 이동시간 안이 아님. 동일 OD 변동계수 0.758(±76%)=대기 잡음이 거리모델 정확도 바닥. (한때 '진입 대기(approach)'를 1단계 신호로 쓰려 했으나 일관 측정 시 중앙 ≈0·옛 67s는 선택편향이라 폐기. 비용 라벨도 drive_s가 아니라 구간시간. learn_leg_decomp는 진단용이었고 retire됨 mig 0081.)

3.5 워크드 예시 — DS 컨테이너 1개

t=0    [정책] TT_42(idle, 안벽 인근) → C11 베이02 양하 배정 → Dispatch
t=0    [TT] EMPTY_TRAVEL: 라우터(현위치→C11 동적작업지점)=95s
t=80   [QC] C11 트럭 없음 → AWAIT_TRUCK, CraneStallStart
t=95   [TT→QC] TruckArriveQC → CraneStallEnd(굶음 15s) → WORKING move_s(DS)=90s
t=185  [QC] QcMoveDone → TT_42 적재 → LADEN_TRAVEL(C11→02J 블록)=210s
t=395  [TT→YC] TruckArriveBlock(02J). YC 큐 비어 즉시 SERVING=70s
t=465  [YC] YcServiceDone → TT_42 자유 → 다음 결정틱(t=480) 후보
지표: C11 STALL +15s, TT_42 공차 95s·적재 210s·핸드오버(90+70)s.

LD는 대칭: 트럭이 블록 먼저(YC 적재) → QC(적재), QC STALL = 그 컨테이너 실은 트럭을 기다린 시간.

3.6 장비 작업시간 — 스펙 분해 vs 실측 ★시간 계산의 근거

결론 — 스펙 분해는 우리 운영로그로 신뢰 불가 → 실측 분포 채택

(A) 실측 집계(learn_qc_move_time 중앙값+상수)는 거리·단(tier)·블록내 위치 의존을 뭉갬. (B) 스펙 분해(물리 동작×장비 속도)는 정확하나, 위치 회귀로 갠트리/권상 속도 분해는 신뢰 불가: ① 무브간 gap이 truck 대기에 묻힘(QC 갠트리 회귀 ≈0), ② 단변량 회귀가 교란(YC 권상 회귀 −0.68 비물리), ③ COMP−ST 무브시간이 권상 사이클을 못 잡음. → 실측 유효시간 분포를 씀(시뮬이 로그정규 샘플). 정밀 분해는 PLC 모션로그 같은 별도 계측 필요(현재 없음). 재현: scripts/estimate_equipment_specs.sh.

순수주행 = 주행 구간 시간(출발→작업지점 도달; 경로 정체 포함·핸드오버 대기 제외) → 배차 cost = 추론 도로망 최단시간 경로를 실측 곡선으로 변환(roadgraph.rs RouteCost/CostCurve: road_route_eval에서 경로시간 6구간별 실제 p50/p90 초를 매듭으로 직접 학습 — 단조 잠금·짧은 경로 바닥 ~89s·매듭 보간). L3 폴백(라우팅 불능 ~3%) = 같은 표의 맨해튼→실제 곡선(콜드스타트만 quay_manhattan_m ÷ 3.30 m/s). Stage-2 cost = 빈차 도착시간 = free_in(곧빔 잔여) + TRAVEL. 처음의 "비율 × 경로시간, 4구간+중점보간"은 당일 리뷰 탈락(비단조 역전·바닥 소실). 소스 변천: 순수-OD → 실현 → 움직인순간만 → 구간시간 → 도로망 곡선(현재). 삭제됨(STALE): learn_travel_zone225_pure, learn_travel_drive_sample, learn_eval, learn_crane_approach, learn_leg_decomp, learn_travel_zone225_drive. learn_travel_zone225(실현·핸드오버 포함)은 갱신되나 cost엔 미사용. 자세히 → 이동시간 모델.

4. ★ 시나리오 구조

에뮬레이터를 초기화·구동하는 모든 것. 모듈 상태(§3) + 적부계획.

Scenario {
  meta: { id, start_ts, duration_s, decision_tick_s: 60, source: "replay:<win>"|"synthetic", seed },
  vessels: [ { vessel_id, voyage, berth_id, berth_loc, estwkc_ts, estdep_ts, cutoff_ts,
    bays: [ { bay, dh:"D"|"H", job:"D"|"L", qty } ] } ],          // queuename 디코드=적부계획
  cranes: [ { qc_id, vessel_id, start_loc,
    queue: [ { bay, dh, job, qty, deadline_ts } ] } ],            // seq 순서. work 단위
  yards:  [ { block_id, loc, latlon, dims:{rows,bays,tiers}, pitch:{row_m,bay_m} } ],
  equipment_specs: {                                             // 실측 분포(§3.6), 로그정규 샘플
    qc_move_s:  { DS: 90,  LD: 121 },
    yc_service: { DS: [10,51,140], LD: [10,76,164] },            // p10/p50/p90
    hatch_s:    { ds: 428, ld: 496 }, bay_change_s: 180 },
  fleet: [ { ytno, loc, latlon, state, free_at_offset_s } ],     // truck_pos_hist/classify_tt/free_in
  env:    { travel:"router", policy_od:"router"|"learned", stochastic: bool },
  policy: { kind:"ours"|"tos_baseline", params:{ SWITCH_PENALTY_S, NEED_HORIZON_S, fleet_size, ... } }
}

개별 work는 시나리오에 정적으로 박지 않음 — QC 모듈이 queue(베이 플랜)를 walk하며 동적 생성(베이이동·해치커버·STALL이 ready/작업지점을 시점마다 바꿈). 각 work: {work_id, qc_id, queuename, container, twin_key, quay_loc=QC현재위치(동적), yard_loc=block, deadline_ts(정적)}.

§4-주 마감

deadline = min(estdep−버퍼, estwkc[가드]). estwkc는 대부분 쓰레기라 출항 0~6h前 정상값일 때만(라이브 finish_by 로직). 선박은 정시 출항 → deadline 정책무관 정적. ready는 §3.2 동적.

5. 시나리오 만들기 — 리플레이 vs 합성

  • (A) 합성 — 1차 권장: 선박 수·QC 수·베이 플랜(베이수×덱/홀드×수량)·블록 분포·트럭 수·마감여유·트윈비율 파라미터화. 부하/공급비/적부패턴을 의도대로 통제.
  • (B) 리플레이: 충실 윈도 = 최근 약 2일(병목 GPS truck_pos_hist 2일). start_ts 트럭위치·QC 큐·마감·cadence를 실데이터로. 반사실 불가(정책 바뀌면 궤적이 달라져 과거 GPS 재생 불가) → 초기조건+적부계획만 실데이터, 이후 전진 시뮬. TOS 실제배차는 baseline 교차검증용.

live_*는 매 ETL 덮어쓰기 → 과거 큐·마감 추이 미보존. 장기 리플레이엔 append 이력테이블 별건.

6. 정책 훅 (코드 재사용 — 재구현 금지)

매 decision_tick_s(60s): snapshot → 배차. 에뮬레이터 상태에서 snapshot 합성 → 정책 호출 → 주문을 에뮬레이터가 실행.

우리 정책 = 2단계 매처(crates/api/src/livemap.rs 추출):

  • 1단계(선택·위치무관): (굶는 QC 먼저 → 마감 빠른 순) + per-crane 수요캡 NEED_HORIZON_S(900)/move_s(DS10·LD8).
  • 2단계(매칭·위치고려): edge=빈차도착+anti-thrash(SWITCH_PENALTY_S 180, COMMIT_LOCK_S 1200, arr<1800). 최적해=3층 MCMF(optimal_assign). 긴급도는 비용에 없음(전부 1단계).

정책 비용추정 OD(env.policy_od): "router"(1차, 배차결정 품질만 격리) | "learned"(도로망 경로시간→실제 곡선 — 라이브 배차 RouteCost와 동일, 라우팅 불능은 맨해튼→실제 곡선).

도로망 라우팅(2026-07-02 갱신)

추론 도로 그래프(road_node/road_edge·Rust 방향 Dijkstra)가 재구축 후 배차 cost에 연결 — 작업지점 5,888곳 커넥터(스냅 100%)·방향은 도로 단위 다수결·기점 정렬(경로 성공률 96.7%). 첫 판(264노드·스냅 30%)의 탈락은 재구축으로 뒤집힘. 시뮬 "router"도 같은 그래프를 쓰면 라이브 배차와 정합. TOS = 보정 baseline(알고리즘 역공학 금지): 알려진 행동(유휴 트럭만 배차·픽업 최단) 휴리스틱 → 같은 에뮬레이터에서 실측 KPI 재현하면 유효.
