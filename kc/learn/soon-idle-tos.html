곧 유휴될 차량 감지 — TOS DB 최소부하 + QC/RTG 핸드오버

배차의 핵심 하나는 곧 유휴될 차량을 미리 감지하는 것. 웹소켓만으론 양하(DS)가 구조적으로 약하고(RTG가 PLC 미전송) 라벨 확보도 어렵다. TOS DB를 보조로 쓰되 부하를 최소로 주면서 (1) 핸드오버 시작 시점, (2) 대상 차량을 얻는 방안 연구.

차를 비우는 핸드오버가 LD는 PLC 있는 QC에서, DS는 PLC 없는 RTG에서. 라이브 tt_cycle_log(61,279 사이클)에서 드롭측 크레인 도착 포착 = LD 50.1% vs DS 0.0%(DS 23,219건 중 4건만 PLC로 잡힘). → "선적 곧유휴는 풀리고, 양하 곧유휴는 구조적으로 어렵다".

권장 — 하이브리드

웹소켓을 1차 라이브 감지로, TOS를 권위·라벨·지연보정 2차로. LD는 PLC가 긴 호라이즌(~90~120초)을, DS는 RTG 근접이 짧은 호라이즌(관여 후 ~30초)만 주되 RTG 미관여 차는 풀에 넣지 않음(오포함 방지).

최소부하 결론: 곧유휴 입력의 대부분(대상차량·작업종류·ETW·배정RTG·POW)은 이미 live_workpool에 90초 주기로 존재 → LD엔 Oracle 추가추출 불필요(234행 전부 ytno·armgc, 95% ETW). DS도 거의 공짜로: 같은 90초 스캔에 JOB_ODR_ACTV_DT 컬럼만 추가(Oracle 추가 쿼리 0).

연구 2차 — prod Oracle 직접 검증 (2026-06-14)

1차는 운영 Oracle 직접조회 금지 제약하에 삼각측량했고 몇 가지를 (미검증)으로 남겼습니다. 저부하 직접조회 허용으로 완화되어 prod TOS Oracle에 직접 질의(직렬·인덱스안전·행수 캡, ~8개 바운드 쿼리) — 양하(DS) 곧유휴 신호가 TOS 라이브에 직접 존재함을 발견.

웹소켓 단독 분류의 약점

현행 곧유휴는 순수 웹소켓 분류(classify_tt()). 각 TT를 5개 상태로: idle / empty_travel / delivering / soon_idle / wait_rtg(+staging). 세 약점:

  • DS엔 물리 신호 없음 — PLC(ctab)는 안벽 C/M/Z만, RTG 미수신.
  • 도착 ≠ 곧유휴 — RTG가 여러 블록·레인 공유해 도착 차를 바로 안 받음("도착했으나 RTG 멀어 대기"=wait_rtg).
  • GPS는 성기다 — 장비당 ~3초, 정지 시 30~55초(도착/출발 시각 ±수십 초 흔들림).

라벨 난제: container1은 TOS 배정 필드이지 물리 적재가 아님(피드 의미론). DS 드롭측엔 정밀화할 신호가 없음(QC측은 PLC ±1초, RTG측은 GPS dwell만).

최소부하 추출 설계

90초 주기로 이미 있는 것(live_workpool 234행): 대상차량 ytno(100%)·작업종류·ETW(95%)·배정RTG(100%). → LD 곧유휴엔 Oracle 추가추출 불필요. 추가 필요 단 하나: 양하 "방금 유휴" 권위 확정 = JOB_ORDER_HISTORY.ACTV_DT 저지연 감지.

현 부하: workpool 90초 = WORKPOOL ~1.2s + WORKQUEUE ~1.6s + ASSIGNED ~0.85s = ~3.7s/tick. 이미 적용된 최소부하 기법: 진행중-only(COMPDATE IS NULL)·상태 화이트리스트·시간경계·인덱스 안전 술어·직렬화·API Oracle 무접근. 미적용이던 증분 워터마크는 아래에서 가동.

하이브리드 감지 로직 — 폴백 사다리

1순위: QC PLC load 전이 (LD, ±1초)       → soon_idle 확정 + 긴 호라이즌
