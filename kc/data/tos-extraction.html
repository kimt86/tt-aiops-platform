TOS 데이터 추출 전수 — 무엇을·어떻게·얼마의 부하로

우리 시스템(TT AIOps 플랫폼)이 TOS Oracle DB에서 가져오는 모든 것을 한 곳에 정리한 문서입니다. ① 어느 테이블의 어느 컬럼을 어떤 조건·주기로 가져오는지(SQL 원문 포함), ② 그 데이터가 우리 쪽 어느 테이블에 채워져 무슨 목적으로 쓰이는지, ③ 이 동작이 TOS DB에 주는 모든 종류의 부하 산정. 내부 파악용이면서, TOS팀에 공유해 승인을 받기 위한 문서입니다.

0. 핵심 요약 (TOS팀께 — 한 문단으로)

Bottom line

우리 접근은 전부 읽기 전용 SELECT입니다 — INSERT/UPDATE/DELETE/DDL/PL·SQL/잠금이 0건입니다. 총량은 하루 약 7,500회(시간당 약 313회, 평균 11.5초당 1건)의 짧은 단문 조회이고, 동시 세션은 발화 시각을 초 단위로 분산해 통상 1개, 순간 최대 2~3개입니다. 모든 조회는 인덱스 시크 또는 시간창으로 범위를 좁힌 조회이며(활성 경로에 무제한 풀스캔 없음), 가장 무거운 단일 쿼리는 야간 01:30에 하루 1번 도는 8.3초짜리입니다. 반환 데이터는 하루 약 340만 행·전송량 약 0.8GB(평균 약 0.08 Mbps) 수준입니다. 어떤 스트림이든 1분 안에 개별·전체 중단할 수 있는 킬스위치가 있습니다.

1. 왜 이렇게 접근하나 — 사본(mirror) 구조

TOS Oracle본부 장부 · 읽기만
→
추출기단문 SELECT · 주기적
→
우리 Postgres로컬 사본
→
대시보드 · 배차 계산 · 시뮬레이션

대시보드·배차 계산·시뮬레이션·KPI는 전부 우리 사본(Postgres)만 봅니다. TOS Oracle에 닿는 것은 추출기 하나뿐입니다. 그래서 화면 사용자가 늘거나 내부 분석이 무거워져도 TOS 부하는 변하지 않습니다 — TOS가 감당하는 것은 이 문서에 적힌 고정된 추출 주기가 전부입니다. 지표(KPI) 계산도 2026-08-06부로 대부분 사본 위에서 재계산하도록 전환해, Oracle을 다시 스캔하는 지표 경로는 아래 ⑨ 하나만 남았습니다.

2. 접근 통로와 보호 장치

  • 단일 통로 — 모든 Oracle 접근은 전용 읽기 계정으로 SQL 게이트웨이(remote-toolbox-sql) 한 경로만 지나갑니다. 애플리케이션이 DB에 직접 붙지 않습니다.
  • 직렬화 — 프로세스 내 잠금 + 파일 잠금(flock)으로 같은 계열 쿼리는 항상 한 번에 하나씩만 나갑니다.
  • 발화 시각 분산 — 주기 작업들의 시작 초를 서로 다르게 고정(:05/:15/:25/:30/:35/:45/:50/:55)해 같은 순간에 겹치지 않게 했습니다(아래 §5 시각표).
  • 타임아웃 — 쿼리당 45~90초 강제 종료. 폭주 쿼리가 세션을 오래 붙들 수 없습니다.
  • 행 수 캡 — 스트림 쿼리는 FETCH FIRST N ROWS ONLY(3,000~20,000)로 상한을 박아, 예외 상황에도 반환량이 폭주하지 않습니다.
  • 병렬 억제 — 집계 쿼리에 /*+ NO_PARALLEL */ 힌트. Oracle 병렬 슬레이브를 쓰지 않습니다.
  • 킬스위치 — 스트림별 systemd 타이머 정지 또는 환경변수 한 줄로 개별·전체 즉시 중단(§8).
  • 변경 통제 — 쿼리·주기를 바꾸면 이 문서를 같이 갱신하고(맨 아래 규칙), TOS팀 공유 프로세스를 거칩니다(§9 제안).

① qc-moves — 안벽 크레인(QC) 작업 이벤트

MCH_OPERATION → 우리 qc_move_log · 60초 · 회당 ~41행 · PK 시크

SELECT /*+ INDEX(MCH_OPERATION MCH_PK_OPERATION) */
       MCH_OPER_MACHNO AS machno, SUBSTR(MCH_OPER_CONTNO,1,11) AS contno,
       MCH_OPER_SEQNO AS seqno, MCH_OPER_JOBTYPE AS jobtype, TRK_ID AS trk_id,
       ST_DT AS st_dt, MCH_OPER_COMPDATE||MCH_OPER_COMPTIME AS comp_dt,
       MCH_OPER_STATUS AS status, MCH_OPER_QUEUENAME AS queuename,
       MCH_OPER_VESSEL AS vessel, MCH_OPER_VOYAGE AS voyage
  FROM TOSADM.MCH_OPERATION
 WHERE MCH_OPER_SEQNO >= '{워터마크-120초}'
   AND MCH_OPER_SEQNO <= '{현재시각}'
   AND REGEXP_LIKE(MCH_OPER_MACHNO, '^(C|M|Z)[0-9]')
   AND LENGTH(MCH_OPER_COMPTIME) >= 6
 ORDER BY MCH_OPER_SEQNO
 FETCH FIRST 5000 ROWS ONLY

부하 근거: MCH_OPER_SEQNO가 PK 선두 컬럼이라 >=워터마크는 인덱스 시크로 새 꼬리만 읽습니다(실측: 시크 ~0.8초 vs 풀스캔이면 ~45초 — 그래서 힌트로 시크를 고정). REGEXP는 그 작은 꼬리에만 적용되는 후처리 필터입니다.

용도: qc_move_log는 안벽 크레인이 "언제 어느 상자를 다뤘나"의 사본 원장입니다. 배차 계산의 작업 도달 정답지(완료시각 comp_ts), 크레인별 처리 속도 학습, 배차 마감 역산, 로컬 KPI 계산의 공통 앵커로 쓰입니다.

④ pool_tick — 작업 풀 + QC 작업큐 (한 왕복으로 병합)

   AND s.JOB_QUE_CRANENO IS NOT NULL

   AND ( NVL(s.JOB_QUE_TOTALQTY, 0) > NVL(s.JOB_QUE_COMPQTY, 0)
         OR s.UPD_DT >= SYSDATE - 0.25 )
UNION ALL
SELECT 'WP' AS src,
       l.JOB_ODR_QUEUENAME, l.JOB_ODR_VESSEL, l.JOB_ODR_VOYAGE,
       CAST(NULL AS VARCHAR2(16)), CAST(NULL AS VARCHAR2(8)),
       CAST(NULL AS NUMBER), CAST(NULL AS NUMBER), CAST(NULL AS NUMBER),
       CAST(NULL AS NUMBER),
       l.JOB_ODR_JOBTYPE, l.JOB_ODR_JOBSTATUS, l.JOB_ODR_YT_STATUS,
       l.JOB_ODR_YTNO, l.JOB_ODR_ARMGC, l.JOB_ODR_ETW_DT, l.JOB_ODR_ACTV_DT,

(전문은 저장소 crates/extractor/sql/pool_tick.sql — 위는 컬럼 일부를 줄인 동일 구조입니다.)

부하 근거: 두 표 모두 "살아있는 것만" — 큐는 최근 1일 내 수정 + 미완(또는 6시간 내 완료), 작업은 미완료(COMPDATE NULL) + 최근 2일 생성분으로 시간창이 좁게 고정되어 있습니다. 반환 ~2,000행/회로 안정적입니다.

용도: 이것이 배차 계산의 본체 입력입니다. live_workqueue(QC별 작업 순서·진척)로 크레인이 각 상자를 다룰 시각을 예측하고, live_workpool(진행 중 + 미배차 상자)과 live_candidate(미배차 수요 집계)로 후보 풀을 만들며, live_assigned_tt(배정 트럭 명단)로 트럭 가동 상태를 봅니다. 화면의 QC 작업 카드·배차 비교도 전부 이 사본을 읽습니다.

2026-08-24 고침 — 배차됐는데 아직 트럭이 상자를 안 실은 작업도 담습니다: 터미널 시스템은 트럭을 붙이는 순간 그 사실을 작업 줄에 바로 적습니다(대기 상태 그대로, 트럭 번호와 배차 시각만 채워짐). 전에는 우리 프로그램이 이런 줄을 "진행 중도 아니고, 완전 미배차도 아니다"라며 버렸습니다. 그래서 배차된 사실을 트럭이 상자를 실은 뒤에야 알았습니다(양하는 보통 9분 늦게). 지금은 이 줄도 그대로 담아서, 배차 사실을 늦어도 1분 안에 압니다. 터미널 시스템에서 더 가져오는 것은 없습니다 — 이미 받아오던 줄을 버리지 않게 됐을 뿐입니다.

2026-08-11 추가 — YT_DIS_DT(터미널 시스템이 트럭을 붙인 시각): 전에는 "이 작업 줄이 마지막으로 바뀐 시각"을 배차 시각 대신 썼습니다. 대개는 둘이 같지만, 배차한 뒤에 그 줄이 또 바뀌면 그 값만 뒤로 밀립니다. 실제로 재보니 트럭이 붙은 작업의 절반가량이 그런 상태였고, 벌어진 차이가 큰 쪽은 30분을 넘었습니다. 그래서 밀리지 않는 원래 값을 따로 받기로 했습니다. 이 표는 이미 1분마다 통째로 읽고 있어서 조회를 더 하지 않습니다 — 읽던 줄에서 칸 하나를 더 가져올 뿐입니다.

⑨ k_cycle — 작업 취급 구간 통계 (야간 1회, 가장 무거운 쿼리)

JOB_ORDER_HISTORY(어제 하루) → 우리 raw_k_cycle · 매일 01:30 · 8.3초 · 반환 10행

WITH job_events AS (
  SELECT JOB_HIST_JOBTYPE, JOB_HIST_CONTNO, JOB_HIST_POINT, JOB_HIST_SEQNO,
         COUNT(*) AS transitions,
         MIN(JOB_HIST_DATE||JOB_HIST_TIME) AS first_evt,
         MAX(JOB_HIST_DATE||JOB_HIST_TIME) AS last_evt
    FROM TOSADM.JOB_ORDER_HISTORY
   WHERE JOB_HIST_DATE = '{어제, YYYYMMDD}'
   GROUP BY JOB_HIST_JOBTYPE, JOB_HIST_CONTNO, JOB_HIST_POINT, JOB_HIST_SEQNO
), cycles AS (
  SELECT JOB_HIST_JOBTYPE, transitions,
         (TO_DATE(SUBSTR(last_evt,1,14),'YYYYMMDDHH24MISS')
        - TO_DATE(SUBSTR(first_evt,1,14),'YYYYMMDDHH24MISS')) * 86400 AS cycle_sec
    FROM job_events WHERE transitions > 1
), stats AS (
  SELECT JOB_HIST_JOBTYPE, COUNT(*) AS jobs, AVG(cycle_sec) AS avg_cyc,
         STDDEV(cycle_sec) AS std_cyc, MEDIAN(cycle_sec) AS med_cyc, ...
    FROM cycles GROUP BY JOB_HIST_JOBTYPE
)
SELECT /*+ NO_PARALLEL */ ... FROM stats s
 ORDER BY s.jobs DESC FETCH FIRST 15 ROWS ONLY

부하 근거: 활성 경로에서 유일하게 남은 Oracle 지표 재스캔입니다. 어제 하루 파티션만(날짜 리터럴 등호 조건), 야간 01:30 단독, 하루 1회 8.3초. 나머지 지표 15종은 전부 로컬 사본에서 계산하도록 전환을 마쳤습니다.

용도: raw_k_cycle은 작업 1건의 취급 구간(첫 이벤트~마지막 이벤트) 분포 — 내부 분석용 참고 통계입니다(화면 표시 지표는 로컬 계산본을 씁니다).

7-5. 동시성·잠금·쓰기

  • 동시 세션: 발화 초 분산(§5)으로 통상 1개. 저빈도 작업(⑦⑧⑫)이 순간적으로 겹치면 최대 2~3개.
  • 잠금: SELECT만 수행하므로 행/테이블 잠금을 잡지 않습니다(읽기 일관성만 사용). 언두 부담은 쿼리 지속시간(대부분 ~2초)에 비례하는 통상 수준입니다.
  • 쓰기: DML/DDL/시퀀스/프로시저 호출 0건. TOS 데이터는 어떤 경로로도 변경되지 않습니다.

7-6. 시간대 분포

  • 주기 작업은 24시간 균등(피크 없음). 유일하게 무거운 ⑨는 야간 01:30 단독 배치.
  • 일회성 검증 조회(사람이 돌리는 조사)는 별도 절차로 통제 — 항상 범위 제한 + 저부하 시간대, 도구 강제 잠금(flock) 경유.

9. TOS팀께 확인·요청 드리는 사항

  1. 현행 승인: 위 12개 추출점·주기·쿼리(§6)에 대한 승인을 요청드립니다. 전부 읽기 전용이며 총량은 §0 요약과 같습니다.
  2. 계정: 현재 사용 중인 읽기 전용 계정의 유지(권한 축소 방향 환영 — SELECT 외 권한은 필요 없습니다).
  3. 교차 검증: 우리 측정은 전부 우리 쪽에서 잰 값입니다(Oracle에 측정 부하 추가하지 않음). 필요하시면 해당 계정 기준 AWR/ASH로 실제 DB 시간을 교차 확인해 주시면 이 문서에 반영하겠습니다.
  4. 변경 절차 제안: 쿼리 추가·주기 단축 등 부하가 늘어나는 변경은 사전 공유 후 진행하고, 부하가 줄어드는 변경은 사후 통지로 갈음하는 절차를 제안드립니다.
  5. 비상 연락: TOS DB에서 이 계정의 이상 부하가 관측되면 연락 주시는 즉시 §8 절차로 중단하겠습니다.
