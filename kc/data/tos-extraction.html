TOS 데이터 — 무엇을·어떻게·얼마나 긁어오나 (전수 해설)

우리 시스템이 터미널 본부 시스템(TOS Oracle DB)에서 긁어오는 모든 것을 — 어느 테이블의 어느 값을 · 어떤 쿼리로 · 얼마나 자주 · 얼마의 부하로 · 어떻게 가공해 · 무슨 의미로 쓰는지 — 신입도 이해하도록 한 곳에 정리한 살아있는 참조 문서입니다.

아키텍처 · 카탈로그단일 출처 · 리빙

1. 큰 그림 (비유로)

TOS(Terminal Operating System)는 터미널의 "본부 장부". Oracle DB에 배·컨테이너·크레인·트럭의 모든 공식 기록이 있습니다. 그 장부를 실시간으로 직접 들여다보면 본부에 부담을 주므로, 추출기(extractor)라는 일꾼이 필요한 부분만 주기적으로 사본(Postgres)에 복사합니다.

TOS Oracle본부 장부
→
추출기주기적·읽기전용·최소부하
→
우리 Postgres사본 스냅샷
→
대시보드 · 배차 매처

대시보드와 배차 매처는 우리 사본(Postgres)만 봅니다. 본부(Oracle)에 닿는 건 오직 추출기뿐이고, 그것도 가볍게·주기적으로·읽기만.

2. 본부 접속·보호 규칙

  • 단일 통로 — Oracle 접근은 remote-toolbox-sql 한 경로로만(runner.rs).
  • 직렬화 — 프로세스 전역 잠금으로 동시에 두 쿼리가 본부를 때리지 않음. 항상 한 쿼리씩.
  • 읽기 전용 · 시간창 제한 — 대부분 최근 1~2일치만·완료 건 제외(풀스캔 회피).
  • 타임아웃 90초 · 병렬 억제 — 무거운 지표 쿼리엔 NO_PARALLEL 힌트.
한마디로

가볍게 · 한 번에 하나씩 · 최근 것만 · 읽기만.

라이브 배차 데이터 (약 90초마다)

① workqueue — QC 작업큐 계획·진척률

JOB_QUEUE_SCHEDULE → live_workqueue · 🟢 가벼움 · PK(qc,vessel,queuename)

QC별 작업큐 계획(어느 QC가 어느 선박/큐를 언제·진척률 완료/총). 삭제 안 됐고 QC 지정됐고 ~1일 내 수정됐고 미완료(또는 6시간 내 완료)인 큐만. 매 tick 전체 삭제 후 upsert. UI 각 QC 진척률 표시 + 배차 매처가 (vessel+queuename) 조인으로 QC 붙임(Oracle 팬아웃 회피).

알아둘 점

ACTIVEYN은 NULL 많아 신뢰 불가 → 진척률(TOTALQTY>COMPQTY)+수정시간으로 활성 판단. queuename은 재사용됨(현재 스냅샷만 유지). voyage·disload는 NULL 가능.

② workpool — 배차 입력 + UI 작업 카드

JOB_ORDER_LIST → live_workpool·live_candidate · 🟢 가벼움

완료 안 된(COMPDATE null) DS·LD 작업(A/Q 상태)을 최근 2일(CRE_DT≥TRUNC−2)에서 한 번에 뽑음. Rust에서 상태 분리: A(배정)→즉시 live_workpool(etw/actv/upd 파싱), Q(미배정, ytno NULL)→집계((queuename,vessel,jobtype,src_block) 키)→live_candidate. 사후 live_workqueue와 조인해 qc 첨부. 배차 매처의 미배정 수요·배정 move의 ETW/위치 소스, UI 작업카드, 배정 시각(upd_ts) 경유 TOS-vs-자사 비교.

알아둘 점

msnseq null이면 배차 후 미적재. yt_topos는 LD에서만 소스블록(block_prefix). etw_dt 파싱 실패는 null로 침묵. 쌍 이동(twin)=같은 contno·다른 row. Q상태 ytno=null만 candidate 집계.

③ assigned_tt — TT 배정 풀(가동률 분모)

JOB_ORDER_LIST → live_assigned_tt · 🟢 가벼움 · 매 tick 전체 리셋

미완료 작업 중 배정 트럭(YTNO NOT NULL)+상태(A/B/Q)만, DISTINCT로 트럭당 1행. 모든 작업 종류 포함(선박 DS/LD + 야드 MI/MO/LC) — 그래서 가동률 분모에 정확. 분자(A=진행)·분모(A+B+Q=배차)로 K_UTIL_TT 계산. livemap.rs가 ~30초마다 live_workpool과 조인해 배정 메타 캐시 갱신.

알아둘 점

스냅샷(이력 없음). 예정(P)·미배차 용역트럭·유휴 트럭은 여기 없음(TOS 가시성 한계). 미배정 컨테이너 수요는 다른 테이블(workpool Q행).

④ vessel_schedule — 선박 항차 일정 마스터

VSB_VOYAGE → live_vessel_schedule · 🟢 가벼움 · PK(vessel,voyage)

취소 안 된(CANCEL='N') + 출항예정 −2~+10일 항차. 입항(ESTBER)·작업완료(ESTWKC=배차 primary deadline)·출항(ESTDEP)·컷오프·실입항(ACTBER)·실출항(ACTDEP)·계획 양하/적하 수량. DATE||TIME(MYT)→UTC 변환. 배차가 데드라인(ESTWKC/ESTDEP)·계획 물량을 제1 제약으로 사용, 대시보드 'Vessel Schedule' 카드.

알아둘 점

DATE/TIME 컬럼이 VARCHAR라 문자열 범위 비교만. ACTBER/ACTDEP는 실제 전까진 null(미래 예정과 혼동 금지). 선박 마스터이지 작업 카드 아님.

거의 실시간 (작업 완료·RTG 이동)

⑤ handover — 완료 이벤트 권위 라벨

JOB_ORDER_HISTORY(JOBSTATUS='C') → tos_handover_label · 🟢 가벼움 · PK(contno,point,seqno)

마지막 워터마크 이후 새로 완료된 DS/LD 핸드오버를 증분 폴링. 인덱스 레인지 스캔(IDX_JOBHIST_DATETIME)+FETCH FIRST 3000. YTNO·ARMGC(야드측 RTG/ES)·완료시각(comp_ts)·활성(actv_ts)·하차(dis_ts). etl_watermark로 증분 추적, >=+ON CONFLICT로 경계 중복 배제. 차량이 "정확히 언제 비었나"의 권위 라벨 — DS는 GPS/PLC 신호가 약해 TOS 정답 필수. 라이브 곧-유휴 예측의 사후 평가함수.

알아둘 점 — ACTV_DT 의미

ACTV_DT는 "RTG가 물리적으로 집은 순간"이 아니라 "QC 양하 완료(트럭 적재) 시점" — RTG 들어올림은 ACTV 이후 약 11분. DS는 블록도착(DIS)→활성화(ACTV) 중앙 7.7분 변동. 보존 한계: JOB_ORDER_HISTORY ~15일 → 깊은 백필 불가.

⑥ rtg_moves — 야드 크레인 전체 작업 스트림

MCH_OPERATION(RTG|ES) → rtg_move_log · 🟢 가벼움 · PK(machno,contno,seqno)

오늘 완료된 RTG/ES 작업을 워터마크 이후 증분 수집(IDX_MCH_OPERATION_COMPDATE·최대 5000행/폴). 전체 작업(DS/LD/RH/AH/GI/GO/MI/MO). dur_s=comp−st(0~3600초만). 핵심: DS 트럭 대기의 ~80%는 RTG가 다른 작업(재배치·게이트·정리) 중이라 — 이 데이터로 RTG 백로그를 계산해 대기 예측 피처로 사용.

알아둘 점

trk_id는 보유작업(AH/RH)에서 NULL. contno는 첫 11자만. 증분(워터마크)이라 과거 재추출 불가(리셋 필요).

⑦ voyage_plan — 항차별 계획 물량

VSS_STATISTICS → raw_voyage_plan · 🟢 가벼움 · T1 3분

지난 3일 vessel/voyage별 계획 컨테이너 최댓값(MAX VAN, NOT NULL만)·상위 120행. 진행 중 항차는 VSS_STT_MOVES가 NULL이므로 VAN이 분모의 유일한 신뢰 출처. 대시보드 LIVE 탭 vessel_shift 진행률 프로그레스바(실적/계획)의 분모. 배차 미사용(vessel panel 전용).

운영 지표 — 빠른 묶음 (T1, 약 3분마다)

⑧ k_mph_realtime — QC 처리량(move/hr)

MCH_OPERATION(C##, LD/DS) → raw_k_mph_realtime · 🟢 가벼움

단일 DAY의 QC별 GROUP BY: 총 move·load/discharge 분해·active_hours(COMPTIME 첫 2자 DISTINCT 시간 수)·K_MPH=move/active_hours·차량/컨테이너 다양성. TOP 30. 각 QC의 유휴 갭 제외된 진짜 처리 효율. 대시보드 "K_MPH" 카드가 active_hours 가중 평균으로 표시.

알아둘 점

active_hours는 시간(HH) 단위라 '08:01~08:59'도 1시간(보수적). shift 실시간은 k_mph_shift 별도 테이블(시계열).

⑨ k_crane_q_daily — 야드 핸드오버 대기 (일일)

JOB_ORDER_HISTORY → raw_k_crane_q_daily · 🟢 가벼움 · PK(work_date,jobtype)

crane_q_sec=(ACTV_DT−YT_DIS_DT)*86400, 0~1800초만(in_range=가중치). work_date×jobtype당 개수·평균·중앙·표준편차·이상치. K_RTG_Q("TT가 야드 핸드오버를 기다림"). 대시보드 숨김.

알아둘 점 — YT_DIS_DT는 DISpatch(배차)

YT_DIS_DT는 하차가 아니라 배차(dispatch) 시각이어서 (ACTV_DT−YT_DIS_DT)는 순수 대기가 아니라 배차→야드활성 전 구간을 재 과대 가능(K_RTG_Q 숨김의 한 이유). SQL엔 ARMGC 필터 없음(모든 크레인 수집). DB/쿼리의 'K_CRANE_Q' 이름은 기술부채 회피로 유지(실명 K_RTG_Q). → TOS DB 레퍼런스.

⑩ k_crane_q_hour — 야드 대기(시간별 분포)

JOB_ORDER_HISTORY → raw_k_crane_q_hour · 🟡 보통 · T2/야간

⑨와 같은 계산을 시간대(0~23)로 분해 — "어느 시간에 RTG 대기가 길었나". alert_threshold(μ+2σ). K_RTG_Q 자체가 숨김이라 전시 안 되나 24시간 패턴·야간 편향 검증 등 백엔드 분석용.

⑪ k_tt_cycle — 당일 트럭 사이클(TOS 근사)

MCH_OPERATION(C##, LD/DS) → raw_k_tt_cycle · 🟢 가벼움 · PK(snapshot_date)

같은 트럭의 연속 QC-move 간격(120~1200초만) 중앙값 = 한 사이클(픽업→운송→드롭→복귀). DS/LD 분리(K_CYCLE_DS/LD). 대시보드 K_CYCLE 핵심 지표(Σ(med_sec·samples)/Σsamples).

알아둘 점 — GPS 사이클과 다름

TOS K_CYCLE은 배차 대기·재계획 등 행정 시간 포함, GPS는 물리 주행만. 교차검증: TOS ≈ GPS의 233~303%(TOS 중앙 ~60분 ↔ GPS 중앙 ~20분). 자세히 → KPI 정확도. (2026-07-15부터 tt_move_log로 배차→완료 두 앵커 재산출.)

⑫ k_empty — 공차거리/공차비율

JOB_ORDER_HISTORY → raw_k_empty · 🟡 보통 · PK(date,jobtype,shift)

작업 1건=(CONTNO,POINT,SEQNO)로 접고 첫 이벤트 시각으로 교대 판정 → (jobtype×shift) 집계. 적재(LNDN)·공차(UN_LNDN) 거리 0~5000m만(이상치 제외). K_EMPTY_R(공차비율)=Σ공차/Σ(공차+적재). 배차 성과 평가·최적화 근거.

⑬ k_qc_q — QC 유휴 갭 분석

MCH_OPERATION(C##, LD/DS) → raw_k_qc_q · 🟡 보통 · PK(date,qc)

QC별 연속 작업군 사이 갭(idle_sec)을 시간대별로 분류. HAVING≥(day=10,shift=2). K_QC_NOMOVE(모든 갭). 2026-06-18 same_bay 컬럼 추가: 같은 베이 갭만=진짜 트럭대기(K_QC_TT_WAIT), 베이 변경 갭=QC 이동.

알아둘 점 — 전체 gap ≠ 트럭대기

초기(2026-06-17 이전)엔 모든 갭을 트럭대기로 계산해 ~1.8배 과대평가(실제 ~45%가 QC 이동/해치). same_bay(QUEUENAME 변화 없음)로 진짜 starvation 분리. 과거 데이터는 same_bay=NULL이라 필터 불가.

⑭ k_util_crane — 크레인(QC/YC) 가동률

MCH_OPERATION(C##/RTG%) → raw_k_util_crane · 🟡 보통 · PK(date,machno)

크레인별 겹침 구간 병합 → active_sec_merged(유휴 제외) → k_util_merged_24h(=active/86400). TOP 60. 대시보드 K_UTIL_CRANE·배차 리소스 제약(작업가능 크레인 식별).

⑮ k_util_tt — 야드 트랙터 가동률

CDY_MACHINE+MCH_WORKTIME+MCH_WORKSTOP → raw_k_util_tt · 🟢 가벼움 · PK(date,machno)

YT별 근무 세션(login/logout) 겹침 병합 → active_min − stop_min = productive_min → k_util_capped=min(1, productive/경과분). logout_anomaly(겹침=미로그아웃). 야간 배포 누적 이력.

알아둘 점 — 세션 기반(실시간 아님)

MCH_WORKTIME은 로그아웃 후에야 행 확정 → 현재 활동 중 TT는 미포함. 실시간 util은 websocket GPS + 작업풀로 계산(KPI 정확도). 이 세션값(근무 기준)과 화면값(할당 기준 ≈63%)은 다름.

운영 지표 — 무거운 묶음 (T2, 약 15분마다)

⑯ k_mph_voyage — 항차별 확정 성과

VSS_STATISTICS → raw_k_mph_voyage · 🟢 가벼움 · PK(vessel,voyage)

최근 30일 확정 항차의 컨테이너/TEU/move(싱글/트윈/탠덤)·소요시간(gross/net/berth)·생산성(GQCR/NQCR=k_mph, GBP/NBP=k_bp). TOP 30. TOS 확정값이라 변경·replay 불가. 선박 역량 평가·선사 계약 성과 검증.

⑰ k_cycle — 작업 사이클(핸들링 span)

JOB_ORDER_HISTORY → raw_k_cycle · 🟡 보통 · PK(date,jobtype)

작업(jobtype×contno×point×seqno)의 첫~마지막 이벤트 간격(transitions>1만) jobtype별 평균·중앙·사분위·이상치(avg+2σ). TOP 15. 주의: 이는 컨테이너 핸들링 span(≈40분)이지 트럭 사이클이 아님 — 표시 K_CYCLE는 ⑪(k_tt_cycle)를 씀.

최근 3일 연속 QC move 간격(1~300초, 순수 처리 cadence)의 크레인·작업종류별 중앙값(표본≥30). 배차 엔진의 ETA/데드라인 계산 입력. med_sec 없으면 상수 fallback(양하 ~90초, 적하 ~110초). 크레인별 편차 큼(양하 79~128초) — 개별 학습 모델의 이유.

알아둘 점

Rolling(날짜 키 없음) — 매일 밤 DELETE+INSERT로 최신 3일만. Quay crane만(C/M/Z), RTG/ES 제외.
