websocket 원본 필드 레퍼런스

GPS/PLC 피드가 실제로 보내는 모든 필드를 원본 프레임을 떠서 구현자 관점으로 정리한 "필드 사전". 상위 개요는 실시간 websocket 데이터.

레퍼런스리빙 문서

1 · 봉투 & 두 개의 존

{"data":{"id":"TT1045","zone":"wpt_gps","datas":"<문자열로 인코딩된 JSON>"}}
  • data.id — 장비 ID. data.zone — 피드 종류. data.datas는 문자열이라 한 번 더 JSON 파싱.
  • wpt_gps 존 → gps_update(차량 GPS, ~3초). ctab 존 → plc_data(크레인 PLC, ~1초).

2 · 전체 26개 키 — 실제 프레임

한 프레임에 항상 26개 키가 모두 포함됩니다. 해당 장비/상황에 없는 값은 빈 문자열(또는 0).

// 활성 LD 트럭 (도착 상태)
{ "device":"TT1253", "lat":"2.93590967", "lon":"101.29527217", "speed":"1kmh",
  "engine_on":"ON", "cur_loc":"WHARF_12", "lapse":20, "arrival":"ARRIVED",
  "arr_dtime":"20:48:19", "container1":"CMAU8919605", "topos1":"C14",
  "container2":"", "topos2":"", "vslname":"CNC URANUS", "jobtype":"LD" }
관찰

약 1,660 프레임을 28초간 떠보니 26개 키가 매 프레임 존재. 미션 필드는 대부분 빈값이고 소수에만 값(예 topos2 8.3%). 이게 "할당 이벤트성"의 직접 증거.

3 · 정체성·위치·모션 — 항상 실림

필드의미 · 관찰
device장비 ID(불변). 앞 알파벳이 종류 — TT/RTG/C·M·Z.
lat / lon위치. 문자열로 옴. 0,0이면 무픽스 → 버림.
speed속도, 끝의 kmh 떼고 파싱. <3km/h = 정지.
accuracyGPS 정확도(m). 스파이크 시 위치 점프 → 거리 누적에 600m 점프가드.
distance⚠️ 항상 0.0 — 무용. 우리가 GPS로 직접 경로거리를 누적.
userid운전자 ID+전화. HTML <br/>이 박혀 옴 → 정제 필요.

4 · 미션/작업 필드 (할당 이벤트성) ⚠️ 핵심이자 함정

이 필드들은 3초 하트비트에 안 실립니다. 작업 할당 이벤트 때만 한 번 실리고, 다음 픽스부턴 빈값. 그래서 빠진 값을 latch(직전 비-빈값 유지)해야 합니다.

필드의미 · 관찰
topos1목적지(다음 핸드오버) — 블록 베이 또는 크레인. = 작업 할당 시점 신호. DS: 크레인(픽업)→블록(드롭), LD: 블록→크레인. 할당 직후엔 아직 100m+ 떨어져 있기도.
container11번 박스. ⚠️ 물리 적재가 아니라 TOS 배정 필드 — 직전 drop 시점에 다음 박스가 미리 배정(c2c). 비-빈→다른값 + 이동≥150m = 진짜 인도.
container2 / topos22번 슬롯 — 트윈/탠덤일 때 채워짐. c1↔c2 슬롯 스왑이 잦음(집합 동일하면 무시).
jobtypeLD/DS/MI·MO·LC. 픽업·드롭 방향 결정. latch.
cur_loc현재 위치 라벨. topos1과 같아지면 도착. (비교적 자주 실림.)
함의 — 단계 감지의 방향

topos1이 "비었다가 잡히는 전이" = 할당 이벤트이므로, 사이클 단계 경계를 약한 arrival이 아니라 topos1 전이 + GPS 근접 + PLC로 잡는 게 더 정확. 상세 사이클 감지 로직.

5 · topos2 심층 조사

  • 키는 매 프레임 존재하지만 값이 차는 건 1,660 프레임 중 138개 = 8.3%. topos1처럼 할당 이벤트성.
  • 값의 형태: 크레인 코드(C34·M7)와 블록 베이(08Q-21) 둘 다.
jobtypetopos1topos2해석
LD02W-4108Q-21서로 다른 두 블록에서 수령 (트윈 컬렉션)
LDC34C34둘 다 같은 크레인 — 두 박스 같은 QC로
MO04L-1504L-03야드이동, 인접한 두 베이
결론

topos2 = 두 컨테이너를 다루는 작업(트윈/탠덤)의 두 번째 핸드오버 지점. 단일 컨테이너 작업에선 빈값. 현재 우리는 topos1만 파싱하지만, 트윈 두 번째 leg를 정확히 잡으려면 topos2를 함께 보면 됩니다.

6 · 도착·체류 — arrival · arr_dtime · lapse

필드의미 · 관찰
arrival목적지 도달 시 "ARRIVED". ⚠️ 블록에선 신뢰성(정차 트럭 ~78%), 크레인에선 약함(~23%) — 크레인 레인이 길고 지오펜스가 느슨.
arr_dtime도착된 시각.
lapse도착 후 경과 분 = 체류 타이머. 핸드오버 대기시간을 서버가 직접 계산해 보내줌 — QC 대기/체류 분석에 바로 쓸 수 있음.

7 · 보조·미해독 필드 (현재 미사용)

필드해석
addr현재 위치 주소 라벨. cur_loc과 동일하게 옴.
mds / ins활성 트럭에서 항상 "Y" / 항상 빈값. 의미 미상 — 추정으로 단정하지 않고 "미해독".

8 · ctab — 크레인 PLC (plc_data, ~1초)

필드의미 · 관찰
crane크레인 ID — GPS device·TOS QC번호와 일치 → 위치/계획 연결고리.
load훅 하중. 빈후크 ~0, 적재 ≥1t. empty→laden 상승엣지 = PICKUP(무브 1건). 라이브 move/hr·QC대기에 사용.
lock / land / hpos / tpos트위스트락 / 안착 / 호이스트 / 트롤리.

9 · 피드 거동 규칙 & 구현 함의

  1. 두 속도: GPS ~3초/장비, PLC ~1초/크레인. 과거 없음 — 사이클은 우리가 직접 누적·영속화.
  2. 미션 필드는 할당 이벤트성: 할당 때만 실리고 평소엔 빔. ⚠️ GPS 스냅샷으로 "배정 수"를 세면 안 됨(한때 160→18 폭락 사고) → 배정은 작업풀(TOS)로 센다.
  3. 수신부가 매 메시지 상태를 새로 만듦 → 빠진 필드는 None. latch가 필수.
  4. 잡 신호: 위치/모션(항상), arrival+arr_dtime+lapse, PLC load. 미션 필드는 전이(이벤트)로 해석.
  5. age 밴드: ≤15s fresh · ≤120s active · >600s 제거.

이 레퍼런스는 사이클 감지 로직의 토대입니다 — 어떤 필드가 신뢰할 만하고(위치·PLC·블록 ARRIVED) 어떤 게 함정인지(container1=배정, 크레인 ARRIVED 약함)를 알아야 단계 경계를 옳게 설계할 수 있습니다.
