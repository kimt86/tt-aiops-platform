차량 풀 · 작업 풀이 어떻게 갱신되는가

TT 배차의 두 축 — 차량 풀(어떤 트럭이 비었는가 · 공급)과 작업 풀(어떤 크레인 작업이 트럭을 기다리는가 · 수요). 둘은 갱신 방식이 완전히 다릅니다.

아키텍처리빙 문서

두 풀 — 갱신 방식이 다르다

차량 풀 (공급)작업 풀 (수요)
출처websocket GPS/PLC (TOS 아님)TOS 라이브 작업지시 2테이블
갱신API 메모리 스냅샷 → 화면 ~2.5초 폴링추출기 90초 → Postgres → 화면 ~15초 폴링
방식standalone — 각 TT를 실시간 상태 분류QC별 작업 시퀀스 + 배정 트럭 + ETW
왜 다른가

차량 상태는 직접 관측됩니다(트럭이 GPS로 자기 상태를 송신). 작업 계획은 TOS의 미래 의도라 websocket에 없어 DB에서 주기적으로 가져옵니다. 화면(Part 4)은 둘을 융합합니다.

Part 1 · 차량 풀 갱신 — 실시간 (websocket)

API가 websocket 두 zone을 받아 장비별 최신 위치 스냅샷을 메모리에 유지하고 /api/livemap/positions로 노출. 화면은 ~2.5초 폴링. (데이터 자체는 websocket 문서.)

신선도 — 메모리 스냅샷의 age-out

  • fresh ≤ 15초 · active(표시) ≤ 120초 · lost(제거) 600초 초과 → 장비가 떠나면 자동 소멸.
  • DB에 안 쌓음 — 현재 순간만. 터널이 끊기면 즉시 빔(피드 헬스가 감시).

배차 상태 분류 (TT)

상태뜻 · 화면
idle 현재 유휴공차 + 정지 + 미배정 → 즉시 배차 가능. 배차 풀 1열.
staging 배차·대기공차 + 정지 + 배정됨 → 순서 대기(노는 게 아님).
soon_idle 곧 유휴적재 + 마지막 핸드오버 진행 중 → 곧 풀림.
empty_travel 공차 주행공차로 픽업 향함. 목적지 멀면(≥150m) 스왑 후보.
delivering 적재 이동적재하고 이동 중(아직 도착 전).
wait_rtg 도착·RTG 대기블록 도착했으나 RTG 미관여 → 아직 대기.
idle → idle/staging 분리 (총 6상태)

이 문서 초판(2026-06-09)은 5상태였으나, "공차+정지"의 절반이 실은 배정된 차(순서 대기)여서 배정된 대기 = staging, 진짜 미배정 = idle로 분리해 6상태가 됐습니다. 상세 TT Dispatch 해설.

Part 2 · 배차 상태 분류 상세

각 TT를 매 스냅샷마다 결정 트리로 분류. websocket 신호만 사용. 상수: 유휴속도 3km/h · RTG 같은bay 30m · 스왑 최소거리 150m.

적재 여부 = container1 이 비었나?
공차(빈 차)
  ├ 속도 < 3km/h · 미배정 ────────▶ idle          (즉시 배차 가능)
  ├ 속도 < 3km/h · 배정됨 ────────▶ staging       (순서 대기)
  └ 이동 중 ─────────────────────▶ empty_travel  (목적지 거리로 스왑성 판정)
적재
  ├ arrival ≠ ARRIVED ──────────▶ delivering    (아직 운반 중)
  └ ARRIVED + 드롭 사이드 도착
      ├ 안벽(LD): QC PLC 신선 ──▶ soon_idle     (크레인 관여 확인)
      └ 블록(DS/MO/MI):
          ├ RTG GPS ≤ 30m ─────▶ soon_idle     (같은 bay = 핸드오버 중)
          └ RTG 멀음 ──────────▶ wait_rtg      (도착 ≠ 곧유휴)
양하(DS)가 어려운 이유 — RTG엔 PLC가 없다

적하는 QC PLC 하중 전이로 핸드오버를 ±1초로 잡습니다. 하지만 양하 블록측 RTG는 PLC가 없어 RTG GPS와 TT GPS가 같은 bay(≈30m)인지로 판정. 블록에 도착만 했다고 곧유휴로 보면 오판(wait_rtg).

블록 위치 학습 (centroid)

크레인이 항상 GPS를 쏘지 않으므로 ARRIVED TT들의 GPS로 블록/베이 위치를 학습(코드별 이동평균). 공차 TT가 픽업 목적지까지 몇 m 남았는지를 TOS 의존 없이 추정 → 스왑성 판정.

Part 3 · 작업 풀 갱신 — TOS 90초 스냅샷

TOS 라이브 작업지시를 90초마다 끌어옵니다. (컬럼 상세는 TOS 레퍼런스)

  • JOB_ORDER_LIST — 개별 컨테이너 move — 배정 트럭·ETW·컨테이너·RTG. JOBSTATUS A만(완료행도 보관되므로 라이브 필터 필수).
  • JOB_QUEUE_SCHEDULE — QC별 작업 큐 계획 — 크레인·순서·진행률. 잔여 = TOTAL−COMP.
조인은 Postgres에서 (Oracle 아님)

큐 이름이 항차마다 재사용돼 Oracle에서 조인하면 fan-out. 활성 move만 뽑고 QC는 깨끗한 현재 큐 스냅샷으로 Postgres에서 붙임. ETW는 MYT→UTC 파싱.

Part 4 · 두 풀의 융합 — QC 작업 시퀀스

"QC 작업 시퀀스 & 배차(라이브)" 패널은 작업 풀(TOS 계획)을 차량 풀/websocket(실측)과 합칩니다. QC당 한 컬럼, 세 신호의 융합:

신호출처화면 표현
TOS 계획작업 풀 (90초)무엇을·어느 순서로·어느 트럭에·언제(ETW)
PLC 실측websocket ctab그 크레인이 지금 돌면 헤더에 PLC live
트럭 GPS차량 풀배정 트럭 옆에 실시간 상태 점(유휴/곧유휴/…)

연결 고리: TOS의 YTNO ↔ GPS device, TOS의 QC(C##) ↔ PLC crane. "이 작업에 배정된 트럭이 지금 실제로 어디서 뭘 하는지"가 한 줄에 보입니다.

Part 5 · 한계 · 노트

  • 활성 작업은 전부 배정됨: TOS의 A는 "트럭이 이미 배차된 진행 작업". "미배차 수요"는 대기(Q) 백로그이고 깊이는 잔여 = TOTAL−COMP로 표시.
  • 대기(Q)는 개별 카드 없음: ETW·순서·배정이 없는 묶음 → 큐 단위 잔여 수치로만.
  • 차량 풀 standalone: 차량 분류는 websocket만으로. 곧유휴 LD는 ~1분 전 사전 판정, DS는 RTG 근접 확인 후.
