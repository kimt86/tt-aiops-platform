실시간 websocket 데이터 & 활용

장비 ~450대가 매초 쏟아내는 GPS 위치와 크레인 PLC 스트림. TOS DB(Oracle)와는 완전히 다른 시스템 — "지금 어디서 무엇을 하는가"의 연속 관측.

핵심

KPI 수치는 전부 TOS에서 나옵니다(websocket 아님). 반대로 실시간 차량/작업 상태는 websocket이 핵심. 작업 풀 화면은 둘을 융합합니다.

두 zone · 메시지 봉투

// 봉투(공통)
{ "data":{ "id":"TT1045", "zone":"wpt_gps", "datas":"<stringified json>" } }
  • wpt_gps (위치 + 미션): 모든 차량/크레인 GPS + (TT) 현재 미션.
  • ctab (크레인 PLC): 동적 크레인(C/M/Z)의 PLC — 하중·트롤리·호이스트. 핸드오버 순간의 정밀 신호.

필드의미 · 활용
device, lat, lon, speed장비ID · 위치 · 속도. 속도<3km/h + 공차 = 유휴 판정.
container1, container2적재 컨테이너(2개=트윈). 비어있음 = 공차/유휴의 1차 신호.
topos1목적지 코드(다음 핸드오버) — 블록 베이 또는 크레인. 픽업↔드롭에 따라 동적.
arrival도착 플래그. 핸드오버 임박/곧유휴 판정의 핵심.
jobtype, vslname작업종류(LD/DS/MO·MI) · 선박명. 드롭 사이드 결정.

ctab — plc_data (크레인 PLC)

하중(load) 전이가 곧 핸드오버 순간이라 동기화의 가장 정밀한 신호. C/M/Z만 송신 — RTG는 PLC가 없습니다.

{ "crane":"C51", "load":1.9, "lock":"False", "land":"False", "hpos":"31.74", "tpos":"27.68" }
필드의미 · 활용
crane크레인 ID. GPS device·TOS QC번호와 일치 → 위치/계획 머지 연결고리.
load하중(톤). 적재 ≥ 1.0t, 빈후크 ~0. 전이로 PICKUP/DROP 검출. "작업 중" 신호.
lock / land / hpos / tpos트위스트락 / 안착 / 호이스트 / 트롤리 위치.
RTG는 PLC가 없다

양하(DS)의 블록측 핸드오버는 PLC가 없어 직접 못 봅니다 → RTG GPS와 TT GPS의 근접도로 추정(같은 bay ≈ 30m 이내).

네트워크 — Azure 경유 터널

원천 ws://172.21.30.72:9986은 WSL2 NAT IP라 직접 불가. Tailscale 노드 azure-wp-poc가 사내망에 닿아 SSH 터널로 API가 수신(systemd tt-ws-bridge). 끊기면 라이브맵·차량 풀이 즉시 비고 피드 헬스가 적색.

차량 풀 — 배차 상태 분류

각 TT를 매 스냅샷마다 배차 상태로 실시간 분류. standalone — websocket 신호만. (상세 차량·작업 풀 갱신.) 초기 5상태(idle·empty_travel·delivering·soon_idle·wait_rtg)에서 나중에 idle을 idle/staging으로 분리해 6상태가 됐습니다.

왜 PLC/GPS 융합인가

적하(LD)는 QC PLC 하중 전이로 핸드오버를 ±1초로 잡지만, 양하(DS)는 RTG에 PLC가 없어 RTG GPS와 TT GPS가 같은 bay(≈30m)인지로 판정. 블록 위치는 ARRIVED TT들의 GPS로 학습(centroid).

작업 풀 융합 · 피드 헬스

  • 크레인 가동 배지 — QC PLC 신선하면 그 크레인이 지금 물리적으로 도는 중 → PLC live.
  • 배정 트럭 실시간 상태 — 각 작업의 배정 TT(TOS YTNO) 옆에 실시간 상태 점 — YTNO ↔ GPS device 매칭.
  • 피드 헬스 — WS 미연결/60초+ 무수신 → 적색. 장비별 age(15s fresh/120s stale/600s 제거)·분당 메시지·정확도 감시.

"TOS 5,575대 vs 웹소켓 539대"로 놀랄 수 있으나 — 5,033대는 외부 게이트 트럭(우리 야드트랙터 아님). 우리 차량 커버리지는 거의 완전.

6.2 ★ 근본 한계 — "정지하면 GPS 단말이 침묵한다"

유일한 한계이자 가장 중요한 발견

전체 갱신 간격의 4%가 5분 넘는 큰 끊김(median 11분). 이 끊김의 68%가 트럭이 짐을 싣고 작업하는 중에 발생. 결정타: 큰 끊김의 100%가 트럭이 멈춘 직후 시작(끊김 직전 이동량 median 0m). 즉 차량 GPS 단말이 "움직이면 보고, 멈추면 침묵"하는 이동 기반 보고 방식 — 우리 피드나 구조물 문제가 아니라 소스 단말의 성질.

6.3 이것이 설명하는 것

트럭은 멈추면 보이지 않는다 — 그런데 우리가 가장 관측하고 싶은 건 멈춰서 크레인을 기다리는 그 순간. 이 하나의 성질이:

  • 곧-유휴 시각(리드타임) 예측이 근본적으로 불가한 이유 — ADR 0002.
  • 부하 도착 시점이 흐릿했던 이유 (도착 = 정지 = 침묵).
  • DS 물림 탐지 재현율이 낮은 이유 (핸드오버 = 정지 = 침묵).

6.4 고칠 수 있나

  • 우리 쪽에선 불가 — 단말의 보고 정책(상류). 피드는 충실히 전달할 뿐.
  • 진짜 해결 = 터미널 측 텔레매틱스 재설정(정지 중에도 보고) — 하드웨어/정책 협의.
  • 우리 완화책(latched 필드 · 지오펜스 도착 · 맵매칭)이 정확히 이 "정지 중 침묵"을 메우려던 장치.
