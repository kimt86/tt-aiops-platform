러닝 센터 — AI가 무엇을, 어떻게, 어떤 데이터로 배우나

러닝 센터는 AI가 현장 데이터로 스스로 배운 것과 그 배움의 재료(데이터)를 보여주는 페이지입니다. 두 탭으로 나뉩니다.

🗄️ 데이터 수집실시간으로 모으는 데이터 16종. 카드마다 설명·출처·쓰임·수집량 + 최근 수집 내역
먼저 큰 그림 — 4가지

1. 학습 = 같은 일을 많이 보면 보통값(중앙값)을 알게 됨. 2. 예측 = 한 숫자가 아니라 범위(분포). 3. 정답 = 실제로 일어난 일 — 트럭 GPS가 1순위. 4. 테스트 = 예측 vs 정답 비교(MAPE·±30%·재현율).

왜 GPS가 1순위가 됐나 — 실화

처음엔 TOS "작업 완료" 시각을 정답으로 썼는데, 적하(LD)에서 트럭이 비고 ~8분 뒤에 찍히는 행정 기록이었습니다(완료=컨테이너가 배에 실린 시각). 트럭 GPS로 교차검증하니 진짜 빈 시각과 0.5분 차이로 일치 → GPS를 1순위 정답으로. (양하 DS는 TOS 완료가 GPS와 거의 같아 그대로.)

카드 ① — TT 이동시간 (한 trip이 몇 초 걸리나)

입력출발지→도착지 좌표 → 추론 도로망 위 최단시간 경로(찻길 속도·일방 반영)
출력그 구간 공차 이동시간(초)의 분포(기대 p50·보수 p90) = 경로시간을 실측 "실제시간 곡선"으로 변환
담당순수주행 = 주행 구간 시간(출발→작업지점) = 2단계 배차 비용. 경로 정체 포함, 도착 후 크레인 대기만 제외
학습완료된 GPS 사이클에서 빈 trip을 수확 → 도로망 라우팅해 실제 vs 경로시간 기록(road_route_eval) → "이 경로시간이면 실제 보통 N초" 곡선(구간별 p50/p90·단조·바닥)을 매 틱 적합
결과상시 게이트: 상관 0.358 vs 맨해튼 0.385(대등)·경로 성공률 96.7%
왜 더 못 맞히나 — 분포로 써야 함

같은 출발→도착이라도 실제 시간은 ±50% 흩어집니다(56초~37분). 그 순간 교통·크레인 줄 때문이라 결정 시점엔 알 수 없는 미래. 그래서 점 하나가 아니라 분포로 씁니다.

딥러닝을 쓰면 더 나을까? — GBM 그림자 (2026-07-13)

데이터로 답했습니다: 이동시간에 GBM(그래디언트 부스팅) 그림자를 붙여보니 통계 중앙값 대비 MAPE 57→49%(+8pp), 신경망도 동률(딥러닝 추가 이득 0). 개선의 지렛대는 모델 종류가 아니라 도로망 자체(찻길 속도·혼잡)입니다. GBM은 무누수 그림자로 병행 중이며 배차는 아직 비모수 백분위수 추정을 씁니다.

카드 ② — 작업지점 좌표 (블록·크레인이 정확히 어디?)

입력트럭이 작업점에 도착(ARRIVED)한 순간의 GPS
출력각 블록·크레인의 중심 좌표 + 신뢰도
담당존 정의·거리/비용 계산의 위치 앵커 (이동 크레인은 ID가 없어 GPS로 위치를 푼다)
학습/결과도착 GPS를 계속 모아 평균(중심점). 잔차(위치 오차 ±m)가 작을수록 정확 → 신뢰도 색(🟢🟠🔴)

카드 ③ — 주행 차선·방향

입력움직이는 트럭의 GPS 자취(격자 → 스켈레톤 → 노드·엣지)
출력방향성 도로 그래프(노드·엣지 + 작업지점 커넥터)·통행 방향·평균 속도
담당★배차 비용의 본체 — 트럭→작업지점 최단시간 길찾기(2026-07-02 연결)
학습/결과GPS 자취 스켈레톤화(매시간 cron), 작업지점 5,888곳 커넥터, 도로 단위 다수결 방향·속도. 방향성 다익스트라(roadgraph.rs). 스냅 100%·성공률 96.7%
한 번 탈락 → 재구축해서 배차 비용에 연결 (2026-07-02)

첫 도로망은 작업지점이 도로에서 중앙 52m 떨어져 30%만 계산 가능·상관도 낮아 탈락이 맞았습니다. 재구축: 조밀화 + 작업지점 전부 커넥터(스냅 100%) + 도로 단위 다수결 방향(성공률 46.6→96.7%). 격자형이라 현재 정확도는 맨해튼과 대등하지만, 도로망은 속도·혼잡 반영 여지 + 비격자 터미널 일반화로 채택. 격자 룩업 폐기(mig 0082).

카드 ④ — 곧 빔 · 유휴 시각 (트럭이 곧 비나? 몇 분 뒤에?)

2026-07-09 — ⑤ 곧-빔 게이트 + 유휴 분(free_in)을 한 카드로 통합

예전에 따로였던 "곧 빌 트럭 판별(게이트)"과 "몇 분 뒤 빌지(free_in)"를 '곧 빔·유휴 시각' 한 카드로 합쳤습니다(러닝 센터 7→6). 게이트는 자가보정(잔차 피드백) + near-miss 양방향 튜닝(놓친 것·헛발화 둘 다 로깅해 임계값 조정)으로, free_in은 사이클 단계별(delivering·approach·wait·soon)로 학습하고 잔차로 보정합니다.

입력트럭 상태 · RTG까지 거리 · 발화 신호(GPS/PLC/TOS)
출력곧 빔(예/아니오) + 몇 분 뒤에 빌지(리드)
담당배차 공급 예측 — 곧 빌 트럭을 미리 2단계 후보 풀에 넣어 둔다
학습매 30초 예측을 기록 → 실제 빈 시각(GPS 정답)과 맞춰봄
결과(예시)리드 DS ~5분 / LD ~3.2분. 정밀도 DS 92~93% / LD 72%. 재현율 DS ~46% / LD ~66%
정밀도가 LD에서 더 정직해진 이유

TOS 라벨만 쓸 땐 LD 정밀도가 40%로 낮았는데, TOS가 놓친 실제 빔을 "헛발화"로 잘못 센 탓. GPS-우선 정답으로 바꾸니 72%로 — 진짜 정밀도가 드러났습니다.

카드 ⑤ — 유휴 분: 피처로 더 맞출 수 있나 (DS·LD)

"몇 분 후 유휴"를 추가 정보(피처)로 더 정밀하게 맞춰보려는 시도(홀드아웃 공정 채점).

DS (양하)LD (적하)
입력(단서)RTG까지 거리 × 발화 신호없음(안벽이라 거리 없음)
출력거리 구간별 중앙(≤30m 4분 → >150m 6.7분)학습 중앙값(~3.2분)
테스트(MAPE)~57% (평균 58% 대비)~66%
  • DS: 거리는 중앙 예측을 밀어주지만, per-건 오차는 거의 안 줄어듦(58→57%).
  • LD: QC·시간대·큐를 다 시험했지만 전부 평균과 같음(~65%) → 쓸 만한 피처 없음.
  • 공통 원인: 크레인 줄(큐)이 언제 내 차례가 될지는 미리 알 수 없는 확률이라 천장이 있음.
그래서 결론

유휴 분 예측도 점 하나가 아니라 분포(p10~p90)로 쓰는 게 맞습니다. 더 정밀히 하려면 거리·신호가 아니라 RTG 큐 깊이/작업률 같은 동적 정보가 필요(현재 미보유). (관련 후속: QC 큐 앞순위로 자유시각을 예측하는 방향 — 곧-유휴 감지 참고.)
