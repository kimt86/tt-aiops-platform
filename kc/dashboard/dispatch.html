TT Dispatch & 라이브맵 — 실시간 값의 모든 것

TT Dispatch 페이지는 "지금 이 순간 트럭들이 어디서 무엇을 하고 있나"를 보여줍니다. 거의 전부 websocket(원천 ②, 실시간 GPS·PLC)에서 오고, 작업 풀만 TOS(원천 ①)와 섞습니다.

대시보드 가이드리빙 문서
실시간 = 메모리

이 페이지의 값은 DB에 저장되지 않은 메모리 스냅샷입니다. SSH 터널이 끊기면 화면이 즉시 비고 피드 헬스가 적색이 됩니다. "과거"가 없으니 시간을 거슬러 볼 수 없습니다.

각 트럭은 매 스냅샷마다 6개 상태 중 하나로 분류됩니다(classify_tt). 분류는 GPS 신호만으로 합니다(작업 풀 배정 여부는 idle/staging 구분에만 사용).

idle vs staging — 왜 갈랐나

예전엔 "공차+정지"면 전부 idle로 셌더니 실제로는 절반이 이미 배차된 차(순서 대기)였습니다. 작업 풀(TOS)을 교차참조해 배정된 대기 = staging, 진짜 미배정 = idle로 분리해 idle 수가 정상화됐습니다.

"크레인 관여 중"은 어떻게 아나? (soon_idle의 핵심)

작업신호정밀도
LD(적하)안벽 QC의 PLC(ctab.load)가 신선 = QC가 지금 이 베이에서 돈다±1초 (PLC 직접)
DS(양하)RTG GPS ↔ 트럭 GPS가 같은 베이(≈30m 이내)근접 추정

RTG는 PLC가 없어 직접 못 봅니다 → GPS 거리로 추정. 블록 위치는 ARRIVED한 트럭들의 GPS로 학습한 중심좌표를 써서, 크레인이 GPS를 안 쏠 때도 거리 계산이 됩니다.

3. "곧 빔 ~N분" (free_in) — 이제 배차 계산과 같은 숫자

soon_idle/도착 트럭 옆에 "곧 빔 ~N분" 추정이 붙을 수 있습니다 — 몇 분 뒤에 빈 차가 될지의 추정.

화면 값 = 배차 계산이 실제로 쓴 값 (2026-08-10)

예전엔 화면의 이 숫자가 표시 전용 상수였고, 배차 계산은 따로 학습한 값을 썼습니다 — 같은 트럭인데 화면과 계산이 다른 숫자를 볼 수 있었습니다. 지금은 배차 계산(60초마다 한 번)이 쓴 값을 그대로 화면에 실어줍니다. 값을 정하는 순서: ① 양하 트럭은 크레인이 실어준 시각부터 남은 시간을 내려 세는 작업 기록 기준이 먼저 ② 드랍 지점에 멈춰 있으면 정차 실측 중앙값 ③ 이동 중이면 단계별 학습값(mig 0084–86) ④ 계산이 잠시 멈춘 사이에만 옛 상수. 그리고 GPS가 2분 넘게 조용해도 작업 기록이 "아직 일하는 중"이라 하면 그 트럭은 후보에서 빼지 않고 유지합니다 — TT 페이지 후보 카드에 "GPS 침묵"으로 표시됩니다. 상세 러닝 센터.

4. TT Dispatch 페이지 — 우리 배차의 실황판 (2026-08-10 전면 개편)

이 페이지는 우리 배차 계산이 지금 어떻게 돌고 있는지를 보여줍니다. 네 개의 카드가 있고, 화면의 모든 숫자는 배차 계산이 실제로 쓴 값을 그대로 실어온 것입니다 (화면이 따로 계산하지 않습니다).

카드무엇을 보여주나읽는 법
① 배차 압력배(급한 순서)마다, 크레인마다 지금 얼마나 급한가큰 숫자 = 배차 마감이 지났는데 아직 트럭이 안 붙은 상자 수(0이면 초록). 신호등은 배차 계산과 같은 잣대: 🔴 지금 속도로는 못 끝냄 · 🟡 여유 30분 미만 · 🟢 충분 · ⚪ 출항 정보 없음
② QC 작업 타임라인크레인이 일할 순서대로 상자를 나열순서 = 배 안 짐 배치 계획(적부계획)의 순번 — TOS 스스로도 이 순번으로 트럭을 배차한다. 상자마다 🏁 배차 마감 카운트다운, 배정 트럭(실시간 상태 점), 🤖 우리 추천
③ 후보 차량 풀배차 계산이 이번 판에 쓸 수 있는 트럭지금 노는 트럭 + 곧 비는 트럭(비는 시각은 계산이 실제 쓴 값). GPS가 조용해도 작업 기록상 일하는 중이면 풀에 남는다
④ 작업 중 차량이미 일이 있어 계산이 건너뛰는 트럭빈 차로 이동 · 싣고 운반 · 배차 후 대기 중
"발행 n / 남은 m" — 목록이 짧아 보이는 이유

TOS는 작업지시를 작업 한 시간쯤 전에야 만듭니다. 그래서 타임라인의 상자 목록은 곧 할 것만 보이고, 나머지는 "남은 m"(TOS 진행 카운터)으로만 셉니다 — 없는 게 아니라 아직 지시가 안 나온 것입니다. 또 크레인이 이미 처리한 양하 상자(트럭이 야드로 운반 중)는 큐가 아니라 ④ 차량 카드에 있습니다.

배는 크레인을 나눠 쓴다

크레인 절반 이상이 두 척 이상을 맡습니다. 그래서 화면은 배 × 크레인 칸으로 갈라, 진행률·트럭 수·여유가 다른 배와 섞이지 않게 합니다. 다음 순서 배의 칸에는 "대기"가 붙습니다.

접안 중인 배만 보입니다 (2026-08-11)

TOS에는 아직 접안하지 않은 배(하루 이틀 뒤 도착 예정)의 작업 계획도 미리 들어 있습니다. 예전에는 그 계획까지 화면에 나와 배가 두 배로 많아 보였는데, 지금은 실제로 부두에 닿아 있는 배만 표시합니다. 배차 계산에는 원래부터 영향이 없었습니다 — 접안 전 배는 작업지시가 발행되지 않아 후보에 들어올 수 없기 때문입니다.

원천 데이터: TOS의 큐 진행표(JOB_QUEUE_SCHEDULE)와 작업지시(JOB_ORDER_LIST, A 활성 · Q 대기)를 ~90초마다 미러 + websocket GPS/PLC 실측(3초 폴). 배정 트럭 칩의 상태 점은 GPS에서 옵니다.

6. (참고) TT Dispatch의 트럭 칩

  • 배정 트럭 칩: 상자 옆 트럭 번호 + 상태 점(위 배차 상태 색) + 지금 어디서 뭘 하는지 한 줄.
  • 🤖 우리 추천 칩: 우리 계산이 보낼 트럭. TOS가 이미 배정한 상자에는 "우리라면 누구"를 나란히 — 같으면 ✓, 다르면 도착이 얼마나 빠른지/느린지. 추천이 3분 넘게 낡으면(계산 정지) 표시를 멈추고 알린다.
