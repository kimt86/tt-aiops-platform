① 장비 · 작업

TT · 야드 트럭 TT####
안벽(QC)과 야드 블록 사이에서 컨테이너를 운반하는 트럭. GPS device id와 TOS의 ytno가 같은 번호 체계.
QC · 안벽 크레인 C##
안벽에서 선박↔TT 사이 컨테이너를 옮기는 크레인. QC를 멈추지 않게 TT를 제때 보내는 게 배차 핵심. PLC(ctab) 송신.
RTG · 야드 크레인 ARMGC
야드 블록에서 TT↔적치장을 처리. PLC가 없어 핸드오버 관여는 TT GPS와의 근접(같은 bay ≈ 30m)으로 판정.
DS · 양하 Discharge
선박→야드. TT 기준 픽업=안벽(QC), 드롭=블록(RTG).
LD · 적하 Load
야드→선박. TT 기준 픽업=블록, 드롭=안벽(QC) — 양하와 방향 반대.
MI / MO / LC · 야드 이동
야드 안 이적 계열. 픽업·드롭이 모두 야드라 사이클 복원에서 첫 ARRIVED를 픽업으로 간주.
트윈 · 탠덤
컨테이너 2개를 한 번에 운반·처리. container1·container2가 모두 채워지고 twintandem 필드로 기록.

② TOS 데이터

작업 계획·배정의 권위 원천. 운영 Oracle은 추출기만 읽고 대시보드는 Postgres 복제본만 봄(FAQ). 상세 → TOS DB 레퍼런스.

TOS Terminal Operating System
터미널 운영 시스템(Oracle). 작업 지시·이력의 권위 원천이며 추출기가 주기적으로 PostgreSQL로 복제.
JOB_ORDER_LIST
TOS 라이브 작업지시 — 개별 컨테이너 move 단위로 배정 트럭(ytno)·컨테이너·ETW·RTG를 담음.
JOB_QUEUE_SCHEDULE
QC별 작업 큐 계획 — 크레인(C##)·순서(SEQ)·양/적·진행률(잔여=TOTAL−COMP).
JOBSTATUS A / B / Q (P, C)
A 활성(배차·진행중) · Q 대기(백로그) · B 차단 · P 계획 · C 완료. 가동률에서 "작업중"=A, "투입"=A·B·Q.
ytno YTNO
작업에 배정된 TT 번호. GPS device id와 일치해 TOS 계획 ↔ websocket 실측을 잇는 연결 고리.
contno CONTNO
컨테이너 번호. 작업과 사이클을 식별하는 기본 요소.
topos / from_pos / to_pos
작업 위치 필드 — 블록-베이(예 03U-21) 또는 크레인(C39) 형식.
ETW · 크레인 준비시각 Estimated Time of Work
크레인이 작업을 처리할 준비가 되는 예정 시각. TOS DB 컬럼은 수 시간 오차가 확인돼 정확값은 tos_etw_gateway에서(FAQ).

③ websocket 필드

GPS(wpt_gps)·크레인 PLC(ctab) 실시간 스트림. 구조와 함정 → 실시간 websocket 데이터.

container1 / container2 wpt_gps
물리 적재가 아니라 TOS "배정" 필드. 직전 drop에 다음 컨테이너가 사전배정(c2c)돼 값이 차 있어도 빈 차일 수 있음(FAQ). 2개 모두면 트윈·탠덤.
topos1 · 목적지 코드 wpt_gps
현재 미션 목적지 — 블록 베이 또는 크레인. 픽업↔드롭에 따라 동적으로 바뀜.
arrival / ARRIVED wpt_gps
목적지 도착 플래그. 픽업/드롭은 도착한 측면으로 복원(LD 블록=픽업·크레인=드롭, DS 반대, MI/MO 첫 도착=픽업).
cur_loc · 현재 위치
트럭이 지금 있는 위치 라벨(예 01U). 부가 표시용.
PLC 훅로드 ctab — load (t)
크레인 후크 하중(톤). 적재 ≥1.0t·빈 후크 ~0이라 하중 전이가 곧 PICKUP/DROP 순간. QC만 송신 — RTG엔 PLC 없음.

④ 지표 · 개념

산출식 전체 → KPI 산출.

사이클타임
TT 작업 1건이 도는 시간. KPI는 중위값·DS/LD 분리. 실측 TT 사이클 약 13–14분.
트럭 작업 4단계
무부하주행(빈 차로 감) → 픽업(실음) → 부하주행(싣고 감) → 드랍오프(내림). 2026-08-04부터 이 이름으로 통일합니다(옛 이름: 공차이동·받기·부하이동·주기). ARRIVED 의존이라 관측 못 한 단계는 추정 없이 NULL(FAQ).
★ 안벽크레인이 끼어드는 단계가 작업 종류마다 반대입니다 — 적하는 안벽크레인이 드랍오프(마지막), 양하는 픽업(둘째). → 배차 마감
트럭 준비시간
트럭을 그 일에 정한 순간부터 안벽크레인이 그 컨테이너를 다룰 수 있게 되기까지. 적하 = 무부하주행 + 픽업 + 부하주행, 양하 = 무부하주행(+ 픽업 대기). 실측 7일 양하 455초 · 적하 1,448초. 배차 마감 = 크레인이 그 컨테이너를 다루는 시각 − 이 값(2026-08-04~).
공차 레그 분해 retire · mig 0081
공차 레그를 30초 GPS로 움직임/정지 분해한 진단(learn_leg_decomp). 비용 라벨(순수주행=구간시간)은 learn_travel_sample로 이관돼 제거. 당시 규명: 구간 속도 ≈13km/h(움직인 순간만 ~22.8), "6.9km/h"는 착시, 같은 OD CV 0.758.
크레인 접근 대기 폐기 · 2026-07-01
크레인 앞 진입 대기를 1단계 신호로 쓰려 했으나 폐기. 일관 측정 시 중앙 ≈0, "중앙 67초"는 선택편향. 진짜 큐는 도착 이후(크레인 스케줄).
2단계 이동비용 · 순수주행
배차 2단계 이동비용 = free_in + 이동시간. 이동시간 = 순수주행(주행 구간 시간), 추론 도로망 최단시간 경로를 실측 "실제시간 곡선"으로 변환(2026-07-02, roadgraph.rs). 라우팅 불능 ~3%만 맨해튼→실제 곡선 폴백. 225m 격자 폐기(mig 0082). → 이동시간 모델.
이동필터 150 m / 30 s
"진짜 인도" 검증 — container1 변경 엣지 + 보유 ≥30초 + 운반 ≥150m일 때만 인도. 미달은 TOS 재배정 artifact로 기각(FAQ).
c2c · 연속적재
drop 시점에 다음 컨테이너가 이미 사전배정돼 작업이 끊김 없이 이어지는 패턴.
staging · 배차·대기
공차 + 정지 + 작업 배정됨. 미배정 유휴(idle)와 구분(FAQ).
idle · 유휴
공차 + 정지 + 미배정 — 즉시 배차 가능한 진짜 유휴(staging 분리 후 ~21대).
TT 가동률
작업 풀 배정 기반 — 작업중 = JOBSTATUS A, 투입 = A·B·Q. 60초 util_tt_sample을 시간 평균.
Little's law W = L / λ
안정 상태 평균 개체 수 L = 도착률 λ × 평균 체류 W. 대기시간 추정·검증에.
운영일 · 교대
Night 00–07 · Day 08–15 · Evening 16–23. 경계는 모두 터미널 시간 MYT(UTC+8) 기준(서버 KST와 1시간 다름).

⑤ 내부 시스템

Rust(axum) API + PostgreSQL + React/Vite 위에서 도는 파이프라인 구성 요소.

extractor · 추출기
운영 Oracle을 읽는 유일한 컴포넌트. 타이머로 정해진 주기에만 조회해 Postgres에 멱등 적재(작업 풀 틱 ~90초). API 크레이트엔 Oracle 클라이언트 없음(FAQ).
live_workpool / live_assigned_tt
작업 풀 스냅샷(~90초 틱). 원천 = JOB_QUEUE_SCHEDULE + JOB_ORDER_LIST.
util_tt_sample
60초 주기로 TT별 배정 상태를 기록. 시간 기반 가동률 평균의 원천.
tt_cycle_log
검증된 사이클 1건 = 1행(작업 메타 + 단계 타임스탬프 + leg 거리/시간). UNIQUE(ytno, dropped_at) 30초 멱등 flush. 학습 파이프라인 상류로 존치(과거 CYCLES 페이지 소스였으나 현행은 tt_cycle_recon).
tt_cycle_recon
현행 싸이클 정의 — 경계는 TOS(tt_move_log: 작업할당→픽업완료→드롭완료), GPS는 그 안의 주행/대기 분해만. 물리 트립 1행(트윈 collapse·3지점 중간경유). CYCLES 페이지가 읽음. 신뢰 기준 = 위치 점 ≥10개. → 해석 품질·한계.
tos_etw_gateway / wp-etw-bridge
정확 ETW 공급 — Azure FastAPI가 TOS RPC를 폴링, SSH 터널로 받아 tos_etw_cntr에 upsert(TTL 30분).
road_route_eval
실측 빈 트립마다 실제 구간시간 vs 도로망 경로시간 vs 맨해튼을 나란히 쌓는 표(10분·21일 백필). ① 상시 게이트, ② 2단계 비용의 두 실측 곡선 원천.
road_node / road_edge
GPS 궤적에서 매시 추론한 방향 도로망(2026-07-02 재구축: 7,189노드·작업지점 5,888 커넥터·방향 도로 단위 다수결). Rust 방향 Dijkstra가 배차 2단계 이동비용을 계산(성공률 96.7%). 첫 판(264노드·스냅 30%)은 게이트 탈락 → 재구축 후 채택.

자주 묻는 질문

Q. 왜 운영 Oracle(TOS)을 직접 조회하지 않나요?

운영 TOS는 터미널의 심장이라 대시보드 조회가 부하·장애 위험이 되기 때문. 추출기만 정해진 타이머에 Oracle을 읽어 Postgres로 복제하고, API 크레이트에는 Oracle 클라이언트 자체가 없어 구조적으로도 직접 조회 불가.

Q. 화면의 ETW가 TOS DB 값과 왜 다른가요?

TOS DB의 ETW 컬럼은 실제와 수 시간 어긋남이 확인됨. TOS RPC를 폴링하는 Azure의 tos_etw_gateway에서 정확값을 받아 tos_etw_cntr에 적재(TTL 30분). 터널이 끊기면 DB 값으로 폴백돼 정밀도가 떨어질 수 있음.

Q. 차량 풀의 idle 수가 갑자기 줄었습니다. 버그인가요?

분류 교정입니다. 기존 분류가 배정 여부를 무시해 idle 102대 중 51대가 실제로는 배정된 상태였음. 공차+정지+배정 = staging을 신설, idle은 진짜 미배정(~21대)만 남김.

Q. 사이클은 어떻게 "진짜"로 검증하나요?

이동필터 — container1 변경 엣지 + 30초 이상 보유 + 150m 이상 운반일 때만 진짜 인도. 미달은 TOS 재배정 artifact로 기각.

Q. container1이 차 있는데 트럭은 왜 빈 차인가요?

container1은 물리 적재가 아니라 TOS 배정 필드. 직전 drop에 다음 컨테이너가 사전배정(c2c). 실측: LD 트럭 34대가 container1이 세팅된 채 픽업 블록에 ARRIVED. 픽업 시점은 ARRIVED 측면 분류로 복원.

Q. 사이클 4단계가 일부만 채워진 행이 있는데요?

4단계 분해는 ARRIVED 신호에 의존해 놓친 단계는 추정하지 않고 NULL. 재시작 등 관측 경계 artifact 56건도 규명 뒤 NULL 정리 — "픽업도착<배정"을 '미리 가서 대기'로 오독했다 데이터(전수 일치, 83%가 재시작 후 첫 사이클)로 정정한 사례.

Q. KPI 옆 "잠정" 표시는 무엇인가요?

낮 동안 "오늘" 값은 교대 틱이 채운 잠정치. 매일 야간(01:30 MYT) 권위 런이 어제를 다시 추출해 확정하며 확정된 날은 재스캔하지 않음. → KPI 산출.

Q. ML 학습 데이터는 어디에 쌓이나요?

tt_cycle_log — 검증된 사이클 1건당 1행으로 30초마다 멱등 flush되며 2단계 예측 모형 연구의 학습 데이터로 축적. CYCLES 페이지에서 열람.

Q. 화면에 데이터가 안 보이면 어디부터 봐야 하나요?

FEED 페이지(WS 데이터 헬스)부터. websocket 데이터는 메모리에만 살아 SSH 터널이 끊기면 라이브 맵·차량 풀이 즉시 빔. Postgres 기반 화면이면 HEALTH 페이지에서 추출기 동작 확인.

Q. staging과 soon_idle은 무엇이 다른가요?

staging은 공차(빈 차 정지·다음 작업 배정돼 대기). soon_idle은 적재(짐 실은 채 드롭 측 도착·크레인 관여 중이라 곧 풀릴 트럭). "이미 배정돼 기다림" vs "곧 비워짐"의 차이. → 배차 풀 §2.
