클라우드 용량 산정 — CPU · 메모리

플랫폼(대시보드·실시간 수집·KPI)과 배차 로직(1·2단계)을 클라우드에 띄울 때 필요한 vCPU·메모리·스토리지 추정. ML 학습은 다른 서버에서 별도 산정. 핵심: 서빙·배차는 가볍고, 무거운 건 학습.

사이징 원칙 — 의도된 여유

수치는 의도적으로 보수적(넉넉)하게, 범위(최소→권장→넉넉)로 제시. 권장값에 이미 헤드룸이 들어 있어 실측 부하 테스트·모니터링 이후 다운사이징(right-size down) 가능 — 이 버퍼는 의도된 것. 불확실하면 권장~넉넉에서 시작하고 안정화되면 비용을 줄이세요.

왜 가벼운가

실시간 서빙·배차 부하는 websocket 수집(~90 msg/s)과 대시보드 폴링이 대부분인데 둘 다 가벼움(코어 1개 미만). 배차 최적화(헝가리안)·예측 추론도 결정당 수~수십 ms. 진짜 자원이 드는 건 ML "학습"이고 상시가 아니라 배치라 별도 서버에서 필요할 때만.

구성요소 — 무엇이 자원을 쓰나

  • ① 플랫폼(상시) — API(axum, WS 수집 + 메모리 라이브맵 + 대시보드 서빙) · PostgreSQL · 추출기(타이머) · 웹(정적) · SSH 터널.
  • ② 배차 엔진(상시) — 차량 풀·후보 작업 풀을 읽어 매칭/배정(헝가리안). 1단계=규칙, 2단계=결정 시 예측 추론 호출 후 최적화.
  • ③ ML 학습(배치·별도) — 누적 데이터로 2단계 모형 학습. 상시 아님(야간/주간), 다른 서버(CPU 다코어, 필요 시 GPU).

장비가 450대뿐이고 메시지도 초당 ~90건. 배차 최적화도 "유휴 트럭 × 후보 작업"의 작은 행렬(수백×수백)이라 헝가리안이 ms 단위로 끝남 — 대규모 트래픽 서비스가 아니라 한 터미널 규모의 실시간 제어라 코어·메모리 요구가 작다.

1단계 권장

최소 4 vCPU·8 GB → 권장 8 vCPU·16 GB 단일 노드로 전부 수용. 운영 안정성을 원하면 PostgreSQL은 관리형(2–4 vCPU·8–16 GB)으로 분리. 예: AWS m6i.2xlarge / GCP e2-standard-8 / Azure D8s_v5. 실측 후 4 vCPU·8 GB로 줄일 여지가 큼.

2단계 사이징 — + 예측 추론

배차 결정 때 모형으로 예측(이동시간·ETW·블록 핸드오버)을 만들어 더 정확히 매칭. 추론은 1단계 위에 얇게 얹힘(학습은 별도).

왜 추론이 가벼운가

2단계 예측은 표 형식 — 그래디언트 부스팅 트리(LightGBM/XGBoost) 추론은 건당 µs, 모형은 RAM 수십 MB. 결정당 수천 건 예측해도 한 자릿수 ms. GPU 불필요(학습 때만 선택). 노드 사양은 추론보다 운영 격리·버스트 여유용.

ML 학습 — 별도 서버 (배치)

2단계 모형을 누적 데이터로 학습. 상시가 아니라 야간/주간 배치라 서빙 클러스터와 분리된 서버에서 필요할 때만. 데이터 규모: 완료 작업 ~15K move/일 → 6개월 ≈ 2.7M 행 × 피처 30–50개. 학습 행렬 ≈ ~1 GB(중간물 포함 4–16 GB).

학습 서버 권장

ETW·이동시간 예측은 트리모형으로 충분 → 최소 16 vCPU·64 GB → 권장 32 vCPU·128 GB (GPU 불필요). 배치라 spot/preemptible로 비용 절감, 학습 끝나면 종료. 학습 산출물(모형 파일, 수~수십 MB)만 서빙 노드로 배포.

학습은 데이터 누적이 선행

2단계 학습엔 수개월치 필요. TOS 보존은 ~15/35일뿐이라(레퍼런스 §2), 1단계 운영과 동시에 매일 스냅샷을 적재해 두어야 6–12개월 뒤 학습 가능(record-only 파이프라인).

스토리지 주의 — GPS 원시

가장 큰 스토리지 항목은 학습용 GPS 원시 보관(연 ~200–300 GB). 대부분 예측은 move 단위 집약 피처로 충분하므로 원시는 샘플링/집약하거나 오브젝트 스토리지 콜드 계층(1–2 TB 예산·수명주기 자동 만료). 실시간 서빙은 GPS를 메모리에만 두고 DB에 안 쌓음(websocket 문서).

권장 · 주의

  • 넉넉히 시작, 실측 후 다운사이징. 1단계는 권장 8 vCPU·16 GB 단일 노드로 출발해 모니터링 후 조정.
  • 가용성(HA). 배차가 운영에 직접 관여하면 앱·배차 노드 이중화(2 AZ) + PostgreSQL 관리형(자동 failover).
  • 분리 원칙. ① 서빙 ② 배차/추론 ③ 학습을 분리(장애·부하 격리). 학습은 절대 서빙 클러스터에서 돌리지 않음.
  • 확장·비용. 사용자 수백 명이면 API 수평 확장. 학습 노드는 spot/preemptible + 배치 종료, GPS 원시는 콜드 스토리지.
전제·한계

위 수치는 한 터미널(Westports) 규모·내부 사용자·측정된 메시지율 기준의 추정이며 의도적으로 보수적인 헤드룸을 포함한 범위. 실제 값은 (가) 동시 사용자 (나) 배차 결정 주기 (다) 2단계 모형 복잡도 (라) GPS 원시 보관 정책에 따라 달라짐. 부하 테스트와 모니터링으로 검증 후 다운사이징해 확정하세요.
