**상태:** `검증됨`(조사·발견) · `초안`(예측 재시험) · **최종 검토:** 2026-06-15

[곧유휴 연구](/kc/research/soon-idle-tos/)에서 양하(DS) 트럭의 RTG 대기(`actv→comp` 중앙 ~12분, p90 34분)가 정밀 예측이 안 되는 게 드러났습니다. 그 **왜**를 끝까지 파다가 — **TOS에 RTG 상세 작업 로그가 이미 있었다는 것**을 발견했습니다. 본 노트는 그 조사 과정·발견·다음 카드를 남깁니다.

> **출처 등급:** **[코드]** · **[DB]** = 서빙 Postgres · **[ORA]** = prod TOS Oracle 직접 조회(저부하) · **[문서]** · **(미검증)**.

## 한 장 요약

1. **RTG 대기는 "줄 서는 큐"가 아니다.** 블록 큐 길이·시간대·RTG 식별자 어느 것도 대기를 예측 못 함(관측 피처로 분산의 **~93% 설명 안 됨**, 최선 피처 block조차 LOO R² +0.07).
2. **RTG는 로밍한다.** 블록당 고정 RTG는 12%뿐, 평균 3블록, move의 37%가 주력 블록 밖 → 블록별 상수는 시간에 표류(자기상관 ~0.05~0.12).
3. **발견: `MCH_OPERATION`에 RTG move가 상세히 찍힌다** — 시작(`ST_DT`)+완료(`COMPDATE‖COMPTIME`), 2일 55,024건 **[ORA]**. 대시보드 추출기가 QC(`^C`)만 필터해 안 보였을 뿐.
4. **물리 핸드오버는 ~60초** (중앙, p10 13·p90 149). 그런데 **우리 DS 핸드오버는 RTG 작업의 ~20%뿐** — 나머지 80%는 RH(재정리)·AH·GI/GO(게이트)·MI/MO(재배치). **12분 대기 = RTG가 그 사이 다른 move 5~10개를 끼워넣는 시간.**
5. → 그래서 DS 큐로는 대기가 예측 안 됐던 것. **RTG 전체 백로그**(모든 작업종류)가 미시도 핵심 피처. `rtg_move_log`로 적재 시작(mig `0032`).

## 1. 양하 대기는 큐가 아니다 — 조사 결과 [DB]

`tos_handover_label`(권위 정답, DS, 24h ~8,600 move) 위에서:

| 후보 피처 | 대기 예측력(LOO 표본외 R² 또는 corr) |
|---|---|
| 블록 큐 길이(겹치는 트럭 수) | **corr ≈ −0.01** — 혼잡해도 대기 안 늘어남 |
| 시간대 | corr ≈ 0.008 |
| 블록 정체성 | LOO R² **+0.07** (유일한 양수, 미약) |
| RTG 식별자(armgc) | LOO R² **−0.007** (사실상 0) |
| 근처 RTG 공급/부하 | \|corr\| ≤ 0.17 (방향만 일관: 공급↑→대기↓) |
| **나머지** | **~93% 미설명** |

- **블록 큐 길이 0대든 6대든 총 대기 ~21분으로 일정** — "줄이 쌓이는 큐"가 아님.
- **블록별 상수도 무효:** 같은 블록의 시간대별 SD(~7.7분) > 블록 간 SD(~4.1분), 전반부/후반부 자기상관 ~0.05~0.12 → 하루 안에서도 지속 안 됨(표류).

## 2. RTG 로밍 — "블록당 고정" 아님 [ORA]

| 지표 | 값 |
|---|---|
| 단일 블록 고정 RTG | 187대 중 **22대(12%)** |
| RTG당 distinct 블록(중앙/평균) | 3 / 3.05 |
| 주력 블록 밖 move | **37.2%** |
| 블록당 distinct RTG(평균) | 2.0 |

→ armgc↔block 1:1 가정은 깨진다(move의 1/3 놓침). "느슨한 홈블록"(주력 66% 집중) 패턴.

## 3. 발견 — `MCH_OPERATION`에 RTG 상세 로그가 있다 [ORA]

```
MCH_OPERATION 크레인 prefix (2일): RTG 55,024 · ES(empty handler) · C##(QC) · TT##(트럭)
```
RTG move도 **`ST_DT`(시작) + `MCH_OPER_COMPDATE‖COMPTIME`(완료)** 로 찍힘(`MCH_OPER_COMP_DT` 합본은 NULL이라 분리 컬럼 사용). 대시보드 KPI 추출기가 `REGEXP '^C[0-9]'`(QC)만 떠서 RTG 측을 안 가져왔을 뿐, **데이터는 있었다.**

**RTG 작업 taxonomy + 실제 작업시간** (오늘 표본 `rtg_move_log`) **[DB]**:

| jobtype | 의미 | 트럭 동반 | 중앙 작업시간 |
|---|---|---|---|
| LD | 적재(야드→트럭) | O | 77s |
| **RH** | **재정리(reshuffle)** | **X(하우스키핑)** | 68s |
| DS | 양하(트럭→야드) | O | **63s** |
| AH | (하우스키핑) | X | 38s |
| MI/MO | 야드 재배치 | O | 45~82s |
| GI/GO | 게이트 인/아웃 | O | 106~142s |

→ **물리 핸드오버 ~60초.** 우리 **DS는 RTG 작업의 ~20%**, RH+AH 등 하우스키핑이 ~30%+, 나머지는 LD/MI/MO/게이트.

## 4. 12분 미스터리 해소

한 RTG의 실제 ~30분 작업 스트림 예 **[ORA]**:
```
LD → AH → AH → GO(게이트) → AH → AH → AH → LD → MI → MI → MI
```
우리 DS 트럭이 활성(`ACTV`) 후 12분을 기다린 건 **RTG가 그 사이 AH 재정리·다른 트럭 LD/MI를 5~10개 끼워넣기 때문.** 진짜 "큐"는 DS 트럭 줄이 아니라 **RTG의 전체 혼합 작업**이고, 그 80%가 우리 DS 라벨엔 안 보였다 → DS 큐 corr≈0의 정체.

## 5. RTG 작업 사이클 — 추적 가능 단계

테이블을 합치면 한 DS 핸드오버를 **5시점 / 4구간**으로:

| 시점 | 출처 | 다음 구간 |
|---|---|---|
| 트럭 도착 `YT_DIS_DT` | JOB_ORDER_HISTORY | → 활성 대기 ~8분 |
| 주문 활성 `ACTV_DT` | JOB_ORDER_HISTORY | **→ RTG가 내 차례 올 때까지 ≈10분 (다른 move 끼임)** ← 변동의 핵심 |
| RTG move 시작 `ST_DT` | **MCH_OPERATION** | → 실제 들기 ~60초 |
| RTG move 완료 `COMPDATE‖COMPTIME` | **MCH_OPERATION** | → 마감 |
| 주문 완료 `'C'` | JOB_ORDER_HISTORY | — |

:::caution
RTG는 PLC가 없어 **±1초 물리 집기 순간**은 여전히 없음 — `ST_DT`는 "RTG가 그 move를 시작" 단위(60초짜리라 충분히 촘촘). `ACTV→ST` 구간이 곧 "내 앞의 다른 작업" = 변동 원천.
:::

## 6. 새 데이터 + 열린 질문 (예측 재시험)

`rtg_move_log`(mig `0032`, `wp-rtg-moves.timer` 5분 증분)가 RTG **전체** move를 적재 시작 — machno·jobtype·st/comp·dur·trk_id.

**열린 질문(미시도 핵심 카드):** `ACTV→ST` 대기를 **"그 RTG가 내 앞에서 처리하는 전체 move 백로그"**(모든 작업종류, DS만이 아니라)로 보면, DS 큐(corr 0)와 달리 대기를 유의하게 예측할까? 데이터가 하루+ 쌓이면 재시험.

:::note[정직한 전망]
완벽 예측은 여전히 어려울 수 있음 — AH 재정리 순서는 RTG 기사 재량이라 비결정적. 하지만 RTG 전체 백로그는 *올바른 데이터*이고 지금껏 시도한 어떤 피처보다 강한 후보. 안 되면 "분 단위 환원불가"를 더 단단히 확증하고, 배차는 기댓값(~21분)+불확실폭으로.
:::
