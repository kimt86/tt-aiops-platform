**상태:** `설계 확정 · 잠정 격자 비용 가동 · 학습 모델 미구축` · **최종 검토:** 2026-07-01

이 문서는 **TT(야드 트럭)의 한 번 이동(trip)이 몇 초 걸릴지 예측하는 모델**의 입력·출력·학습 방법을 정리합니다. 배차가 "이 트럭을 저 작업에 보내면 언제 도착하나"를 알아야 해서 만듭니다. 처음 보셔도 이해되도록 천천히 씁니다.

## 한눈 요약

1. **trip = 한 번의 연속 이동의 *주행 부분*** (출발지에서 *움직이기 시작* → 목적지에 *도달*). 라벨은 정지를 뺀 **순수 주행시간 `drive_s`**.
2. **출력은 "한 숫자"가 아니라 "분포"** (보통 N초, 빠르면 ~, 늦으면 ~). 같은 OD도 실제로 **±76%(변동계수 0.758)** 흩어지기 때문(야드는 확률 시스템).
3. **입력은 두 부류:** ㉠ *어디서 어디로*(도로망 경로거리·Manhattan — 순위는 됨) ㉡ *그 순간 상태*(날씨·시간대 — 변동 공략). 단, **정지·큐 노이즈가 지배적이라 어떤 거리 모델도 CV 0.758 바닥을 못 이깁니다.**
4. **학습은 단순·누적식:** 화려한 ML이 아니라 OD별 경험분포 + 거리→시간 관계. 데이터가 쌓일수록 좋아짐. **현재 비용은 학습 모델이 아니라 잠정 225m 격자 순수주행 룩업**입니다.

## 1. 이 모델이 푸는 문제

배차 결정엔 세 입력이 필요합니다 — **①차량 작업 완료 시점, ②완료 지점, ③완료지점→후보까지 이동시간.** 이 문서는 **③ 이동시간**을 다룹니다([①②는 곧유휴 연구](/kc/research/soon-idle-tos/) 참고).

## 2. trip이란? (모델의 단위)

```
빈다 ─[① 유휴: 배차 대기]─[② 공차 주행]─[③ 픽업 대기+적재]─ 찬다 ─[④ 적재 주행]─[⑤ 드롭 대기+하역]─ 빈다 …
                          └──── trip ────┘                      └──── trip ────┘
```

**trip = 출발지에서 *움직이기 시작한 순간* → 목적지에 *도달한 순간*** (순수 주행). 적재 여부 무관.
- 경계는 **모션 이벤트**(출발/도착)지 핸드오버(적재/하역)가 **아님** → 유휴·크레인 대기는 trip에 안 들어감.
- 컨테이너 작업 1건 = **2 trip**(공차 trip + 적재 trip).
- 데이터 출처: GPS 사이클 추적기(`tt_cycle_v2`)의 레그 `left`(출발 모션)→`arrived`(도착 모션). 이건 핸드오버가 아니라 **속도 기반 모션 경계**라 trip 정의와 맞습니다.

:::note[trip 안에도 정지가 섞여 있다 — 라벨은 주행만]
공차 레그를 30초 GPS 모션으로 분해(`learn_leg_decomp`)하면 한 레그의 **~53%만 실제 주행(`drive_s`), ~47%는 정지(`stop_s`, 대부분 목적지 최종접근·큐)** 입니다. 그리고 `ARRIVED`가 곧 물리 도착(중앙값 격차 −4s)이라 **큰 크레인 큐는 도착 *이후*** 에 있지 이동시간 안에 있지 않습니다. 그래서 이 모델의 라벨은 정지를 뺀 **주행 부분 `drive_s`** 이고, 큐·접근 대기는 1단계로 분리합니다(`learn_crane_approach`).
:::

## 3. 출력 — 왜 "분포"인가 ⭐

가장 중요한 설계 결정입니다.

> **출력 = 한 숫자(❌ "350초")가 아니라 분포(✅ "보통 350초 · 빠르면 200 · 늦으면 700").**

**근거(측정):** 같은 OD(동일 출발→도착)인데도 주행시간 `drive_s`가 **동일 OD 내 변동계수 0.758(±76%)** 로 흩어집니다. **이 바닥 밑을 이기는 거리 모델은 없습니다.**

**왜?** 이 변동은 모델이 부족해서가 아니라 **주행에 정지·큐 노이즈가 섞여** 있고 **야드가 확률 시스템**이라서입니다 — 순간 교통·양보·경로 차이·목적지 최종접근 정지. **결정 시점엔 관측 불가능한 미래 상태**라 점 하나로 맞추는 건 원천적으로 천장이 낮습니다. 그래서 정직한 출력은 **기댓값 + 불확실폭**입니다.

## 4. 입력 설계 ⭐

### 철칙: "결정 시점에 아는 것"만 입력
trip 시작 *전*에 배차하므로, 그때 모르는 건 못 씁니다.
- ❌ **실제로 달린 경로/거리** — trip이 끝나야 아는 사후정보(넣으면 컨닝). 대신 **"그 OD에서 보통 얼마나 도는지"의 학습값**을 씀.

### ㉠ "어디서 어디로" — OD 간 차이 (순위 결정, *됨*)
| 입력 | 정체 | 신호 |
|---|---|---|
| **Manhattan 거리** | 안벽 좌표계 격자 거리(`quay_manhattan_m`) | **corr 0.565** — 현재 최강 신호 |
| **도로망 경로거리** | 추론 도로망 Dijkstra 경로(`road_edge`) | corr 0.490 — Manhattan보다 약함(아래) |
| 출발/도착 존 | 225m OD 격자(`oz`/`dz`) | 거리·그룹 키 |

:::caution[도로망 경로거리는 Manhattan을 못 이겼다 — 음성 게이트]
격자가 좁은 다리·일방통행을 표현 못 해 **도로망 라우팅**으로 갈아타려 했습니다(빌드·검증 완료). 그러나 `drive_s` 라벨 대비 **도로 경로 corr 0.490 < Manhattan 0.565**, 게다가 **레그의 30%만 도로망에 snap**(작업점이 도로에서 중앙값 62m 밖). → **비용에 배선 안 함.** 도로 그래프는 향후 **학습 모델의 경로거리 *피처*(+노드 snap)** 로 쓸 계획이지, 그 자체가 비용이 아닙니다.
:::

### ㉡ "그 순간의 상태" — OD 내부 변동 공략 (*수집 중*)
같은 OD가 흩어지는 그 변동. 실제 교통·날씨라, **그 순간 공간 상태**만이 설명 가능.
| 입력 | 정체 | 상태 |
|---|---|---|
| **날씨(우천)** | 시간별 강수 → 우천 시 ~5% 느림 | 🔄 수집 중 — 약하지만 실재 |
| 엣지 혼잡(`congestion_edge`) | 도로 엣지별 트럭 밀도(시간당) | 전용도로라 **주행속도 영향 ≈0** |
| 시간대(dow/hour) | — | 약함, 보조 |

### 버린/약한 입력 (왜)
- ❌ **직선거리** → Manhattan/경로거리로 대체.
- ❌ **전역 혼잡도**(동시 in-flight 수) — 공간정보 없어 무의미.
- ❌ **엣지 혼잡** — 측정 결과 주행속도에 거의 영향 없음(전용도로) → 유지하되 신호 미미.

## 5. 출력 만드는 법 — 3단 폴백

데이터 조밀도에 따라(현재 구현 = 격자 룩업 + 거리 폴백):
1. **존쌍 충분히 쌓임** → `learn_travel_zone225_drive`의 그 존쌍 **순수주행 p50/p90**을 그대로.
2. **드묾** → 상위 존/블록 프리픽스로 완화한 룩업.
3. **처음 보는 존쌍(L3 폴백)** → `quay_manhattan_m ÷ 6.33 m/s`(≈22.8 km/h)로 p50 추정.

→ 조밀한 곳은 실측 분포로, 희소한 곳은 Manhattan÷속도로 거칠게. (학습 모델 단계에서 이 룩업을 회귀로 대체할 계획.)

## 6. 학습 방법

- **라벨(정답)** = 실제 trip의 **주행 부분 `drive_s`**(30초 모션 분해로 정지 제외, 정밀 도착만, 클린).
- **누적식 온라인 학습:** 애그리게이터가 완료된 GPS 사이클에서 공차 레그를 분해해 `learn_leg_decomp`에 적재하고, 존쌍별 순수주행 p50/p90를 matview `learn_travel_zone225_drive`로 집계. **데이터가 쌓일수록 OD 커버리지가 늘어 정확해짐.**
- **모델 형태 = 현재는 단순 격자 룩업 + 거리 폴백** (학습 모델은 미구축). `drive_s`의 동일 OD 내 변동계수가 0.758이라 **뽑을 신호가 그만큼 적어**, 거리 모델의 천장이 낮습니다. 설계상 다음 단계는 그래디언트 부스팅류 학습 모델(라벨 `drive_s`, 피처 = 도로망 경로거리 + Manhattan + 날씨 + 시간대).

## 7. 데이터 파이프라인

```
GPS 사이클(tt_cycle_v2) ──▶ 공차 레그 30초 모션 분해 ──▶ learn_leg_decomp
                                (drive_s · stop_s · approach · oz/dz · 좌표)
                                          │
             존쌍 순수주행 p50/p90 집계 ──▶ learn_travel_zone225_drive (배차 비용 소스)
             픽업지점 접근 대기 집계 ─────▶ learn_crane_approach (1단계로 분리·미배선)
```

| 테이블/매트뷰 | 내용 | 용도 |
|---|---|---|
| `learn_leg_decomp` | 공차 레그 1건/행: `drive_s`·`stop_s`·`approach`·좌표·`dest_topos` | 라벨·분석 원천 |
| `learn_travel_zone225_drive` | 존쌍별 순수주행 p50/p90(225m 격자) | **배차 비용 소스(현재)** |
| `learn_travel_zone225` | 존쌍별 실측(정지 포함) p50/p90 | 참조용(비용에 안 씀) |
| `learn_crane_approach` | 픽업지점별 접근 대기(`arrived − gps_arrived`) | 1단계 신호(미배선) |

## 8. 현재 상태와 정직한 발견 (수치)

| 항목 | 결과 |
|---|---|
| Manhattan 거리 ↔ 주행시간 | corr **0.565** — 현재 최강, 모더릿 |
| 도로망 경로거리 ↔ 주행시간 | corr **0.490** — Manhattan보다 약함(30%만 snap) → 미배선 |
| 같은 OD 내 변동 | CV **0.758(±76%)** — 진짜 확률성, 거리 모델의 천장 |
| 실제 주행속도 | ≈ **22.8 km/h**(레그의 ~53%가 주행) |
| 큐/접근 대기 | 중앙값 67s, 크레인별 22~194s → **1단계로 분리** |
| 날씨(우천) | ~5% 느림(약하나 실재) · 엣지 혼잡 ≈0 |

**중간 결론:** ③ 이동시간은 **거친·분포형 입력**입니다 — 정밀 점예측은 천장이 낮음(CV 0.758). 배차는 **기댓값 + 폭**으로 쓰고, 정밀 경쟁 대신 **유휴 제거 + 가용성(곧유휴)** 같은 통제 가능한 레버에 집중. 큰 크레인 큐는 이동시간이 아니라 **도착 이후**에 있으므로 1단계로 분리해 겨냥합니다.

## 9. 배차에서 쓰는 법

- 후보들을 **p50(기대)로 순위** → 명백히 가까운 트럭 선택(분포 안 겹치면 확실, 비슷하면 무관).
- **폭(p10~p90)으로 리스크 관리** — 꽉 짜지 말고 슬랙, 자주 재평가(그리디/롤링).
- 점추정 정밀 최적화 **금지**(노이즈 바닥 밑은 환상).

## 10. 예시 한 건

> **입력:** `06T-12(블록) → C29(안벽), 공차`, 지금 14:30, 비 안 옴
> → Manhattan 1,200m, 존쌍 순수주행 룩업 히트
> **출력(주행):** **p50 190초 (p10 130 · p90 330)** — 22.8 km/h 부근, CV 0.758 폭
> **배차:** 여기에 목적지 접근/큐(1단계 `learn_crane_approach`)를 더해 "언제 핸드오버 가능한가"로 후보 비교.
