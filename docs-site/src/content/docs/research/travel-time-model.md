**상태:** `가동 — 비용 = 도로망 경로시간 → 실제시간 곡선(격자 룩업 폐기)` · **최종 검토:** 2026-07-02

이 문서는 **TT(야드 트럭)의 한 번 이동(trip)이 몇 초 걸릴지 예측하는 모델**의 입력·출력·학습 방법을 정리합니다. 배차가 "이 트럭을 저 작업에 보내면 언제 도착하나"를 알아야 해서 만듭니다. 처음 보셔도 이해되도록 천천히 씁니다.

## 한눈 요약

1. **trip = 한 번의 연속 이동** (출발지에서 *움직이기 시작* → 목적지에 *도달*). 라벨은 **순수 주행시간 = 그 주행 구간에 걸린 시간**(출발→도달). 경로에서 신호·정체로 잠깐 멈춘 것도 *아직 주행 중*이라 **포함**하고, 도착해서 크레인과 주고받으려 기다리는 시간만 **뺍니다**.
2. **출력은 "한 숫자"가 아니라 "분포"** (보통 N초, 빠르면 ~, 늦으면 ~). 같은 OD도 실제로 **±76%(변동계수 0.758)** 흩어지기 때문(야드는 확률 시스템).
3. **입력은 두 부류:** ㉠ *어디서 어디로*(추론 도로망 위 경로 — 순위는 됨) ㉡ *그 순간 상태*(날씨·시간대 — 변동 공략). 단, **정지·큐 노이즈가 지배적이라 어떤 거리 모델도 CV 0.758 바닥을 못 이깁니다.**
4. **학습은 단순·누적식:** 화려한 ML이 아니라 물리 모델 + 실측 잔차. **현재 비용 = 추론 도로망 경로시간을 실측 "실제시간 곡선"으로 변환**(빈 트립에서 계속 배움) — 225m 격자 룩업은 **폐기**했습니다(2026-07-02).

## 1. 이 모델이 푸는 문제

배차 결정엔 세 입력이 필요합니다 — **①차량 작업 완료 시점, ②완료 지점, ③완료지점→후보까지 이동시간.** 이 문서는 **③ 이동시간**을 다룹니다([①②는 곧유휴 연구](/kc/research/soon-idle-tos/) 참고).

## 2. trip이란? (모델의 단위)

```
빈다 ─[① 유휴: 배차 대기]─[② 공차 주행]─[③ 픽업 대기+적재]─ 찬다 ─[④ 적재 주행]─[⑤ 드롭 대기+하역]─ 빈다 …
                          └──── trip ────┘                      └──── trip ────┘
```

**trip = 출발지에서 *움직이기 시작한 순간* → 목적지에 *도달한 순간*** (순수 주행 = 이 구간 전체 시간). 적재 여부 무관.
- 경계는 **모션 이벤트**(출발/도착)지 핸드오버(적재/하역)가 **아님** → 유휴·크레인 대기는 trip에 안 들어감.
- 컨테이너 작업 1건 = **2 trip**(공차 trip + 적재 trip).
- 데이터 출처: GPS 사이클 추적기(`tt_cycle_v2`)의 레그 `left`(출발 모션)→`arrived`(도착 모션). 이건 핸드오버가 아니라 **속도 기반 모션 경계**라 trip 정의와 맞습니다.

:::note[라벨 = 주행 구간 시간 (2026-07-01 정정)]
한때 라벨을 "움직인 순간만 센 시간(`drive_s`, 레그의 ~53%)"으로 뒀는데 **그건 틀렸습니다.** 경로에서 신호·정체로 멈춘 시간은 진짜 이동시간의 일부(날씨·혼잡이 예측할 몫)라 빼면 안 되고, 그렇게 빼면 가까운 트럭과 먼 트럭의 차이를 뭉갭니다. 반대로 "도착 후 핸드오버까지 다 포함한 시간"은 크레인 대기까지 섞여 과대. **정답은 그 가운데 — 출발부터 작업지점 도달까지의 구간 시간(`total_s`).** `ARRIVED`가 곧 물리 도착(중앙값 격차 −4s)이라 큰 크레인 큐는 도착 *이후*에 있어 자연히 빠집니다. 실측 중앙: 거리 781m·구간 237초(13km/h)인데 움직인 순간만 세면 120초(22km/h)로 과소.
:::

## 3. 출력 — 왜 "분포"인가 ⭐

가장 중요한 설계 결정입니다.

> **출력 = 한 숫자(❌ "350초")가 아니라 분포(✅ "보통 350초 · 빠르면 200 · 늦으면 700").**

**근거(측정):** 같은 OD(동일 출발→도착)인데도 주행시간이 크게 흩어집니다 — 움직인 순간만 잰 성분(`drive_s`)조차 **동일 OD 내 변동계수 0.758(±76%)**. **이 바닥 밑을 이기는 거리 모델은 없습니다.**

**왜?** 이 변동은 모델이 부족해서가 아니라 **주행에 정지·큐 노이즈가 섞여** 있고 **야드가 확률 시스템**이라서입니다 — 순간 교통·양보·경로 차이·목적지 최종접근 정지. **결정 시점엔 관측 불가능한 미래 상태**라 점 하나로 맞추는 건 원천적으로 천장이 낮습니다. 그래서 정직한 출력은 **기댓값 + 불확실폭**입니다.

## 4. 입력 설계 ⭐

### 철칙: "결정 시점에 아는 것"만 입력
trip 시작 *전*에 배차하므로, 그때 모르는 건 못 씁니다.
- ❌ **실제로 달린 경로/거리** — trip이 끝나야 아는 사후정보(넣으면 컨닝). 대신 **"그 OD에서 보통 얼마나 도는지"의 학습값**을 씀.

### ㉠ "어디서 어디로" — OD 간 차이 (순위 결정, *됨*)
| 입력 | 정체 | 신호 |
|---|---|---|
| **도로망 경로시간** | 추론 도로망 위 최단시간 경로(차선 속도 반영) | **현재 배차 비용의 본체** (아래) |
| Manhattan 거리 | 안벽 좌표계 격자 거리(`quay_manhattan_m`) | 라우팅 불능 쌍의 폴백 |
| 출발/도착 존 | 225m OD 격자 | ~~폐기~~ — 격자 인터림의 마지막 잔재까지 제거(mig 0082) |

:::note[도로망 — 한 번 탈락했다가, 다시 만들어 채택 (2026-07-02)]
첫 도로망은 탈락이 맞았습니다: 도로가 작업지점까지 들어오지 않아(중앙값 52m 밖) **경로의 30%만 계산 가능**했고 상관도 Manhattan보다 낮았습니다. 그래서 도로망을 **다시 만들었습니다** — ① 더 촘촘하게(길을 35m 조각으로), ② **작업지점 5,888곳을 전부 도로에 연결**(커넥터) → 이제 **작업지점 100%가 도로 위**(52m→0m), ③ 길의 방향(일방통행)은 조각별이 아니라 **도로 전체의 다수결**로 결정(조각별로 정하면 방향이 서로 충돌해 길이 끊긴 것처럼 됨), ④ 길 지오메트리를 기점 기준으로 정렬(거울상 노드 방지) — 경로 계산 성공률 46.6%→**96.7%**.
이 터미널은 격자형이라 **경로거리 ≈ Manhattan(상관 0.998)** — 현재 정확도는 대등합니다. 그래도 도로망을 쓰는 이유: (a) Manhattan은 공식이라 **천장이 고정**이지만 도로망은 차선 속도·혼잡·일방을 반영한 **경로'시간'** 으로 올라갈 여지가 있고, (b) 격자가 아닌 **다른 터미널에도 그대로 일반화**됩니다.
:::

### ㉡ "그 순간의 상태" — OD 내부 변동 공략 (*수집 중*)
같은 OD가 흩어지는 그 변동. 실제 교통·날씨라, **그 순간 공간 상태**만이 설명 가능.
| 입력 | 정체 | 상태 |
|---|---|---|
| **날씨(우천)** | 시간별 강수 → 우천 시 ~5% 느림 | 🔄 수집 중 — 약하지만 실재 |
| 엣지 혼잡(`congestion_edge`) | 도로 엣지별 트럭 밀도(시간당) | 전용도로라 **주행속도 영향 ≈0** |
| 시간대(dow/hour) | — | 약함, 보조 |

### 버린/약한 입력 (왜)
- ❌ **직선거리** → Manhattan/경로거리로 대체.
- ❌ **전역 혼잡도**(동시 in-flight 수) — 공간정보 없어 무의미.
- ❌ **엣지 혼잡** — 측정 결과 주행속도에 거의 영향 없음(전용도로) → 유지하되 신호 미미.

## 5. 출력 만드는 법 — 경로시간 → 실제시간 곡선 (+ 폴백)

현재 구현(2026-07-02, 격자 룩업 폐기 · 당일 리뷰로 "비율 곱하기"→"곡선 직접 학습"으로 교체):
1. **도로망 경로시간**: 트럭 위치→작업지점을 추론 도로망 위에서 최단 '시간'으로 계산(차선별 학습 속도 반영). 작업지점은 전부 도로에 연결돼 있어(커넥터) 사실상 모든 쌍이 계산됩니다.
2. **경로시간→실제시간 곡선(잔차 학습층)**: 경로시간은 물리 추정이라 실제와 체계적으로 다릅니다. 그래서 검증 표에서 **"이 정도 경로시간이면 실제로 보통 N초 걸리더라"를 구간별로 배워 그대로 씁니다** — 경로시간을 6구간(<30 / 60 / 120 / 240 / 480 / ≥480초)으로 나눠 각 구간의 **실제 p50(기대)·p90(보수) 초**를 매듭으로 삼고, 매듭 사이는 선형 보간, 첫 매듭 아래는 **바닥 유지**(아주 짧은 경로도 실측상 ~89초는 걸림), 끝 매듭 위는 기울기 연장. 매듭값에 단조 잠금(누적 최대)을 걸어 **더 먼 트럭이 더 싸게 계산되는 일이 구조적으로 불가능**합니다. 실측 매듭(현재): 경로 19초→실제 89/296 · 90초→102/351 · 344초→193/455 · 713초→296/591 (p50/p90).
3. **폴백(라우팅 불능 쌍만, ~3%)** → 같은 검증 표에서 배운 **맨해튼 거리→실제시간 곡선**(6구간: 125m→89초 … 3,846m→447초)으로 — 라우팅층(R)과 폴백층(L3)이 **같은 실현 스케일**이라 티어가 섞여도 비교가 공정합니다. 거리÷속도(`quay_manhattan_m ÷ 3.30 m/s`) 어림은 곡선조차 없을 때(콜드스타트)만.

:::caution[처음 넣었던 "비율 곱하기" 보정은 당일 리뷰에서 탈락]
처음엔 실제÷경로시간 **비율**(짧은 경로 1.40배·긴 경로 0.41배)을 구간별로 배워 **곱하는** 방식이었는데, 적대적 리뷰에서 결함 2개가 확정돼 같은 날 위의 직접 곡선으로 교체했습니다: (a) 비율이 스케일 따라 급감해 경로시간×비율이 **거리에 비단조** — 가까운 트럭이 먼 트럭보다 비싸져 순위·마감 필터가 뒤집힘, (b) 곱셈만으로는 짧은 경로의 실측 바닥이 사라짐 — 15초짜리 경로가 21초로 계산돼 초근거리 트럭이 공짜처럼 보이고 절감률이 과대계상.
:::

→ 비용 티어 표기: **R**(도로망 라우팅) / **L3**(Manhattan 폴백). 트럭(출발점)은 차선 밖 주기장에 서 있을 수 있어 스냅 반경 150m(짧은 진입 스텁은 곡선이 흡수), 작업지점(도착점)은 60m(커넥터로 0m에 붙음).

## 6. 학습 방법

- **라벨(정답)** = 실제 trip의 **주행 구간 시간 `total_s`**(출발→도달, 경로 정체 포함·핸드오버 대기 제외).
- **누적식 온라인 학습:** 애그리게이터가 완료된 사이클마다 **빈 트럭 트립**(출발→픽업 도착)의 구간시간을 `learn_travel_sample`에 적재(출발점 = 트럭의 **직전 드롭 위치**, 사이클 체이닝으로 GPS 없이 산출 — GPS 2일 창에 안 묶여 사이클 이력 3주치 사용). 10분마다 검증기가 이 빈 트립들을 도로망에서 라우팅해 **실제(라벨) vs 경로시간 vs 맨해튼**을 나란히 기록(`road_route_eval`, 21일 자가 백필)하고, 배차 비용은 매 틱 이 표에서 **두 곡선(경로시간→실제 · 맨해튼→실제)** 을 새로 적합해 씁니다 — 데이터가 쌓일수록·도로망이 좋아질수록 곡선이 저절로 따라갑니다. *(공차 레그 30초 모션 분해 `learn_leg_decomp`는 **retire됨**(mig 0081); 225m 격자 집계 매트뷰도 **폐기**(mig 0082).)*
- **모델 형태 = 도로망 경로시간 + 실측 곡선** — 격자 룩업이 아니라, 어디서 어디로든 답이 나오는 물리 모델 위에 "추정→실제" 실측 곡선을 입힌 형태. 같은 OD 내 변동이 커(CV 0.758) **뽑을 신호가 그만큼 적어** 정밀 점예측 천장은 낮습니다. 다음 단계 후보: 도로망 자체를 살찌우기(차선 속도·혼잡 반영 — 경로'시간'의 헤드룸), 곡선 피처 추가(날씨 등, 단 측정상 신호 미미).

## 7. 데이터 파이프라인

```
GPS(이동 트럭) ──매시간 재추론──▶ 도로망 그래프 road_node/road_edge (조밀화 + 작업점 커넥터·방향=부모도로 다수결)
                                        │
tt_cycle_v2 ─▶ 빈트립 구간시간 ─▶ learn_travel_sample(leg_ord=0)     │
                     │                                              ▼
                     └──10분 검증기: 빈트립을 라우팅──▶ road_route_eval (실제 vs 경로시간 vs Manhattan)
                                                          │
              배차 비용(매 틱) ◀── 두 실측 곡선: 경로시간→실제 p50/p90 (R) · 맨해튼→실제 (L3)
```

| 테이블/매트뷰 | 내용 | 용도 |
|---|---|---|
| `road_node`/`road_edge` | 추론 도로망(7,189 노드 — 작업점 5,888개 커넥터 포함, 일방·차선속도) | **배차 비용의 본체**(경로시간) |
| `road_route_eval` | 빈트립 1건/행: 실제 구간시간(라벨)·경로시간·경로거리·Manhattan | **두 비용 곡선의 원천 + 상시 게이트** |
| `learn_travel_sample` (leg_ord=0) | 빈트립 1건/행: 구간시간·출발=직전드롭·좌표 | 라벨 원천(3주·GPS불필요) |

## 8. 현재 상태와 정직한 발견 (수치)

| 항목 | 결과 |
|---|---|
| 경로 계산 성공률(라우팅) | 재구축 전 46.6% → **96.7%**(방향=부모 도로 다수결 + 지오메트리 기점 정렬) · 작업점 스냅 52m→**0m(100%)** |
| 도로망 경로시간 ↔ 실제(구간시간) | corr **0.358** vs Manhattan **0.385** — **대등권**(상시 게이트로 계속 측정) |
| 경로거리 ↔ Manhattan | corr **0.998** — 격자형 터미널이라 거의 같음(도로망의 가치는 정확도가 아니라 헤드룸+일반성) |
| 경로시간→실제 곡선(매듭) | 경로 19초→실제 **89**/296 · 90초→102/351 · 344초→193/455 · 713초→**296**/591 (p50/p90) — 짧은 경로 바닥 ~89초 |
| 마감 충족(feasible, 라우팅층) | 비율 곱 보정에서 20.6%로 붕괴 → **직접 곡선으로 81.6% 정상화** |
| 같은 OD 내 변동 | CV **0.758(±76%)** — 진짜 확률성, 어떤 거리 모델도 시간↔거리 corr ~0.38 천장 |
| 주행 구간 속도 | ≈ **13 km/h**(구간시간 기준) · 움직인 순간만 보면 ~22.8 km/h |
| 크레인 진입 대기 | **폐기** — 일관 측정 시 중앙값 ≈0(옛 67초는 선택편향), §아래 |
| 날씨(우천) | ~5% 느림(약하나 실재) · 엣지 혼잡 ≈0 |

**중간 결론:** ③ 이동시간은 **거친·분포형 입력**입니다 — 정밀 점예측은 천장이 낮음(CV 0.758). 배차는 **기댓값 + 폭**으로 쓰고, 정밀 경쟁 대신 **유휴 제거 + 가용성(곧유휴)** 같은 통제 가능한 레버에 집중. 큰 크레인 큐는 이동시간이 아니라 **도착 이후**(work_eta·크레인 스케줄 영역)에 있습니다. 한때 이걸 "크레인별 진입 대기"로 1단계에 넣으려 했으나, 일관된 방법으로 재보니 중앙값 ≈0이고 옛 67초는 선택편향(도착 전에 근처에 찍힌 트럭만 셈)이라 **폐기**했습니다.

## 9. 배차에서 쓰는 법

- 후보들을 **p50(기대)로 순위** → 명백히 가까운 트럭 선택(분포 안 겹치면 확실, 비슷하면 무관).
- **폭(p10~p90)으로 리스크 관리** — 꽉 짜지 말고 슬랙, 자주 재평가(그리디/롤링).
- 점추정 정밀 최적화 **금지**(노이즈 바닥 밑은 환상).

## 10. 예시 한 건

> **입력:** `06T-12(블록) → C29(안벽), 공차`, 지금 14:30, 비 안 옴
> → 도로망 라우팅: 트럭 위치를 가까운 차선에, C29 작업지점은 커넥터로 도로 위 — 최단시간 경로 계산(예: 경로시간 340초)
> **출력(주행):** 경로시간→실제 곡선에서 읽음 = **p50 ~193초·p90 ~455초** — 기대와 보수, 큰 폭
> **배차:** p50으로 후보 순위를 매기고 p90으로 마감 여유를 검사합니다(크레인 진입 대기 항목은 없음 — 측정 ≈0이라 폐기).
