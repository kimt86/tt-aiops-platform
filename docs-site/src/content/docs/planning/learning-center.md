## 한 줄 요약

**학습 센터**는 누적되는 작업 사이클 데이터로 **예측 모형을 학습→검증→활용**하는 일을 한곳에서 굴리는 거점이다. 무엇을·어떻게의 *기술 상세*는 이미 [예측 모형 연구](/kc/research/tt-prediction/)에 있다 — **이 문서는 그 학습을 어떻게 조직·운영·활용할지의 프로그램 차터**다.

## 왜 지금

- 운영(1단계)이 도는 것만으로 **학습데이터가 자동 생산**된다 — record-only 파이프라인이 사이클을 라벨로 바꾼다([연구 §5·§6](/kc/research/tt-prediction/)).
- 우리는 이미 [`tt_cycle_log`/`tt_cycle_v2`(6-이벤트)](/kc/experiments/cycle-v2-shadow/)를 검증된 단위로 쌓고 있다 — 학습의 연료가 매일 쌓인다.
- 흩어지면 또 까먹는다. 데이터셋·모델·실험·교훈을 [지식센터](/kc/start/overview/) 컨벤션 위에 **단일 출처로** 모은다.

## 1. 무엇을 학습할지

**1차 범위 — 웹소켓(GPS) 데이터만으로 학습할 3가지** (확정):

| # | 학습 대상 | 출력 | 웹소켓 원천 |
|---|---|---|---|
| ① | **TT 이동시간(실측 OD)** | 구간(출발→도착) 소요 초 — 주행/정지 분해 포함 | GPS 트립 (사이클 6-이벤트) |
| ② | **블록 작업지점 좌표** | 각 topos 코드(예 `03U-21`)의 실제 (x,y) 위치 | GPS 좌표 ↔ `topos1`/`cur_loc` 누적 |
| ③ | **차량 주행 차선·방향** | 트럭이 실제 다니는 도로·차선 네트워크(경로·방향) | GPS 트레이스(궤적) 집계 |

- **②③ = 레이아웃을 데이터로 학습한다.** 블록 작업지점의 위치(②)와 차선망(③)을 GPS에서 직접 배워, 수작업 레이아웃 정의를 **보완·대체**한다 — 어떻게·활용은 아래 §4.
- **세 가지가 맞물린다**: ②로 출발·도착 지점을 정확히 찍고, ③ 차선망 위 경로로 거리를 잡아, ①(이동시간)을 **레이아웃 인지**로 끌어올린다.

:::note[공차 레그 분해 — `learn_leg_decomp`]
①(이동시간)의 학습 라벨은 **순수주행 = 주행 구간 시간**(출발→작업지점 도달, `total_s`)이다. 경로에서 신호·정체로 멈춘 것은 *아직 주행 중*이라 포함하고, 도착 후 크레인과 주고받는 대기만 뺀다. `learn_leg_decomp`는 이 구간시간과 함께 그 안의 움직임(drive_s·~53%)/정지(stop_s·~47%) 분해를 진단용으로 담는다. 핵심: ARRIVED가 실제 도착과 거의 같아(중앙값 −4초) 큰 크레인 대기는 이동시간 밖(도착 이후)에 있으며, 같은 OD에서도 변동계수 0.758로 대기 노이즈가 지배해 거리 모델의 정확도 바닥이 여기서 정해진다. **[2026-07-01 정정]** 한때 라벨을 "움직인 순간만(drive_s)"으로 뒀으나 경로 정체까지 벗겨 근거리-원거리 차이를 뭉개므로 구간시간으로 교정했다.
:::

:::note[연구의 다른 예측기는 1차 범위 밖]
[예측 모형 연구](/kc/research/tt-prediction/)는 QC ETW·블록 핸드오버·곧유휴도 다루지만, 이들은 **PLC·TOS DB가 함께** 필요하다. 이 문서의 **1차 학습 범위는 위 웹소켓 3가지**로 잡고, 나머지는 데이터·합의가 갖춰진 뒤 확장한다.
:::

## 2. 어떻게 학습할지

- **자가 라벨(record-only)**: 운영 중 파이프라인을 돌려 *예측 vs 실제*를 매 배차 기록 → 라벨이 자동 누적. 별도 라벨링 없음.
- **점진적 복잡도**: `v0 베이스라인`(구간별 중앙값) → `v1` 그래디언트 부스팅 → 필요 시 `v2`. **항상 v0 대비 개선분을 입증**한다.
- **정직한 검증**: **시간 분할**(미래 교대로 검증, 누설 차단), 지표 **MAE(초)·P90**, 주/야·물량·작업종류 층화. 배차 품질은 보조 시뮬레이터로 교차.
- **데이터 품질 규율**(이 프로젝트의 핵심 자산):
  - 관측 못 한 값은 **NULL**, 추측으로 채우지 않는다.
  - 세 신호(GPS·PLC·TOS) 교차 일치 표본만 학습에 쓴다(노이즈 제거).
  - **누설 방지**: 피처는 "결정 시점 t₀ 이전" 정보만.

## 3. 학습한 것을 어떻게 활용할지

- **배차 비용 함수에 투입**: ①(이동시간) + ②③(레이아웃: 작업지점·차선망)으로 후보 (차량→작업)의 **공차 이동 도착비용**을 산출 → 최소비용 매칭의 기본 비용(= free_in + 이동시간). **현재 이동비용은 순수주행(구간시간) 격자 조회가 잠정**: 매트뷰 `learn_travel_zone225_drive`(225m OD 격자·구간시간 p50/p90), L3 폴백 = quay_manhattan_m ÷ 3.30 m/s. ①의 학습 OD 모델이 이 조회를 대체하는 것이 목표다.
- **크레인 앞 대기는 이동비용에서 제외**: 도착 후 크레인과 주고받는 대기는 이동시간이 아니라 도착 이후(크레인 스케줄) 영역이라 트럭별 이동비용에 넣지 않는다. **[2026-07-01 정정]** 이를 "크레인별 진입 대기"로 1단계에 넣으려 매트뷰(`learn_crane_approach`)를 만들었으나, 다시 재보니 그 대기는 실제로 **거의 0**(옛 67초는 편향)이라 **폐기**했다. 크레인대기(ETW)까지의 완전한 시간비용은 연구의 PLC/TOS 예측기와 함께 확장([연구 §2·§3](/kc/research/tt-prediction/)).
- **그림자 → 측정 → 승격** (사이클 v2와 **같은 규율**, [실험](/kc/experiments/cycle-v2-shadow/)): record-only로 예측·추천을 그림자로 돌려 *예측 vs 실제* lift를 측정하고, 게이트 통과 시에만 실제 배차에 반영.
- **대시보드 노출**: 예측 사이클타임·추천 배차·혼잡/크레인대기 예보를 surfacing(FEED/HEALTH 연계).
- **폐루프**: 예측↔결과를 다시 학습데이터로 — 정확도를 상시 모니터.
- **폴백 안전**: 예측 신뢰 낮음·모형 장애 시 **1단계 거리비용으로 즉시 복귀**. 2단계는 1단계 위에 얹는 가중치라 투자가 보호된다.

## 4. 레이아웃(②③) 학습 — 방법·활용

§1의 ②③은 **레이아웃 자체를 GPS에서 배우는** 부분이다. 별도 레이아웃 빌더·라우터 이니셔티브가 수작업 정의를 만들면, 학습은 그것을 **검증·자동초안·보정**한다(상호 보완).

### 어떻게 학습하나

- **② 블록 작업지점 좌표**: 트럭이 `topos1` 타깃에 **도착(ARRIVED)** 한 순간들의 GPS 좌표를 topos 코드별로 **누적·클러스터링** → 각 작업지점의 대표 (x,y). 사이클 6-이벤트의 도착 표본이 깨끗.
- **③ 차량 주행 차선**: 전체 GPS 트레이스(궤적)를 모아 **도로·차선 네트워크로 추론** — 빈번 경로·주행 방향·차선 수. GPS는 장비당 ~3초로 성기므로 차선 단위는 정확도 임계(예 ≤30m)에서만 채택.
- record-only 자가 라벨 규율 동일 — 운영이 돌수록 좌표·차선이 정밀해진다.

### 어떻게 활용하나

- ②③ → **데이터로 구성한 레이아웃(작업지점 + 차선망)** → 이동시간(①)의 거리 피처를 직선/arc에서 **도로망 경로 거리**로 보강(라우팅 자체가 비용이 아니라, 모델의 **경로거리 피처**를 공급).
- 도로망은 이미 라우팅 가능하게 적재됨: 매시 Python cron이 GPS→스켈레톤→링크로 추론, `road_node`/`road_edge`(mig 0077·~264노드/353방향엣지), Rust 방향 Dijkstra 라우터 `crates/api/src/roadgraph.rs`.
- 구간 통행·혼잡 통계(`congestion_edge`) → 이동시간 모델의 피처(단, 전용도로라 주행속도 영향 ≈0로 관측).

:::caution[도로망 라우팅 게이트 — 검증 완료·미채택]
225m 격자는 좁은 다리·일방통행을 표현 못 해 폐기 결정했으나, 도로망 라우팅도 게이트에서 떨어졌다. **결과(drive_s 라벨·585 스냅 레그)**: 도로 경로 상관 0.490 vs 맨해튼 0.565 → 도로가 더 나쁘고, 스냅되는 레그는 30%뿐(작업지점이 도로망에서 중앙값 62m 벗어남). → **핫패스 비용에 미채택**, 비용은 순수주행 격자 유지. 도로망 인프라는 향후 더 촘촘한 그래프의 **경로거리 피처** 공급용으로 보존한다.
:::

## 5. 학습 센터 운영 — "센터"의 형태

학습 산출물을 지식센터 어디에 둘지(단일 출처 유지):

| 산출물 | 위치 |
|---|---|
| 예측 대상·데이터 설계 연구 | [리서치](/kc/research/) (예: [예측 모형 연구](/kc/research/tt-prediction/)) |
| 모델 학습·게이트·lift 측정 | [실험](/kc/experiments/) (실험 로그 템플릿) |
| 큰 선택(모델·피처·승격) | [의사결정 ADR](/kc/decisions/) |
| 작업 일지·삽질·정정 | [구현 기록](/kc/journal/) |
| **데이터셋·모델 레지스트리** | 대시보드에 **학습 센터 페이지**로 구현됨 — 탭 2개: (1) 예측 모델(모델 카드 6종: ① TT 이동시간(실측 OD·주행/정지 분해) ② 작업지점 좌표 ③ 주행 차선·방향 ④ Soon-idle ⑤ 유휴 분 예측 ⑥ 배차 작업시점(1단계)) (2) 데이터 수집(수집 스트림 16종·`learn_leg_decomp` 포함·각 카드에 소스/용도/건수+최근 행). API: `/api/learn/data-catalog`·`/api/learn/data-sample` |

- **카덴스**(제안): 주간 모델 리뷰(지표·lift·드리프트), 실험은 로그로 즉시 기록.
- **합의 필요**(TOS팀): "곧 유휴" 정의·호라이즌·신뢰 임계([연구 §7b.4](/kc/research/tt-prediction/)).

## 6. 단계별 로드맵

연구의 일정과 정합([연구 §11](/kc/research/tt-prediction/)) — *(미검증)* 날짜는 연구 문서 기준, 함께 확정 필요:

1. **지금**: record-only 파이프라인 가동, `train_*` 테이블 축적, **v0 베이스라인으로 데이터 건전성 조기 점검**.
2. **학습·검증**: v1 학습, 시간분할 검증, 지표 합의.
3. **전환 검증**: record-only로 예측 vs 실제 lift 공동 판정.
4. **활용 전환**: 게이트 통과 시 시간비용(2단계)으로 전환. 선적 곧유휴 먼저, 양하는 점진 확대.

## 원칙

- **그림자 → 검증 → 승격.** 검증 안 된 예측을 핫패스에 바로 쓰지 않는다.
- **관측 못 한 값은 NULL**, 추측 금지. 베이스라인 먼저, 복잡도는 입증된 만큼만.
- 모든 학습 문서는 [글쓰기 규칙](/kc/start/contributing/)의 상태표시·`(미검증)` 원칙을 따른다.
