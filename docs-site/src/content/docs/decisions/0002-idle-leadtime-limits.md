**상태:** `채택됨` · **최종 검토:** 2026-07-15

:::note[한 줄 결론]
**"방금 비었다"(탐지)는 알 수 있지만, "몇 분 후 빌지"(리드타임)는 개별 트럭 단위로는 못 맞춘다.** 대기를 만드는 크레인 큐가 우리 관측 신호에 안 보이기 때문이며, 이는 모델을 바꿔서 될 문제가 아니다. 배차는 리드타임을 점이 아니라 **보수적 p90 분포**로 쓴다.
:::

## 맥락 — 무엇을 하려 했나

2단계 배차는 "지금 유휴" 트럭뿐 아니라 **"곧 유휴될" 트럭**도 후보 풀에 넣으려 한다. 이때 필요한 게 **리드타임** — "이 트럭이 몇 분 후 비는가"를 미리 아는 것. 이걸 정확히 알면 대체 트럭을 미리 준비할 수 있다.

리드타임은 두 조각으로 나뉜다:

```
유휴까지 시간 = (크레인이 나에게 올 때까지 대기) + (실제 핸드오버 작업)
```

- **핸드오버 작업**: 짧고 안정적 (LD ~0초, DS ~57초) — 예측 가능.
- **대기**: 크레인이 내 차례 전에 몇 개를 먼저 하느냐(다른 슬롯/베이·선측 듀얼사이클·야드 재취급 AH/RH ~26%)에 달림 — **이게 전부이고, 이걸 못 맞춘다.**

## 결정

**유휴 리드타임을 개별 정밀 예측하려는 시도를 중단한다.** 대신:

1. **점추정** — 사이클 단계별 실측 중앙값(학습)을 후보 타이밍의 기준으로.
2. **보수적 p90 방어** — 배차 마감 판정은 낙관적 중앙값이 아니라 **p90 도착**으로. 예측이 틀려도 크레인이 트럭을 못 받아 노는 사고를 막는다. (이미 이렇게 동작 중)
3. **탐지는 정확하니 그걸 쓴다** — "방금 빈" 트럭은 즉시·정확히 후보 풀에.

## 근거 — 세 각도가 모두 같은 결론

### ① GPS 앞대수로 큐를 못 본다 (재설계 검증, mig 0088)
"작업지점 도착 + GPS로 센 앞 트럭 수 × 크레인 사이클"로 리드타임을 예측하려 했으나 실패:

| | 앞대수 0인데 실제 대기 |
|---|---|
| LD | 198초 = **2.2 크레인 사이클** |
| DS | 341초 = **3.7 사이클** |

GPS로 "앞에 아무도 없다"인데도 크레인은 이미 2~4개를 먼저 했다. **보이는 트럭 줄 ≠ 진짜 큐.** 대기를 만드는 건 크레인 상태(재취급·다른 베이·선측 작업)이고, 트럭 GPS엔 안 보인다. *(위 초 단위는 부풀려진 laden 앵커 기준 — 정차 앵커로 재면 절반이지만, "앞대수로 큐를 못 본다"는 결론은 앵커와 무관하게 유지.)*

### ② 어떤 모델도 못 넘는다 (ML 벤치마크)
관측 가능한 모든 피처(상태·RTG거리·사이클위치·크레인)를 GBM·신경망에 줘도 MAPE **64→62% (+2pp뿐)**. 신호가 있으면 ML이 뽑아낸다. 안 뽑힌다 = **데이터에 신호가 없다.**

### ③ TOS 크레인 기록도 실시간이 아니다 (Oracle 직접조회, 2026-07-15)
TOS `MCH_OPERATION`에 크레인 작업 시작시각·컨테이너·트럭이 있어 한때 "이걸로 리드타임을 크랙할 수 있다"고 봤으나 — **레코드가 완료 시점에 생성됨**을 확인:

| 검사 | 결과 |
|---|---|
| 최근 1시간 생성 행 중 진행중(완료 전) | **0건** (전체 3,301건) |
| 행 생성시각 − 완료시각 | **0초** (완료 때 생성) |
| 행 생성시각 − 시작시각 | **276초(4.6분)** (시작은 4.6분 전인데 그때 행 없음) |

즉 TOS는 작업이 **끝날 때** 행을 만들고 시작시각을 소급 기입한다. "지금 크레인이 이 트럭을 물기 시작했다"를 실시간으로 알 방법이 없다(행이 완료돼야 존재). RTG 이동 시작이 트럭 자유를 ±30초로 감싸는 건 맞지만, 그 기록은 **완료 + 추출지연(2.5~5분) 뒤에야** 온다 = 리드타임이 아니라 **지연된 탐지**(GPS로 이미 하던 것).

## 핵심 뉘앙스 — "아무것도 모른다"가 아니다

- **중앙값은 안다** — "DS 곧빔 트럭은 보통 ~250초 후 빈다".
- **개별 판별이 안 된다** — "지금 이 트럭이 90초일까 600초일까?"

배차가 원하는 건 개별 판별인데, 그게 관측 신호로 불가능하다. 트럭이 드롭에 **정차한 뒤에도** 남은시간은 LD median 140초·p90 520초 / DS median 256초·p90 763초 로 흩어진다("곧 빈다는데 언제일지 개별론 모름").

:::note[측정 정정 (2026-07-15)]
초판은 "곧빔→자유"를 우리 `laden_arrived_at`(느슨한 70m 지오펜스/TOS 도착) 기준으로 재서 **p90 ~1000~1500초로 부풀렸다**. 검증 결과 그 "대기"의 **~50%는 트럭이 아직 이동 중**(도착이 일찍 찍힘)이라 주행시간이 섞였다. **GPS 정차 순간을 앵커**로 다시 재면 진짜 대기는 절반: **LD p50 140·p90 520초 / DS p50 256·p90 763초**. dropped_at(자유)은 훅로드 엣지와 −29초로 정확. → 결론(개별 리드타임 불가·hazard 무의미)은 **정정된 값에서도 유지**되나, **점추정·p90 캘리브레이션은 정차 앵커로 바로잡아 배차에 반영**(learn_free_in 정차 기준). 경과시간(hazard)은 정차 기준에서도 약함(DS prec@120 31→34%).
:::

## 더 근본적으로 — 트럭은 멈추면 안 보인다 (2026-07-15)

웹소켓 데이터 감사에서 가장 깊은 원인이 드러났다: **차량 GPS 단말이 "움직이면 보고, 멈추면 침묵"** 한다(큰 끊김의 100%가 트럭 정지 직후 시작). 그런데 우리가 관측하고 싶은 건 **멈춰서 크레인을 기다리는 순간**이다 — 바로 그때 트럭이 피드에서 사라진다. 위 세 각도의 실패는 결국 이 하나로 수렴한다: **관측하려는 대상이 관측 시점에 침묵한다.** 상세: [웹소켓 데이터 품질](/kc/architecture/websocket-data/#62--근본-한계--정지하면-gps-단말이-침묵한다).

## 이것이 되려면 (경계)

대기를 보이게 하려면 **크레인 작업의 실시간 진행 신호**가 필요하다 — RTG PLC(없음) 또는 크레인 작업큐의 실시간 진행 상태(TOS는 완료 후에만 기록). 또는 **차량 단말이 정지 중에도 주기 보고**하도록 터미널 측에서 재설정. 셋 다 현재 없다. 이 중 하나가 생기면 재검토한다.

## 대안 (검토 후 기각)

- **GPS 앞대수 × 사이클** — 큐를 못 봄(①). 기각.
- **GBM/신경망** — +2pp뿐(②). 기각.
- **TOS `MCH_OPERATION` 실시간 물림 신호** — 사후 생성이라 실시간 불가(③). 기각.
- **TOS `JOB_ORDER_LIST` 활성 작업(90초 라이브)** — DS 활성화시각은 선측 픽업이지 블록 물림이 아님. 리드타임 신호 아님.

## 후속

- GPS 앞대수·타이트 도착 그림자 로거(`qc_handover_edge`·`tt_wp_arrival`, mig 0087/0088)는 무해하여 유지하되 **리드타임 목적 재추진 금지**.
- DS 물림 **탐지**(사후·지연 허용 시)에는 `rtg_move_log`가 GPS보다 나을 수 있음 — 별건.
