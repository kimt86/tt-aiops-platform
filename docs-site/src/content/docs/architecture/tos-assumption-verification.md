:::tip[한 줄 요약]
우리는 TOS Oracle DB에서 값을 읽어 **의미를 추정**해 배차합니다. 그 추정이 맞는지 **실제 TOS 소스코드**(Java, `oss-core`)와 대조했습니다 — 25개 에이전트 병렬 조사. **대부분 정확**했고, 몇 개를 고쳤으며, 두 개는 "틀린 줄 알았는데 실제 데이터로 보니 우리가 맞았던" 헛다리였습니다.
:::

## 고친 것

### 1. 트윈 식별: contno → twinkey (실데이터로 확정)
- **틀린 가정**: "같은 contno 다른 행 = 트윈". 그런데 contno는 **컨테이너 고유번호**라 같을 수 없습니다(같으면 재작업).
- **실제(직접조회 확인)**: 트윈 리프트는 **서로 다른 두 컨테이너를 동시에** 듭니다. 묶는 키는 **`JOB_ODR_TWINKEY`** — 같은 twinkey = 다른 컨테이너 2개 + **같은 트럭 1대**. (예: twinkey…1920739 → CSGU2008444 + CSNU1920739, 둘 다 TT1143)
- **수정**: 후보 수요를 **컨테이너 수가 아니라 트럭-로드 수**로 셉니다 — 트윈 쌍은 1대로(같은 twinkey는 한 번만 카운트). 그래야 매처가 트윈에 트럭 2대를 보내는 과배정을 안 합니다. (검증: 한 베이 40컨테이너 → 29 트럭로드)
- 참고: 작업시간(무브수) 계산은 이미 `twintandem='W'`로 트윈을 옳게 반영하고 있었습니다(무브 ≈ 컨테이너 × (1−트윈비율/2)).

### 2. 마감에 ESTWKC 반영 — 단, "정상값일 때만" 가드
- **보완점**: 우리 배차마감은 **출항(ESTDEP)만** 역산했는데, TOS엔 **ESTWKC(전 크레인 작업완료 예정)** 가 있고 보통 출항보다 빠릅니다 → 이걸 안 보면 트럭을 너무 늦게 보내 RTG 대기가 늘 수 있습니다.
- **⚠️ 그런데 실데이터를 보니 ESTWKC가 대부분 쓰레기값**이었습니다 — 많은 선박이 "작업완료"가 **접안보다 며칠 전**(물리적으로 불가능). 맹목 적용했으면 마감이 다 음수로 깨질 뻔했습니다.
- **수정**: 마감 = `min(출항−버퍼, ESTWKC)` 로 하되, **ESTWKC가 출항 0~6시간 전인 정상값일 때만** 사용(그 외엔 출항 기반). 안전하게 — 정상인 소수 선박에만 더 정확히 적용.
- **교훈**: 소스코드 의미가 맞아도 **실제 데이터 품질은 따로 확인**해야 한다.

## 헛다리 (틀린 줄 알았으나 우리가 맞았던 것 — 재추적 방지)

- **yt_topos**: 한 에이전트가 "QC 번호다"라고 했으나, **prod 직접조회 결과 전부 블록-베이 코드**("02N-06", "06H-2425"). 우리 `block_prefix()`가 출발 블록을 정확히 추출 중. **LD 배차·공정비교·지도 좌표 모두 정상.**
- **KPI 상태필터**: "완료만 집계 안 한다"고 우려했으나, KPI 쿼리들은 `JOB_ORDER_HISTORY`에서 읽고 **그 테이블은 100% 완료('C')건**(최근 87,096행 전부 C). 필터 불필요.

## 우리 강점 (확인됨)

- **OD 이동시간이 TOS보다 실측 기반**: TOS는 거리×가정속도지만, 우리는 **실측 GPS에서 추론한 도로망 위 길찾기**를 씁니다. 현재 2단계 비용의 이동시간 = **도로망 최단시간 경로 → 실측 "실제시간 곡선" 변환**(실제 빈 트립에서 "이 경로시간이면 보통 N초"를 구간별로 계속 학습; 잰 값의 정의 = 순수주행 = 주행 구간 시간 — 경로 정체 포함·핸드오버 대기 제외). 폴백(라우팅 불능 쌍만)은 맨해튼 거리→실제 곡선(콜드스타트만 거리÷3.30 m/s). 도착 후 크레인 대기는 이동시간에서 제외합니다(도착 이후 = 크레인 스케줄 영역).
- **MCMF 최적 매칭**: 단순 방식 대비 총 도착시간 38~43% 절감, anti-thrash(흔들림 4%) 이미 구현.

## 개선 로드맵 (TOS 로직에서 배운 것 · 이득/노력 순)

TOS는 **자체 ITV(트럭) 배차기**(`mover.dispatcher.itv-chooser` + `itv.supervisor.factor/filter`)를 갖고 있어, 그 결정 인자·필터를 우리 비용행렬에 반영할 수 있습니다.

| 우선 | 개선 | 출처(TOS) | 현황 |
|---|---|---|---|
| **A** | Lane Affinity 보너스 | `SAME_LANE_DUAL_CYCLE` | ⏭️ **생략** — TOS DualCycle은 적부계획 수준이고, 우리 OD(빈 위치 근접)가 이미 그 효과를 냄 |
| **B** | 크레인 부하분산 | `QcPriorityAppPow` | ↩️ **되돌림**(bcd146b) — 비용행렬 보너스로 넣었다가 **설계 위배**로 제거. 분산은 **1단계 크레인당 수요 캡**(구조적 천장)이 담당. 아래 "2단계 정리" 참조 |
| **C** | committed window(직전 권고 ETW<10분 near-lock) | `JobPrefetching` | ✅ **유지**(9fb41b3) `COMMIT_LOCK 1200` — anti-thrash라 2단계에 남김 |
| **D** | 무브타임 shift(주/야)별 + ALL 폴백 | `learn_qc_move_time` | ✅ **구현**(792f37f) 야간 ~10-16% 느림 확인. 작업ETA→1단계 마감정렬에 반영 |
| **E** | 특별취급(냉동·위험물·OOG) 제약층 | `Reefer/Hazardous` 필터 | ⏸️ **보류** — ITV는 범용 섀시라 트럭선택 제약 거의 없음(특별취급은 야드/크레인 사안). 실배차 롤아웃 시 **특별 컨테이너를 범위에서 제외**하는 게 맞음(별도 추출층 신설은 이득 대비 과도) |

### 2단계 비용 정리 — "1단계=긴급도, 2단계=순수 효율" (bcd146b)
B를 넣다 발견한 더 큰 문제: **비용행렬(2단계)에 긴급도 항(urgency·starve·load-balance)이 섞여** 있어 원래 2단계 설계("총 도착시간 최소화")를 흐리고 있었습니다. 정리:
- **2단계(매칭) = 순수 효율**: 엣지 비용 = **트럭이 작업지점에 공차로 도착하는 시간**(free_in[트럭이 비는 데 걸리는 시간] + 이동시간) + anti-thrash(switch/committed). 긴급도 항 전부 제거.
- **1단계(선택) = 긴급도 + 캡**: 작업풀을 **(굶는 크레인 먼저 → 마감순)** 으로 정렬, **크레인당 수요 캡**(NEED_HORIZON/move)으로 버킷별 수요를 미리 잘라 2단계로 전달.
- 그 결과 2단계의 **QC 레이어가 중복**(1단계 선택 + 2단계 레이어 이중 캡)이라 제거 — `optimal_assign` 4층→3층.
- **부하분산(B)의 교훈**: "빈 크레인으로 능동 당김"은 총 이동 최소화(효율)와 **충돌**. 독식 방지는 1단계 캡(천장)으로 충분하고, 그 이상의 능동 균등화는 효율을 희생하므로 안 함.

**ACTV_DT 실측보정 (별도 연구)**: 측정 결과 ACTV_DT는 dispatch(YT_DIS_DT)보다 약 9분 **뒤**(DS 중앙 546초) — 트럭 이동+대기 후 QC 양하 시점에 활성화됨이 정합. 다만 "ACTV vs **물리** 핸드오버 완료" 편차는 **우리 GPS 핸드오버 검출과 짝지어** 측정해야 하는 별도 연구(곧-유휴 정확도 좌우). 빠른 쿼리로는 불가 — 데이터 축적 후 진행.
