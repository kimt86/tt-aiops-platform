이 문서는 **트럭 한 바퀴(사이클)를 지금 우리가 어떻게 5단계로 쪼개는지**를 한 곳에 정리한 현행 레퍼런스입니다. (대시보드 화면 설명은 [Cycle 페이지](/kc/dashboard/cycle/), 초기 실험 이력은 [사이클 감지 v2 실험](/kc/experiments/cycle-v2-shadow/)을 보세요.)

이 분해 결과(`tt_cycle_v2` 표)는 **운영 진단·트럭별 분석·배차 학습 데이터**의 토대입니다. 특히 배차 2단계의 **공차 주행 비용**이 여기서 나옵니다.

:::note[구현 상태]
아래는 **정리된 5단계 모델**입니다. 밑단 표(`tt_cycle_v2`)는 아직 옛 "빈차 출발"(`empty_travel_start_at`) 시점을 계산·보관하지만, **모델에서는 더 이상 단계로 쓰지 않습니다**(폐기 진행 중 — §1 참고).
:::

## 0. 먼저 — 왜 어려운가

트럭이 보내주는 GPS에는 `container1`(싣는 박스)이 붙어 있지만, 이건 **"지금 물리적으로 실린 박스"가 아니라 "TOS가 배정한 박스"** 입니다. 트럭이 **빈 차로 픽업하러 가는 동안에도** 이미 채워져 있어요. 그래서 `container1`만 봐서는 "빈 차 구간 / 짐 실은 구간"을 나눌 수 없습니다.

그래서 우리는 **물리적 증거 = GPS 움직임**으로 사이클을 감지하고, 그 안을 **레그(leg)** 단위로 다시 쪼갭니다.

:::note[v1과 v2의 역할 분담]
사이클의 **완료 판정**(한 바퀴가 끝났다)은 기존 v1(`tt_cycle_log`)이 담당합니다 — 박스를 **30초 이상 들고 150m 이상 달렸을 때**만 진짜 인도로 인정(제자리 재배정 가짜를 걸러냄). v2(`tt_cycle_v2`)는 그 **한 바퀴의 내부를 단계로 다시 분해**합니다. 둘은 같은 행 `(트럭, 인도시각)`으로 1:1 대응하고, 같은 곳에서 함께 기록됩니다.
:::

## 1. 5이벤트 · 구간

한 바퀴는 시간 순서로 5개 시점과, 그 사이 구간들로 나뉩니다.

```mermaid
flowchart LR
  O["①배차"] -->|"공차 (배차→픽업 도착)"| PA["②픽업 도착"]
  PA -->|"받기"| PL["③픽업 떠남"]
  PL -->|"부하 이동"| LA["④부하 도착"]
  LA -->|"주기(넘기기)"| D["⑤드롭(사이클 끝)"]
  classDef ev fill:#1e293b,stroke:#94a3b8,color:#fff
  class O,PA,PL,LA,D ev
```

| 이벤트 | 컬럼 | 뜻 |
|---|---|---|
| ① 배차 | `opened_at` | 이 트럭에 새 일이 배정된 순간 |
| ② 픽업 도착 | `empty_arrived_at` | 빈 차로 픽업 지점에 **도착**한 순간 |
| ③ 픽업 떠남 | `pickup_left_at` | 짐 싣고 픽업 지점을 **떠난** 순간(= 상차 완료) |
| ④ 부하 도착 | `laden_arrived_at` | 짐 싣고 하역 지점에 **도착**한 순간 |
| ⑤ 드롭 | `dropped_at` | 인도 완료 = **사이클 끝** (기본키) |

이 5시점이 만드는 구간:

| 구간 | 사이 | 성격 |
|---|---|---|
| **공차** | ①→② | 배차받고 빈 차로 픽업 도착까지 (출발 준비 + 주행) — **배차 2단계 비용의 바탕** |
| 받기 (픽업 핸드오버) | ②→③ | 픽업지 도착~적재 후 출발 |
| **부하 이동** | ③→④ | 짐 싣고 하역지까지 주행 |
| 주기 (드롭 핸드오버) | ④→⑤ | 하역지 도착~인도 완료 |

:::note[왜 "빈차 출발" 시점을 뺐나]
예전 모델은 공차 구간을 "빈차 출발"에서 한 번 더 쪼갰습니다(배차 후 대기 / 순수 주행). 그런데 그 시점이 **가장 안 잡히고**(양하 45%·적하 17%), 쪼개도 얻는 게 없었습니다. 그래서 **빼고 "배차→픽업 도착"을 한 구간**으로 둡니다.

이러면 이 구간의 관측률이 **35%/12% → 69%/85%로** 크게 오릅니다(양 끝만 있으면 되니까). 다만 이 구간엔 **출발 준비 시간이 섞여** 있으므로, 순수 주행 비용은 출발 준비가 거의 0인 **유휴 트럭의 "배차→도착"** 에서 깨끗이 뽑습니다. 바쁜 트럭의 출발 준비 시간은 **트럭의 현재 상태**로 따로 추정합니다.
:::

:::note[핸드오버 "시작" 시점은 왜 없나]
받기·주기의 **정확한 시작 순간**(크레인이 집는 순간)은 웹소켓으로 신뢰성 있게 못 봅니다(크레인 PLC에 트럭 식별자가 없음). 그래서 이 두 구간은 **도착~다음 이벤트의 체류 간격**으로 대신 재고, 별도 "핸드오버 시작" 컬럼은 두지 않습니다.
:::

## 2. 각 시점을 무슨 신호로 잡나

### ① 배차 (`opened_at`)
직전 인도 이후 **처음 들어온 배정 신호**로 엽니다 — `container1`이 빈→참으로 바뀌거나, 목적지 코드(`topos1`)가 새로 바뀌는 순간. 작업종류(양하/적하)는 **이때 확정**해 기록합니다(닫힐 땐 이미 다음 일 정보로 바뀌어 있어서). **100% 잡힙니다.**

### ② 픽업 도착 (`empty_arrived_at`) — 제일 까다로운 부분
"도착"은 여러 신호 중 **가장 믿을 만한 것부터** 골라 잡습니다(우선순위 사다리):

| 순위 | 소스(`arr_src`) | 무엇 |
|---|---|---|
| 1 | `arr_dtime` | 피드가 주는 도착 시각(가장 정확·재시작에 강함) |
| 2 | `arrived` | GPS `ARRIVED` 플래그가 처음 켜지는 순간 |
| 3 | `cur_loc` | 현재 위치 라벨이 목적 블록/안벽과 일치(정지 중일 때만) |
| 4 | `gps` | 크레인 GPS와 60m 이내 근접(크레인 픽업만) |
| — | `container1` | 박스가 빈→참으로 바뀌는 픽업 신호 |
| — | `pre_positioned` | 이미 목적 블록에 정차해 있던 트럭 → 도착=배차 시각 |
| — | `v1` | 위 사다리가 놓쳤을 때, v1 추적기의 도착으로 **사후 보완** |

:::caution[cur_loc는 ~200초 일찍 찍힌다 → 업그레이드]
안벽 대기줄에서는 위치 라벨(`cur_loc=WHARF…`)이 실제 도착보다 **~200초 먼저** latch됩니다. 그래서 `cur_loc` 도착은 **"거친 값"** 으로 두고, 이후 더 정확한 `arr_dtime`/`arrived`가 오면 **덮어써서 교정**합니다(과거 오차 200초→1초로 해결).
:::

### ③ 픽업 떠남 (`pickup_left_at`)
도착한 트럭이 **다시 움직이기 시작**할 때(도착 후 최소 5초 뒤 3km/h 이상), 또는 목적지 코드가 다음 목적지로 바뀔 때. = 상차 완료.

### ④ 부하 도착 (`laden_arrived_at`)
하역 레그의 도착 — ②와 **똑같은 도착 사다리**를 씁니다.

### ⑤ 드롭 (`dropped_at`)
v1의 **검증된 인도**(30초↑ 보유 + 150m↑ 주행)를 그대로 물려받습니다 — `container1`이 비워지는 시점(드롭 도착 후 중앙 ~5.5분). 이 값이 **기본키**이자 v1↔v2 연결 키입니다.

:::note[물리적 드롭의 TOS 정답지가 있다]
`container1` 클리어는 편의 프록시입니다. **진짜 물리적 완료는 TOS 크레인 작업 로그(MCH_OPERATION)** 에 있고, 우리는 이미 RTG측을 `rtg_move_log`(comp_ts = RTG가 트럭에서 컨테이너를 내린 순간)로 추출 중입니다. **양하 드롭의 87%가 여기에 대응**되며 `container1` 클리어와 대체로 일치합니다. → 더 정밀한 드롭 앵커·검증에 쓸 수 있습니다(현재 `dropped_at`엔 미적용). QC측(적하 드롭)도 같은 TOS 표에 있으나 아직 트럭 연결로 추출하진 않았습니다.
:::

## 3. 픽업/드롭이 QC냐 RTG냐 — 그리고 왜 RTG가 안 보이나

같은 "도착·핸드오버"라도 **어느 크레인이냐**에 따라 잘 잡히고 안 잡히고가 갈립니다.

| 작업 | 픽업 측 | 드롭 측 |
|---|---|---|
| **양하(DS)** | 안벽 크레인 **QC** | 야드 블록 **RTG** |
| **적하(LD)** | 야드 블록 **RTG** | 안벽 크레인 **QC** |

(목적지 코드가 `C`/`M`/`Z`+숫자면 크레인, `블록-베이`면 블록.)

:::caution[QC는 잘 보이고, RTG는 잘 안 보인다]
- **QC(안벽)** 는 **PLC 신호**(하중·트롤리 상태)를 우리한테 직접 보냅니다 → 핸드오버가 또렷이 관측됩니다.
- **RTG(야드 블록)** 는 **PLC가 없습니다.** 그래서 "RTG가 이 트럭에 붙었다"는 걸 **GPS 근접(30m)** 이나 TOS의 대략적 활성 신호로만 추정합니다. GPS가 RTG를 30m 안에서 못 짚는 경우가 많아, **양하 드롭 핸드오버는 16%만** 깔끔히 잡힙니다.

이게 양하 트럭의 "곧 빔" 예측이 흐린 근본 원인입니다. → 개선을 위해 **RTG GPS 수집을 시작**했습니다(§6).
:::

## 4. 레그(leg) — 분해의 기본 단위

**레그 1개 = 목적지 코드 1개** (배정 → 도착 → 핸드오버 → 출발). 한 사이클은 두 인도 사이의 **레그들의 연속**입니다. 트럭이 목적지를 바꿀 때마다 레그가 닫히고 새 레그가 열립니다(최대 6개 보관).

인도가 확정되면, 그 사이클의 레그들을 **픽업 쪽 / 드롭 쪽으로 가르고**(양하면 크레인 레그가 드롭, 블록 레그가 픽업), 각 쪽의 도착·출발을 골라 위 이벤트로 채웁니다. 레그 원본은 `legs`(jsonb)에 그대로 저장돼 감사·재분석에 씁니다(목적지·크레인여부·배정/도착/출발 시각·도착 좌표).

## 5. 정직 원칙 — 못 본 건 NULL, 그리고 순서 보증

**추측하지 않습니다.** 관측 못 한 시점은 **빈칸(NULL)** 으로 두고 절대 지어내지 않습니다.

또 시간 순서가 뒤집히면(백필·재시작 탓) **덜 믿을 만한 쪽을 NULL** 처리합니다:
- 픽업 도착 > 픽업 떠남, 픽업 떠남 > 부하 도착 → 그 떠남 NULL
- 픽업 도착 > 부하 도착 → 백필(`v1`)로 들어온 쪽 NULL

### 시점별 데이터 소스 + 포착율 (최근 7일)

각 시점은 **1단계(사이클 완료 즉시 = 웹소켓 GPS 추정)** 로 먼저 채우고, 가능하면 **2단계(추후 TOS 정답지로 보정)** 로 덮습니다.

| 시점 | 1단계: 라이브 추정 (웹소켓) | 2단계: 보정 (TOS 크레인 정답지) | 포착율 DS/LD |
|---|---|---|---|
| ① 배차 | TOS 배정 신호(container1/topos1) | — | 웹소켓 100 / 100 |
| ② 픽업 도착 | 트럭 GPS (arr_dtime·ARRIVED·cur_loc·크레인 근접) | — (크레인 정답지 없음) | 웹소켓 69 / 85 |
| **③ 픽업 떠남**(상차 완료) | 트럭 GPS (도착 후 이동 재개) | **크레인 `comp_ts`**(상차 완료) — LD=RTG 정확 / DS=QC는 단조 가드 | 웹소켓 96 / 73 → **통합 97 / 94** |
| ④ 부하 도착 | 트럭 GPS | — | 웹소켓 87 / 79 |
| ⑤ 드롭(트럭 비움) | `container1` 클리어(v1 이동필터) | (하차 `comp_ts`는 트럭 순간 아님) → 트럭 GPS 가능·미구현 | 웹소켓 100 / 100 |

:::note[포착율 기준 — 웹소켓 / 크레인 / 통합]
포착율은 모두 **웹소켓(1단계)** 기준입니다 — 각 이벤트 컬럼이 채워진 비율. **③만 2단계 크레인 정답지가 얹혀** "통합"(웹소켓 OR 크레인)이 됩니다:
- **적하(LD) ③: 72% → 94%** — 크레인이 웹소켓이 놓친 것을 보완(서로 다른 사이클을 잡음).
- **양하(DS) ③: 96% → 97%** — 웹소켓이 이미 높아 지금은 +1%p뿐이나, QC 로그가 축적되며 상승 + 시각 정확도↑.
- **①②④⑤는 크레인 정답지가 없어 웹소켓 그대로.**
:::

읽는 법:
- **공차 구간(①배차→②픽업 도착)은 양 끝만 있으면 되므로 관측률 = 픽업 도착 = 69%/85%.** (예전처럼 "빈차 출발"까지 요구하면 둘 다 잡힌 비율이 35%/12%로 떨어졌는데, 그 시점을 빼서 해소.) 다만 이 구간엔 출발 준비 시간이 섞여, 순수 주행 비용은 준비 시간이 거의 0인 **유휴 트럭의 배차→도착**에서 뽑습니다.
- **크레인 정답지가 보정하는 건 ③ 픽업 떠남 하나뿐**입니다(§3 참고: 상차=트럭에 실림만 트럭 사건). ②·④·⑤는 크레인으로 못 잡아 웹소켓 GPS 유지.

:::note[2단계 픽업 보정 — 가동 중]
③ 픽업 완료를 크레인 `comp_ts`로 보정하는 루프가 5분마다 돕니다(`pickup_done_at`, mig 0088). 매칭=트럭+컨테이너(`tt_cycle_log.container` ⨝ `crane_log.contno`), **단조 가드**로 `comp_ts`가 [픽업 도착 ~ 부하 도착] 창 안일 때만 채택. 커버리지: **LD ~72%**(RTG 로그 성숙) · **DS ~14%**(QC 로그 방금 시작, 축적되며 상승), 순서 오류 0.

**크레인 시각의 의미(확정)**: TOS `MCH_OPERATION`의 `ST_DT`는 **작업이 TOS에 걸린(큐잉) 시각**(완료 시 소급 기록되어 `ST_DT→comp` 간격이 3~42분으로 극가변 — comp가 늦은 게 아니라 ST가 큐잉). **`comp`(COMPDATE‖COMPTIME)가 물리적 완료(안착)**. RTG(LD 픽업)는 작업이 ~1분이라 `comp` ≈ 상차 완료로 깨끗하고, QC(DS 픽업)는 일부가 늦게/오매칭되지만 위 단조 가드가 걸러냅니다.
:::

## 6. 알려진 한계와 진행 중 대응

- **양하 드롭(RTG) 핸드오버 16%** — RTG에 PLC가 없어 GPS 근접으로만 추정. **RTG GPS 이력 수집을 시작**(`rtg_pos_hist`)해, 블록 격자축 기준으로 GPS 튐을 보정하면 핸드오버 순간을 더 잡을 수 있는지 연구 중.
- **RTG 대기시간은 예측 불가** — RTG는 작업 큐가 없고 선착순도 아니라(부하 기반 평균 대기까지 실험했으나 실패), 개별 트럭 대기는 예측하지 않고 **넓은 밴드**로 다룹니다.
- **공차 구간에 출발 준비가 섞임** — "배차→픽업 도착"은 순수 주행 + 출발 준비이므로, 깨끗한 주행 비용은 유휴 트럭 사이클(준비≈0)에서 뽑고, 바쁜 트럭의 준비 시간은 **트럭 현재 상태**로 따로 추정한다.
