# 연계 송신부 설계 — '이미 보낸 짝'을 잊지 않기 (2026-10-12)

**설계만 했다. 코드·마이그레이션은 없다.** TOS 연계 전에 필요한 송신부의 기억 장치를 정한다.

---

## 한 줄 답

보낸 지시는 **보내기 전에 DB 표에 먼저 적고**(적기 실패 = 안 보냄), 매칭 루프는 **기동할 때 그 표에서 아직 안 풀린
지시를 읽어 고정을 되살린 뒤에야** 첫 지시를 낸다(읽기 실패 = 안 보냄). 고정을 푸는 근거는 지금과 같되,
**'시간 만료'만으로는 풀지 않는다** — 보낸 뒤에 찍힌 작업목록이 와야 푼다(아래 '지금 코드의 빈틈').

---

## 왜 필요한가

- 지금의 '내보낸 짝 고정'(10-08, `crates/api/src/livemap.rs` `held`)은 **메모리에만 있다.** 재시작하면 비어 있다.
- 재시작 직후 첫 틱은 **그때 있는 작업목록으로 바로 돈다**(`should_wake` 의 `(None, Some(_)) → Startup`).
  그 목록은 최대 1분(느릴 때 3분 이상) 전에 찍힌 것이라, **재시작 직전에 보낸 지시가 반영되기 전**의 모습일 수 있다.
  ⇒ 보낸 트럭이 여전히 '빈 트럭', 보낸 상자가 여전히 '미배차'로 보여 **같은 트럭에 두 번째 지시**, 또는
  **같은 상자에 두 번째 트럭**이 나갈 수 있다.
- 재시작은 드물지 않다 — 배포가 곧 API 재시작이다.
- 연계 계약(10-06): 우리 짝 통보 → TOS 가 **즉시 적용**. 그래서 두 번째 지시는 그대로 현장 혼선이 된다.

## 무엇을 저장하나 — 표 초안

```sql
-- 초안 (적용하지 않음). 이름·타입은 구현 사이클에서 확정.
CREATE TABLE IF NOT EXISTS dispatch_sent (
  msg_id        uuid        PRIMARY KEY,            -- 우리가 붙이는 지시 번호 = TOS 쪽 중복 제거 키(TOS 지원 여부 확인 필요)
  kind          text        NOT NULL,               -- 'assign'(짝 통보) | 'swap'(맞바꿈)
  ytno          text        NOT NULL,               -- 트럭
  contno        text        NOT NULL,               -- 상자
  jobtype       text,                               -- DS / LD
  qc            text,                               -- 그 상자를 다룰 안벽 크레인
  swap_peer     uuid        REFERENCES dispatch_sent(msg_id), -- 스왑이면 짝 지시(트럭 둘 = 행 둘)
  tick          bigint,                             -- 이 지시를 낸 매칭 틱(stage2_solver_shadow 와 잇기)
  basis_as_of   timestamptz,                        -- 판단에 쓴 작업목록의 찍힌 시각
  written_at    timestamptz NOT NULL DEFAULT clock_timestamp(), -- 표에 적은 시각(now() 는 트랜잭션 시작이라 쓰지 않는다)
  sent_at       timestamptz,                        -- 송신이 끝난 시각(NULL = 적었지만 보냈는지 모름)
  tos_result    text,                               -- 'applied' | 'rejected' | 'unknown' | NULL(아직 답 없음)
  tos_detail    text,                               -- 거부 사유 등 TOS 응답 원문
  released_at   timestamptz,                        -- 고정이 풀린 시각(NULL = 아직 고정 중)
  release_why   text,                               -- 'listed'(새 목록에 반영) | 'not_listed'(새 목록에 미반영)
                                                    -- | 'truck_busy'(트럭이 더는 빈 트럭 아님) | 'cancelled'
                                                    -- | 'superseded'(같은 트럭의 더 최근 지시) | 'expired_on_restore'(1시간 초과)
  mode          text        NOT NULL                -- 'live' | 'shadow' (그림자에서도 같은 표를 쓴다 — 아래)
);
CREATE INDEX IF NOT EXISTS dispatch_sent_open ON dispatch_sent (written_at) WHERE released_at IS NULL;
CREATE INDEX IF NOT EXISTS dispatch_sent_truck ON dispatch_sent (ytno, written_at);
```

규모: 그림자 기준 하루 새 1계층 짝 **42,714건**(10-11, 같은 트럭의 연속 행에서 상자가 바뀌거나 3분 넘게 끊긴 경우를
'새 짝'으로 셈) + 스왑 **849건**. 21일 보관이면 약 90만 행으로 작다.
(그림자에서는 TOS 가 먼저 다른 짝을 배차해 우리 짝이 계속 바뀌므로, 연계 후 실제 송신량은 이보다 적을 것으로 본다 — 해석.)

## 순서 — 언제 적고 언제 보내나

1. **적는다**: 이번 틱에 새로 낼 1계층 짝(이미 고정 중인 같은 짝은 새 지시가 아니다)과 스왑을 한 트랜잭션으로
   `dispatch_sent` 에 넣는다(`sent_at` NULL). **이 트랜잭션은 잠금 전용 연결 위에서 한다**(아래 '프로세스가 둘이 되면') —
   잠금 세션이 죽었으면 적기가 실패하고, 적기가 실패하면 보내지 않는다. 그래서 잠금을 잃은 줄 모르는 프로세스도 보낼 수 없다
   (2차 리뷰 지적). **커밋이 실패하면 이번 틱은 아무것도 보내지 않는다.**
2. **보낸다**: 커밋된 행만 TOS 로 보낸다. 지시 번호(`msg_id`)를 같이 보낸다.
3. **결과를 적는다**: `sent_at`(송신이 **끝난** 시각)·`tos_result` 갱신. 이 갱신이 실패해도 지시는 이미 나갔으므로 고정은
   유지된다(행은 1에서 이미 있다).
   - **고정의 '보낸 시각' = 송신이 끝난 시각**이다(메모리 경로도 같다). 풀기 규칙 "목록 시각 > 보낸 시각 + 2초"가 실제로 나간
     뒤에 찍힌 목록만 받아들이게 하려는 것이다. `sent_at` 이 NULL 인 행은 **`written_at` + 송신 제한시간 상한**을 보낸 시각으로
     쓴다 — 송신이 재시도로 늦게 나갔을 수 있기 때문이다(2차 리뷰 지적). 송신 제한시간은 송신부가 정하는 상수(구현 때 확정).
4. **죽으면**: 1과 2 사이, 2 도중, 2와 3 사이 어디서 죽어도 행은 남아 있다. 기동 때 `sent_at` NULL 행은
   **"보냈을 수도 있다"로 보고 고정한다**(보수적). TOS 가 지시 번호로 중복을 걸러 준다면 다시 보내도 안전하다 —
   그 전까지는 다시 보내지 않는다.

## 기동 — 고정 되살리기

- 송신 권한(아래 '프로세스가 둘이 되면'의 잠금)을 **얻은 직후, 첫 지시를 내기 전에** `mode='live' AND released_at IS NULL`
  인 행을 **시간으로 자르지 않고 전부** 읽어 메모리 고정(`held`: 트럭 → (상자, 보낸 시각))을 채운다. 스왑 행도 같은 방식으로
  '스왑 동결'과 고정에 넣는다. 잠금을 얻기 전에 읽은 값은 쓰지 않는다 — 그 사이 다른 프로세스가 보낸 지시가 빠진다.
  (그림자 기록기는 `mode='shadow'` 행만 복원한다 — 둘을 섞지 않는다.)
- **같은 트럭에 열린 행이 둘 이상이면 가장 최근 행(보낸 시각 기준)이 이긴다.** 스왑은 그 트럭의 이전 짝을 대체하는 지시다.
  더 오래된 열린 행은 복원하면서 'superseded' 로 닫는다(2차 리뷰 지적 — 안 그러면 옛 짝이 이겨 스왑을 되돌리는 새 지시가 나간다).
- **왜 시간으로 자르지 않나**(2차 리뷰 지적): 신선도 게이트는 '추출이 마지막으로 **성공한** 뒤 경과'를 재지만, 고정을 푸는 데
  쓰는 목록 시각은 추출기가 Oracle 조회 **전에** 찍는다. 그래서 게이트를 통과한 목록도 300초 + 추출 소요만큼 낡을 수 있고,
  어떤 고정된 창 길이도 이 두 시계 차이를 따라 틀릴 수 있다. 대신 풀기가 증거로만 이뤄지므로, 오래된 행은 **보낸 뒤 찍힌
  첫 목록이 오면 바로 풀린다** — 전부 복원해도 해가 없다. 안전 상한으로 1시간보다 오래된 열린 행은 복원하면서
  'expired_on_restore' 로 닫고 경보를 낸다(정상이면 한 행도 없어야 한다 — 열린 채 쌓이는 행을 정리하는 규칙도 겸한다).
- **읽기가 실패하면 송신을 막는다**(그림자 기록만 계속하고 경보). 고정을 모르는 채로 보내는 것보다 한 틱 쉬는 쪽이 낫다.
- 그 뒤 풀기 규칙은 평소와 같다. 기동 직후 목록이 재시작 전에 찍힌 것이면 고정은 안 풀리고, 그 트럭과 상자는
  서로만 본다 — **같은 트럭에 다른 상자, 같은 상자에 다른 트럭이 나가지 않는다.**

## 풀기 — 언제 고정을 놓나

| 근거 | 지금(메모리) | 설계 |
|---|---|---|
| 보낸 뒤에 찍힌 작업목록이 왔다(+2초 여유) | 푼다 | 푼다 · `release_why` = 반영됐으면 'listed', 아니면 'not_listed' |
| 트럭이 더는 '지금 빈 트럭'이 아니다 | 푼다 | **TOS 신호로 바빠진 것이 확인될 때만** 푼다 · 'truck_busy' (아래) |
| 보낸 지 3분이 지났다 | **푼다** | **혼자서는 안 푼다** — 위 두 근거 중 하나가 와야 푼다 |
| 운영자 취소 | 없음 | 'cancelled' (수동) |

**'바빠짐'과 '풀에 없음'을 가른다**(리뷰 지적). 지금 코드는 이번 틱 후보 트럭 목록에 그 트럭이 없으면 바빠진 것으로 보고
푼다(`keep_holds_of_free` 의 `free_now` 는 `vehicles` 에서 나온다). 그런데 트럭은 **자료가 빠져서도** 목록에서 사라진다 —
예: 위치 보충 조회(`truck_pos_hist`)가 한 번 실패하면 `unwrap_or_default` 로 빈 결과가 되고, 위치를 못 찾은 빈 트럭이 그 틱
풀에서 빠진다. 재시작 직후엔 장치 목록이 비어 이 갈래를 더 많이 탄다. 그러면 고정이 풀리고, 다음 틱에 트럭이 돌아왔을 때
목록이 아직 보내기 전 것이면 다른 상자가 나갈 수 있다. ⇒ 설계: **새 배차·픽업·배차 목록 등재 같은 TOS 신호가 그 트럭을 바쁘다고
보여 줄 때만** 'truck_busy' 로 푼다. 단지 이번 틱 풀에 없으면 고정을 그대로 둔다(그 트럭에 지시를 내지 않을 뿐).

**풀린 기록도 남긴다**(`released_at`·`release_why`). 'not_listed' 가 잦으면 TOS 가 우리 지시를 안 받았다는 뜻이다 —
연계 후 첫 점검 지표가 된다.

### 지금 코드의 빈틈 — 3분 만료 (발견, 고치지 않음)

- 지금은 보낸 지 3분(`HOLD_MAX_MS = 180_000`)이 지나면 목록과 무관하게 고정을 푼다.
- 그런데 작업목록이 낡았다고 매칭을 멈추는 문턱은 **300초**다(신선도 게이트).
- ⇒ 작업목록 추출이 3~5분 늦어지면, **보내기 전에 찍힌 목록**으로 틱이 돌면서 고정은 이미 풀린 상태가 된다.
  그러면 같은 트럭에 두 번째 지시가 나갈 수 있다.
- 실제로 일어날 수 있는 지연이다 — `tt-workpool` 은 60일 최장 197초가 걸렸다(노트 기록값, 이번에 다시 재지 않음).
- 설계는 만료를 "보낸 뒤 목록이 왔을 때만 푼다"로 바꾼다. 3분 만료의 원래 목적은 '목록이 안 오면 그 상자가 영영 막히는 것'을
  막는 것이었다. 설계에서 그 경우는 이렇게 된다: 추출이 멈추면 신선도 게이트가 매칭 전체를 멈추므로 막힌 상자가 문제 되지
  않는다. 추출은 도는데 작업목록이 비어 목록 시각이 없을 때(상자가 하나도 없을 때)는 고정이 안 풀리지만, 그때는 막힐 상자도
  없고 목록이 다시 차면 풀린다(2차 리뷰가 '영영 안 풀리는 고정'을 찾지 못함). 두 시계(게이트 = 추출 성공 시각, 풀기 = 목록이
  찍힌 시각)는 다르다는 점에 주의 — 위 '기동' 참조.

## 프로세스가 둘이 되면

배포 중 겹침 등으로 API 가 두 개 뜨면 둘 다 보낸다. **송신 권한은 DB 권고 잠금(`pg_try_advisory_lock`)을 쥔 프로세스만**
갖는다. 잠금을 못 쥔 쪽은 그림자 기록만 한다. 잠금은 연결이 끊기면 저절로 풀린다.

- 권고 잠금은 **DB 연결(세션)에 묶인다.** sqlx 연결 풀에서 아무 연결로 잡으면 그 연결이 풀로 돌아가 다른 질의에 쓰이거나
  닫히면서 잠금 소유가 흐려진다 → **잠금 전용 연결 하나를 따로 열어 계속 쥔다.** 그 연결이 끊기면 송신을 멈추고
  다시 잠금을 얻은 뒤 **고정을 다시 복원**한다.
- **잠금을 잃은 걸 알아채는 방법**: 놀고 있는 연결은 서버 쪽에서 세션이 죽어도 다음에 쓸 때까지 모른다. 그래서 위 '순서' 1단계
  (적기)를 **바로 이 잠금 연결 위에서** 한다. 세션이 죽었으면 적기가 실패하고 송신이 막힌다 — 송신 묶음마다 잠금 소유를 확인하는
  셈이다. 다른 프로세스가 잠금을 이미 얻었다면, 새 연결로 다시 잡으려는 시도가 실패하므로 그쪽은 그림자로 내려간다.
- 순서: 잠금 획득 → 고정 복원 → 송신. 잠금을 잃었다 다시 얻을 때도 같다.

## 스왑

- 스왑은 이미 배차된(픽업 전) 두 트럭의 행선지를 맞바꾸는 지시다. 트럭 하나당 한 행, `swap_peer` 로 서로 잇는다.
- 지금 '배차 사이 1회' 동결은 `stage2_swap_shadow` 를 읽는다(이미 DB라 재시작에 안전). 연계 후에는 `dispatch_sent` 의
  `kind='swap'` 행을 읽도록 옮긴다 — 실제로 보낸 것만 세야 하기 때문이다.
- 스왑을 보낸 두 트럭도 보낸 뒤 목록이 올 때까지 고정한다(다시 스왑하거나 다른 지시를 내지 않는다).
- TOS 가 스왑을 '맞교환 한 번'으로 받는지, '한 방향 옮기기 두 번'으로 받는지는 아직 모른다(TOS팀 질문 목록).
  두 번이면 둘째가 실패할 때 한 상자에 트럭 둘이 남는다 — 그 경우 송신부가 첫째를 되돌리는 규칙이 필요하다.

## 그림자에서 먼저 쓴다

- 송신부가 없어도 `mode='shadow'` 로 같은 표를 지금 채울 수 있다(2단계 '보낸다'를 건너뛴다).
- 그러면 그림자 고정도 재시작에 안전해지고, 연계 전에 **재시작을 사이에 둔 이중 지시 0** 을 실측할 수 있다.
- 권고: 다음 구현 사이클은 '표 + 그림자 기록 + 기동 복원 + 만료 규칙 변경'까지, 실제 송신(2단계)은 TOS 협의 뒤.

## 이 설계가 "재시작 직후 같은 트럭에 두 번째 지시가 나가지 않는다"를 보장하는 방법

1. **지시가 나간 적이 있으면 표에 행이 있다** — 적고 나서 보내므로(1→2). 적지 못하면 보내지 않는다.
2. **기동하면 그 행이 고정으로 돌아온다** — 첫 틱 전에 읽고, 못 읽으면 보내지 않는다.
3. **고정은 그 트럭에 그 상자 간선만 남긴다** — 다른 상자로 가는 간선이 없으니 두 번째 지시를 낼 수 없다
   (지금의 `edge_allowed_by_hold` 그대로). 상자 쪽도 다른 트럭 간선이 막힌다.
4. **고정은 보낸 뒤의 증거로만 풀린다** — 보낸 뒤 찍힌 목록, 또는 TOS 신호로 확인된 트럭 상태 변화. 시간만 흘러서도,
   트럭이 한 틱 풀에서 안 보여서도 풀리지 않는다.
5. **복원은 잠금 뒤, 시간으로 자르지 않는다** — 그래서 프로세스가 바뀌거나 목록이 멈춘 동안 보낸 지시도 빠지지 않는다.
6. **적기는 잠금 연결 위에서 한다** — 잠금을 잃은 줄 모르는 프로세스는 적지 못하고, 적지 못하면 보내지 못한다.
7. **보낸 시각은 송신이 끝난 시각(모르면 적은 시각 + 송신 제한시간)** — 실제 송신보다 먼저 찍힌 목록으로는 풀리지 않는다.

남는 경우: TOS 가 지시를 받고도 목록에 늦게 반영하면(목록 시각 > 보낸 시각인데 반영 전) 'not_listed' 로 풀려 다음 틱에
다른 지시가 나갈 수 있다. 이건 재시작과 무관한 TOS 쪽 반영 지연 문제이고, TOS 의 적용 확인 응답(`tos_result`)이 있으면
'applied' 인 동안은 풀지 않는 규칙으로 막을 수 있다 — TOS팀 확인 필요.

## 구현할 때 검증

- **단위**: 표에서 읽은 행으로 만든 고정이 `edge_allowed_by_hold` 에서 다른 상자를 막는지 · 만료만으로는 안 풀리는지
  · 풀에서 빠진 것만으로는 안 풀리는지 · 읽기 실패 시 송신 차단 플래그가 서는지 · 잠금 전 복원값을 쓰지 않는지 ·
  `sent_at` NULL 행의 보낸 시각이 '적은 시각 + 송신 제한시간'인지 · 같은 트럭의 옛 행이 최근 행에 밀리는지. 돌연변이로 실효성 확인.
- **실측**: 그림자 기록을 켠 뒤 API 를 재시작하고, 재시작 경계를 포함한 창에서
  `psql -v from=… -v to=… -f scripts/hold_conflict_check.sql` → 트럭에 상자 2개+ **0**.

## TOS팀에 물을 것 (추가)

- 지시 번호로 **중복 제거**를 해 주는가(같은 번호를 두 번 받으면 한 번만 적용).
- **적용 확인**을 동기 응답으로 주는가, 아니면 작업목록·배차 이력으로만 알 수 있는가.
- 거부할 때 사유 코드가 있는가.
- 스왑은 맞교환 한 번인가, 옮기기 두 번인가(기존 질문).
